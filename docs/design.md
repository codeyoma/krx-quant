# KRX 4분 예측 엔진 설계

- 작성: 2026-10-08
- 상태: 확정 (설계 인터뷰 Q1–Q34 합의). 구현하며 바뀐 결정은 그 절에 **바뀜**·**삭제됨** 표시로 남긴다(규칙은 [AGENTS.md](../AGENTS.md)의 Documentation).
- 관련 문서: [paid-data.md](paid-data.md) (유료 데이터 조사)

## 1. 목표와 범위

**목표.** KRX 종목의 4분 뒤 가격 움직임을 여러 퀀트 알고리즘이 각자 다른 로직으로 예측하고, 그 예측을 자동 채점해 통계로 보여준다. 결과는 스캘핑할 때 참고 자료로 쓴다. 알고리즘은 매일 스스로 다시 학습한다.

**하지 않는 것.**
- 주문 실행. 엔진에는 주문 코드가 없고, 앞으로도 넣지 않는다.
- 투자 조언. 엔진은 통계 신호만 낸다.

**사용 환경.** macOS(MacBook Pro M4, 16GB)와 Windows. 두 컴퓨터 모두 Fincept Terminal 안의 화면으로 결과를 본다.

## 2. 전체 구조

```
[KIS Open API]
   │ WebSocket(실시간) / REST(조회)
   ▼
[상시 서버: AWS Lightsail 시드니 2GB, Docker]
   수집기 ─► 원본 Parquet(하루 단위) ─► S3 (영구 보관)
   피처 저장소 ─► 알고리즘 N개 ─► Condorcet(합의) ─► 채점·통계(SQLite)
   엔진 API(HTTP/WebSocket) ◄─ Tailscale ◄─ Fincept 화면 (Mac, Windows)
   텔레그램 봇 (장애·비용 알림)

[밤 학습] 거래일 21:30 (지금은 상시 서버의 별도 프로세스, #23에서 EC2 Spot)
   S3 데이터 ─► 학습·검증(champion/challenger) ─► 모델 + 검증 리포트 + 승격 목록 ─► S3
   상시 서버가 다음 거래일 08:00에 새 모델로 교체
```

학습하는 곳과 실시간으로 예측하는 곳을 분리한다. 학습은 PyTorch·LightGBM 등으로 하고, 실시간 예측은 ONNX Runtime 같은 가벼운 런타임으로 한다. 그래서 학습 장비를 바꿔도 상시 서버는 영향을 받지 않는다. 지금 알고리즘(Newton, Gauss, Granger)의 모델은 JSON 파라미터라서 엔진이 직접 계산한다. ONNX는 신경망 알고리즘이 생기면 쓴다.

## 3. 저장소와 upstream 동기화

| 저장소 | 공개 | 내용 |
|---|---|---|
| `codeyoma/FinceptTerminal` | 공개 (GitHub fork는 비공개로 바꿀 수 없음) | Fincept 화면 코드만. 엔진 주소는 설정 파일에서 읽는다. |
| `codeyoma/krx-quant` | 비공개 | 엔진, 알고리즘, 학습 파이프라인, 문서 |

`krx-quant`는 fork를 `fincept/` submodule(`custom` 브랜치)로 포함한다. 그래서 `krx-quant`를 한 번 clone하면 두 저장소를 모두 받는다. 엔진 API 변경과 그에 맞는 화면 버전은 한 커밋으로 묶는다. 이렇게 하면 엔진과 화면 버전이 어긋나지 않는다. 비공개 저장소의 흔적은 공개 fork에 남지 않는다.

**fork 브랜치.**
- `main`: upstream 미러. 직접 커밋하지 않는다.
- `custom`: 개인 빌드. 기본 브랜치다. upstream은 릴리스 태그(v4.x)만 merge 하고, rebase는 하지 않는다. 맥과 윈도우가 같은 이력을 공유하기 때문이다.
- `custom/UPSTREAM_BASE`에 현재 기반 태그를 적는다 (시작: v4.5.0).
- `custom-upstream-watch` workflow가 매주 월요일 09:00 KST에 `main`을 동기화한다. 새 릴리스가 나오면 issue를 연다.
- 반영은 `custom/merge-upstream-release.sh`로 한다. 자세한 내용은 fork의 `custom/README.md`에 있다.

**Fincept 수정 원칙.**
- 새 화면 하나만 추가한다. 화면 등록 때문에 고치는 upstream 파일은 `fincept-qt/CMakeLists.txt`, `src/app/WindowFrame_Setup.cpp`, `src/app/DockScreenRouter.cpp`, `src/ui/navigation/ToolBar.cpp`, `src/ui/navigation/CommandBar.cpp`로 제한한다.
- Fincept SQLite migration은 쓰지 않는다. upstream의 다음 번호와 충돌하기 때문이다.
- 개인 빌드에서는 앱 내 자동 업데이트를 끈다.
- upstream의 예약·릴리스 workflow는 fork에서 disable 했다.

**기타.**
- 라이선스: AGPL-3.0. 개인 사용이므로 문제없다.
- Fincept 로그인: 무료 계정을 그대로 쓴다. 엔진은 로그인과 무관하게 동작한다.
- 빌드: P3에서 GitHub Actions workflow를 만든다. `custom`에 태그를 달면 맥 DMG와 윈도우 `setup.exe`를 만든다. 코드 서명은 없어서 첫 실행 때 Gatekeeper와 SmartScreen 경고를 한 번 허용해야 한다.

## 4. 데이터

### 4.1 출처

- KIS Open API만 쓴다. 실전계좌를 쓴다. 과거 분봉 조회와 선물 실시간에 실전계좌가 필요하다.
- 엔진에는 주문 기능을 구현하지 않는다. CI가 주문 TR 코드가 코드에 들어오는 것을 막는다.
- 나무증권(NH) API는 쓰지 않는다.

### 4.2 종목

- 삼성전자(005930), SK하이닉스(000660), 삼성전기(009150). 사용자가 추가할 수 있다.
- 실시간 구독 한도는 세션(앱키 하나)당 41건이다(2026-10-08 실측). 종목 하나에 6건이 들고, 시장 전체 피드가 약 20건을 쓴다. 그래서 3종목이면 모든 피드가 실시간으로 들어가고, 종목을 늘리면 뒤쪽 피드부터 REST 조회로 바뀌거나 빠진다. 더 늘리려면 KIS 계좌를 하나 더 만들어 앱키를 2개로 쓴다.

### 4.3 실시간 피드

구독 순서와 키, REST 대체는 [kis-feeds.md](kis-feeds.md)에 정리했다. 요약하면 다음과 같다.
- **WebSocket 38건(3종목 기준)**: KOSPI200 선물, 달러선물, 미국 주간거래 NVDA·MU·AMD, 종목별 통합 체결·통합 호가·프로그램매매·회원사, 업종지수 3개, 등가격 ±2 행사가 옵션 10개, KRX 상장 미국 ETF 2개(NXT에서 거래되지 않아 KRX 전용 체결), 종목별 KRX·NXT 전용 체결.
- **REST**: 외국인·기관 추정 가집계(5분 간격), 종목별 VI 현황(5초 간격). 한도를 넘어 잘린 체결·호가·회원사·지수는 REST로 5초마다 조회한다.
- 선물과 옵션 코드는 KIS가 매일 배포하는 마스터 파일에서 최근월물을 찾는다. 옵션 전광판 API는 행사가 높은 쪽 100개만 줘서 쓰지 않는다.

> **바뀜** (2026-10-08, 0f5800c): 처음 계획은 WebSocket 14건(통합 체결·통합 호가·프로그램매매 각 3종목, KOSPI200 선물, 달러선물, 미국 주간거래 3)과 REST 2순위(회원사, 업종지수, KRX 상장 미국 ETF, 옵션 IV, 외국인 추정 가집계를 5–10초 간격)였다. 구독 한도는 "20건 또는 41건, 앱키 하나에 약 8–18종목"으로 가정했다 → 지금은 위와 같다. WebSocket이 38건이고, 늘 REST로 받는 것은 외국인 추정 가집계와 VI 현황뿐이다. 이유: 한도를 41건으로 실측했다. 설계는 "한도가 41건이면 2순위도 WebSocket으로 옮긴다"였다.

### 4.4 과거 데이터

- 주식과 ETF의 1분봉 1년치를 받아 채운다 (`FHKST03010230`, 호출당 120개). 형식은 [events.md](events.md)의 `bars` 계층에 있다.
  - 수집기가 시작할 때와 매일 20:30에 Backfiller가 돈다. 첫 실행은 지난 365일의 모든 거래일을, 그다음부터는 빠진 거래일만 받는다.
  - 하루치는 그날의 모든 장이 끝난 뒤 통째로 받아 파일 하나로 쓴다. 다시 받아도 결과가 같다.
  - 통합(KRX+NXT) 1분봉을 받는다. NXT에서 거래하지 않는 ETF는 KRX 1분봉을 받는다.
- 호가와 틱 체결은 과거 데이터를 무료로 받을 곳이 없다. 그래서 수집기가 직접 녹화한다. 녹화가 빠진 구간은 복구할 수 없어서 결측으로 표시한다(`gaps` 계층, 채울 수 없음).
- 서버 재시작이나 장애로 빈 구간이 생기면 1분봉은 그날 장이 끝난 뒤 하루치를 REST로 받아 채운다. 장중에 바로 채우는 것은 피처 저장소(P2)가 필요할 때 만든다. 피처 저장소(#10)가 생긴 지금도 장중에는 채우지 않는다. 엔진은 재시작한 뒤 받은 체결로만 그날 1분봉을 만든다.
- KOSPI200 선물과 달러선물도 1분봉 1년치를 받는다(`FHKIF03020200`, 호출당 102개). 날마다 그날의 최근월물을 받아 상품마다 연속 1분봉(`KOSPI200F`, `USDF`) 하나로 이어 붙이고, 봉마다 받은 월물 코드를 남긴다.
  - 최근월물은 만기 규칙으로 판정한다. KOSPI200 선물은 분기월 둘째 목요일, 달러선물은 매월 셋째 월요일이 최종거래일이고, 휴장이면 앞 거래일로 당긴다.
  - 최종거래일에는 다음 월물로 바꾼다. 만기 월물은 그날 일찍 끝나고, 다음 월물 거래가 이미 더 많다.
  - 실측과 코드 형식은 [kis-feeds.md](kis-feeds.md#과거-1분봉)에 있다.

> **바뀜** (2026-10-08, #31): 빈 구간의 1분봉을 "자동으로 다시 받아 채운다" → 그날 20:30 뒤에 하루치를 받는다. 장중에 바로 채우는 것은 미뤘다. 이유: 빠진 분은 20:30 뒤에 채워지고, 더 빨리 채우는 일은 P2 피처 저장소에 맡겼다(PR #31 "Not included").

### 4.5 매크로 지표

Macro Collector(`macro.py`, #8)가 거래일마다 07:30(`KRX_MACRO_AT`, 미국 장 마감 뒤)에 아래 지표를 한 번 읽고, 그날의 시장 국면을 정한다. 장중 실시간 피처로는 KIS 실시간 피드(달러선물, KOSPI200 선물, 업종지수, 미국 주간거래, ETF)를 쓴다. 금리와 원자재는 하루 단위 국면 정보로만 쓴다.

| 지표 | 출처 | 코드 |
|---|---|---|
| 원/달러 매매기준율 (`usdkrw`) | 한국은행 ECOS | `731Y001` / `0000001` |
| 국고채 3년 금리 (`ktb3y`) | ECOS | `817Y002` / `010200000` |
| 미국 국채 10년 금리 (`us10y`) | FRED | `DGS10` |
| WTI 유가 (`wti`) | FRED | `DCOILWTICO` |
| 필라델피아 반도체지수 (`sox`), VIX (`vix`), 나스닥100 선물 (`nq`), 엔비디아 (`nvda`), 마이크론 (`mu`) | Yahoo 차트 API | `^SOX`, `^VIX`, `NQ=F`, `NVDA`, `MU` |
| 달러선물 최근월물 (`usdf`) | KIS (이미 받은 백필 1분봉의 종가) | `USDF` |

- 출처마다 따로 읽는다. 한 출처가 실패해도 나머지는 기록된다. 한 출처 안에서도 지표 하나가 실패하면 나머지 지표는 남는다. 실패한 출처는 10분 뒤 다시, 그날 아침 3번까지 읽는다. 같은 출처가 3번 연속 실패하면 텔레그램으로 알리고, 다시 응답하면 해제를 알린다. 실패 횟수와 알림은 메모리에만 있어서, 수집기가 다시 시작하면 처음부터 센다.
- VIX는 FRED(`VIXCLS`)가 아니라 Yahoo에서 받는다. FRED는 하루 늦게 올려서 07:30에는 SOX보다 하루 오래된 값이 된다.
- ECOS와 FRED는 무료 API 키가 필요하다(`KRX_ECOS_API_KEY`, `KRX_FRED_API_KEY`). 키가 없으면 그 출처만 건너뛴다. 발급 방법은 [operations.md](operations.md#22-서버-준비)에 있다.
- 값은 그날(KRX 기준) 전의 것만 쓴다. 7일보다 오래된 값은 없는 것으로 본다.
- 등락률은 KRX 전 거래일 아침에 알던 값에서 오늘 아침에 아는 값까지다. 그래서 미국 휴장 다음 날에는 0이고, KRX 연휴 뒤에는 그동안의 미국 장이 모두 더해진다.

**일일 국면.** 지표를 읽을 때마다 정한다(`regime.py`). 위에서부터 처음 맞는 규칙이 국면이다.

1. `shock`(충격): SOX가 ±3% 이상, VIX가 30 이상, 또는 원/달러가 ±1% 이상 움직였다.
2. `risk_off`(위험회피): SOX가 1% 이상 떨어졌거나, 원화가 0.5% 이상 약해졌다(원/달러 +0.5% 이상).
3. `risk_on`(위험선호): SOX가 1% 이상 올랐고, 원화가 강해졌다(원/달러 하락).
4. `neutral`(중립): 어느 규칙에도 해당하지 않거나, 지표가 하나도 없다.

- SOX는 위의 등락률, VIX는 마지막 종가다. 원/달러는 달러선물 최근월물 종가(전 거래일 장 마감)의 등락률을 먼저 쓴다. 없으면 ECOS 매매기준율(전 거래일 거래로 정해져 하루 더 오래됐다)의 등락률을 쓴다.
- 없는 지표는 어떤 규칙도 만족시키지 않는다.
- 같은 입력이면 늘 같은 국면과 이유가 나온다. 문턱값은 `KRX_REGIME_*` 설정으로 바꾼다.
- Markov(#14)가 국면마다 전이행렬을 따로 배운다.

## 5. 예측 정의

- **시간.** KRX 연속매매 09:00–15:20. 시가·종가 동시호가는 제외한다. 예측 시각은 09:01부터, 채점 시각(t + 4분)이 연속매매 안에 드는 15:16까지다(#9).
- **주기.** 1분봉이 마감될 때마다 모든 알고리즘이 모든 종목을 예측한다.
- **정답 가격.** 통합 중간가다. KRX와 NXT를 합친 최우선 매수호가와 최우선 매도호가의 평균이다. NXT가 열리기 전인 09:00:00–09:00:30에는 KRX 호가만 쓴다.
- **대상.** 예측 시점 t의 중간가 대비 t+4분 중간가의 변화.
- **출력.** P(상승), P(보합), P(하락), 기대수익(틱).
- **보합 판정.** |변화| < k틱이면 보합이다. k는 왕복 거래비용 이상이 되도록 현재가와 호가단위표로 자동 계산한다.
  - 2026년 거래세는 매도 시 0.20%다.
  - 수수료율은 설정값이다.
- **시간 예산.**
  - 알고리즘 하나는 한 번 예측하는 데 최대 30초까지 쓸 수 있다.
  - 서버 전체 CPU 예산은 따로 둔다. 예산을 넘으면 늦게 등록된 알고리즘부터 그 회차를 건너뛰고 기록한다(`runs` 테이블). 순위는 보지 않는다. 경고는 로그에만 남는다.

  > **바뀜** (2026-10-09, #37): "순위가 낮은 알고리즘부터 건너뛰고, 잦으면 서버를 늘리라고 경고한다" → 순위와 상관없이 늦게 등록된 것부터 건너뛰고, 텔레그램 경고는 없다. 이유 기록 없음(PR #37 본문은 텔레그램 경고를 넣지 않았다고만 적었다).
- **합의.**
  - 빠른 합의: 알고리즘 계산을 시작하고(봉 마감 직후) 2초 안에 끝난 정식 알고리즘만 쓴다.
  - 최종 합의: 정식 알고리즘이 모두 끝나거나, 실패하거나, 각자의 시간 예산(30초)에 걸리면 낸다. 그래서 늦어도 계산 시작 +30초쯤이다.

  > **바뀜** (2026-10-10, #42): 빠른 합의 "봉 마감 +2초" → "계산 시작부터 2초". 이유: 엔진이 이미 2초 늦게 돌면 빠른 합의가 늘 비기 때문이다. 가중치 규칙의 바뀐 점은 [engine-api.md](engine-api.md#예측)의 합의 메모에 있다.
- **특수 상황.**
  - VI 단일가매매 중에는 예측하지 않는다.
  - 4분 구간 안에 VI, 서킷브레이커, 사이드카가 끼면 그 예측은 "특수"로 따로 채점한다. 기본 통계에서는 뺀다.

## 6. 채점과 통계

**채점 기준 두 가지.** 모든 예측과 합의를 두 기준으로 모두 채점한다.
- (A) 봉 마감 기준: t의 중간가에서 t+4분 중간가까지. 모델 실력을 본다.
- (B) 표시 시점 기준: 신호가 화면에 표시된 시각의 중간가에서 t+4분 중간가까지. 실제로 신호를 따라 매매했을 때의 성적이다. **화면 맨 위에는 (B)를 보여준다.**

**헤드라인 지표.** 95% 신뢰구간을 함께 보여준다.
- 방향 정밀도: 상승·하락이라고 예측한 것 중 맞은 비율. 커버리지(방향을 예측한 비율)와 함께 본다.
- 기준 예측 대비 개선폭(lift). 기준 예측은 "항상 보합", "직전 4분 방향 지속", "클래스 비율대로 무작위" 세 가지다. lift는 같은 종목·봉 마감끼리 짝지은 3클래스 정답률 차이다. 순위는 세 lift 중 가장 작은 것의 신뢰구간 하한으로 정한다(#11). 정의는 [engine-api.md](engine-api.md#통계와-순위표)에 있다.
- 비용 반영 가상손익(틱).

**상세 지표.**
- 3클래스 정확도
- Brier 점수와 보정도
- 분해: 종목별, 30분 시간대별, 모델 버전별, 기간별(오늘/5일/20일)

**운 보정.** 알고리즘이 많으면 운으로 상위에 오르는 경우가 생긴다. 이를 막기 위해 다음을 적용한다.
- 순위표는 평균이 아니라 신뢰구간 하한으로 정렬한다.
- 최소 표본 수를 채운 알고리즘만 순위에 올린다.
- 기준 예측 대비 개선은 FDR 보정으로 판정한다.
- Condorcet 가중치는 균등 쪽으로 당긴다(shrinkage). 여러 기간에서 꾸준한 알고리즘만 가중치를 올린다.

## 7. 알고리즘

### 7.1 명단 (v1)

지금 구현된 것은 Newton(#10), Gauss(#13), Granger(#15), Condorcet(#18)뿐이다(`algorithms/__init__.py`의 `ALGORITHMS`). Markov(#14), Turing(#16), Kalman(#25), Shannon(#26), Poisson(#27)은 계획이다.

"시작" 열은 처음 계획이다. "첫날"은 1분봉 1년치로 바로 시작한다는 뜻이고, "수습"은 호가 녹화가 10거래일 쌓일 때까지 순위표와 합의에서 빠진다는 뜻이었다. 지금은 모든 알고리즘이 처음 돌 때 수습(`probation`)으로 시작한다(7.5). 수습 알고리즘도 순위표에는 나오고, 합의에서만 빠진다.

| Gauss | 역추세 | 당일 VWAP 대비 z-score를 구하고, Ornstein–Uhlenbeck 평균회귀 속도로 되돌림 확률을 낸다. | **VWAP 대비 z-score, 평균회귀 속도**, 실현변동성 | OU 파라미터, z 임계값 | 첫날 |
| Kalman (계획, #25) | 잡음 제거, 선물 추종 | 상태공간 모델로 microprice에서 숨은 적정가와 추세를 추정한다. KOSPI200 선물을 외부 입력으로 쓴다. | **선물을 입력으로 받는 필터**, microprice, 베이시스 | EM으로 잡음 공분산 추정 | 수습 |
| Shannon (계획, #26) | 호가창 해독 | 주문흐름 불균형(OFI), 잔량 불균형, 체결방향 엔트로피로 다항 로지스틱 회귀를 한다. | **OFI, 체결방향 엔트로피**, 10단계 호가, KRX/NXT 체결 비중, 프로그램매매, 회원사 흐름 | L1 로지스틱 재학습 | 수습 |
| Poisson (계획, #27) | 쏠림 감지 | 매수·매도 시장가 체결의 도착을 Hawkes 과정(자기흥분 점과정)으로 모델링한다. 어느 쪽 쏠림이 강한지 본다. | **체결 도착 시각·방향·크기만** | 최대우도로 강도 파라미터 추정 | 수습 |
| Markov (계획, #14) | 국면 탐정 | 4국면(조용함/상승추세/하락추세/급변동) 은닉 마르코프 모델을 쓴다. 다음 국면 전이확률을 예측으로 바꾼다. | **매크로 일일 국면별 전이행렬**, 옵션 IV 국면, 변동성, 스프레드, 시간대 | Baum–Welch 재추정 | 첫날 |
| Granger | 이웃 관찰 | Granger 인과 검정으로 선행-후행 관계를 찾아 회귀한다. 이웃 종목과 시장 지표가 먼저 움직인 것을 반영한다. | **3종목 간 시차, 달러선물, 업종지수, 미국 주간거래 MU·NVDA, KRX 상장 미국 ETF** | 시차와 계수 재선택 | 첫날 (선물·ETF·다른 종목 묶음은 백필로도 학습한다. 지수와 미국 주간거래 묶음은 녹화된 날로만 학습하고, 학습 구간의 절반 넘게 녹화가 쌓이면 시험한다) |
| Turing (계획, #16) | 만능 학습 | LightGBM으로 상승/보합/하락을 분류한다. | 전체 피처 + **시간대, 옵션 만기일, 투자자별·프로그램매매·회원사 흐름** | 최근 60거래일 롤링 재학습 | 첫날은 1분봉 버전, 10거래일 뒤 호가 피처 추가 |
| Condorcet (메타) | 합의 | 각 알고리즘의 확률을 최근 성적(종목·시간대별 로그손실)으로 가중해 합친다. 수습·벤치·복제 상태는 뺀다. | 각 알고리즘 출력과 최근 성적 | 가중치 재계산 | 첫날 |

- 예비 후보: Mandelbrot. Hurst 지수로 추세 지속과 되돌림을 판정해 둘 사이를 전환한다. Markov와 역할이 겹쳐 v1에서는 뺐다.
- 알고리즘끼리는 서로의 출력을 보지 않는다. 출력을 합치는 것은 Condorcet뿐이다.

### 7.2 알고리즘 모듈 규약

- 위치: `src/krx_quant/algorithms/<name>/`. 규약, 등록 검사, 피처, 학습 명령은 [engine-api.md](engine-api.md#알고리즘)에 있다(#10).
- 각 모듈은 공통 인터페이스를 따른다. 사용하는 피처 선언, `fit`, `predict`, 모델 버전.
- 각 모듈에는 **성격 카드**를 둔다. 과학자, 핵심 로직, 고유 피처, 학습 방법을 적는다.
- 피처는 공용 피처 저장소가 1분에 한 번만 계산한다. 알고리즘은 그 결과를 공유한다.
- 엔진은 예측 종목 말고도 선행 시리즈(KOSPI200·달러 선물, 지수, 미국 주간거래, ETF)의 1분봉을 피드에서 따로 만든다. 피처는 봉 마감 시점의 봉만 본다(#15).

### 7.3 개성 검사

- 등록할 때: 피처 조합이 기존 알고리즘과 같거나 고유 피처가 하나도 없으면 거부한다. 고유 피처는 먼저 등록된 알고리즘이 쓰지 않는 피처여야 한다(#10).
- 수습 중: 기존 알고리즘과의 예측 상관이 0.9를 넘으면 "복제"로 표시하고 합의에서 뺀다.
- 상태(수습, 정식, 벤치, 은퇴, 복제)와 전환 규칙은 [engine-api.md](engine-api.md#상태-관리-17)에 있다(#17).

### 7.4 새 알고리즘 추가 절차

1. 모듈과 성격 카드를 작성한다.
2. 재생 테스트를 통과시킨다. 저장된 최근 20거래일 데이터로 돌려서 실시간과 같은 채점·통계를 낸다. 시간 예산과 개성 검사도 이때 확인한다. 20거래일을 한 번에 돌리는 사전 검증 도구는 아직 없다(#24). 지금은 `krx-quant replay <날짜>`로 하루씩 돌리고, 개성 검사는 `ALGORITHMS`에 등록할 때(`register`) 한다.
3. 수습으로 시작한다. 공식 성적은 실시간 결과만 인정한다.

### 7.5 상태 관리

| 상태 | 합의 참여 | 진입 조건 |
|---|---|---|
| 수습 | X | 새로 등록됨 |
| 정식 | O | 수습 10거래일 후, 기준 대비 lift의 신뢰구간 하한 > 0 (자동) |
| 벤치 | X (예측·채점은 계속) | 정식 중 최근 20거래일 lift ≤ 0 (자동) |
| 은퇴 | X (예측 중단, 기록 보존) | 벤치 60거래일 동안 회복 없음 → 은퇴 후보 → 사용자 승인 |
| 복제 | X (예측·채점은 계속) | 수습 중 먼저 등록된 알고리즘과 예측 상관 > 0.9 (자동, 상관이 내려가면 수습으로) |

- 벤치에서 최근 20거래일 lift 하한이 0보다 커지면 정식으로 돌아간다. 판정 통계와 세부 규칙은 [engine-api.md](engine-api.md#상태-관리-17)에 있다(#17).
- 정식 승격은 lift 신뢰구간 하한으로 판정한다. 순위표의 FDR 보정 q값은 판정에 쓰지 않는다.

## 8. 학습

- 학습은 그날 1분봉 백필(20:30)과 업로드(21:00)가 끝난 뒤 시작한다. 지금은 Lightsail 수집기가 21:30에 별도 프로세스로 돌린다(#22). #23에서 EventBridge Scheduler가 EC2 Spot 인스턴스를 띄우도록 옮긴다. 기본은 CPU 인스턴스이고, 신경망 알고리즘이 있을 때만 GPU 인스턴스를 쓴다.
- 각 알고리즘은 롤링 구간 데이터로 walk-forward 학습을 한다. 기본 구간은 20거래일이고 Turing은 60거래일이다.
- 녹화된 날은 녹화 이벤트로 학습한다. 1분봉, 선행 묶음, 기준가(중간가)가 엔진이 본 것과 같고, 정답도 실전 채점과 같다. 백필만 있는 날은 1분봉 종가로 학습한다([engine-api.md](engine-api.md#학습)).
- 새 모델(challenger)이 학습에 쓰지 않은 최근 3거래일에서 현재 모델(champion, 서버가 돌리는 모델)보다 log loss가 낮을 때만 교체한다.
- 결과 모델(지금은 JSON 파라미터, 신경망이 생기면 ONNX), 검증 리포트, 승격 목록을 S3에 올린다. EC2에서는 끝나면 인스턴스가 스스로 종료한다.
- 상시 서버는 다음 날 08:00에 새 모델로 교체한다.
- 07:30까지 학습이 끝나지 않으면 기존 모델을 그대로 쓴다.
- Spot 인스턴스가 중간에 회수되면 체크포인트(알고리즘별 검증 리포트)부터 다시 시작한다.
- 모델 버전 이력을 남기고 `krx-quant rollback <알고리즘>` 한 번으로 되돌릴 수 있다. 모든 예측에는 모델 버전을 기록한다. 운영 절차는 [operations.md](operations.md#밤-학습과-모델-교체-22)에 있다.

> **바뀜** (2026-10-10, #45): "매일 16:00 KST에 EventBridge Scheduler가 EC2 Spot을 띄우고, 모델은 ONNX" → 거래일 21:30(`KRX_TRAIN_AT`)에 상시 서버의 수집기가 별도 프로세스로 학습하고, 모델은 JSON 파라미터다. EC2 Spot은 #23으로 미뤘다. 이유: 그날 1분봉은 20:30에 백필하고 21:00에 올린다. 16:00에 학습하면 전날까지의 봉만 본다(PR #45). 16:00을 원하면 하루 늦은 데이터로 `KRX_TRAIN_AT=16:00`을 쓴다.

## 9. 인프라와 비용

- **상시 서버.** Lightsail 시드니(`ap-southeast-2`) 2GB, 월 $12. IPv4 주소가 있는 요금제여야 한다. KIS 서버에 IPv6 주소가 없기 때문이다. 엔진은 Docker로 띄운다.
  - 서울이 아니라 시드니인 이유: 2026-10-08에 AWS의 새 가입 방식(AWS Settings 프로젝트)으로 계정을 만들었다. 이 방식에서는 프로젝트마다 리전이 하나뿐이고, 연락처 주소의 국가에 따라 오하이오·스톡홀름·시드니 중 하나로 정해진다. 서울을 쓰려면 고급 기능을 활성화해야 하는데 되돌릴 수 없어서, 시드니에 둔다.
  - KIS까지 왕복 지연이 100ms 넘게 늘어나지만, 4분 뒤를 예측하는 데는 무시할 만하다.
  - 학습용 EC2 Spot과 S3도 같은 리전에 둔다. 리전 사이 데이터 전송 요금을 피하기 위해서다.
  - Lightsail은 버스트형 CPU다. 부하가 늘면 4GB($24) 요금제나 비버스트형 EC2로 옮긴다.

  > **바뀜** (2026-10-08, #34): 서울(`ap-northeast-2`), Lightsail 번들 `small_3_0` → 시드니(`ap-southeast-2`), 번들은 리전에서 자동으로 고른다(시드니 `small_3_2`). 코드 기본값(`AWS_REGION`)과 `.env.example`도 바꿨다. 이유: 새 가입 방식의 계정은 리전이 하나뿐이고, 서울을 쓰려면 되돌릴 수 없는 고급 기능을 켜야 한다(위). 번들 ID는 리전마다 다르다.
- **접속.** Tailscale(무료)로 상시 서버, 맥, 윈도우를 연결한다. 서버 포트는 인터넷에 열지 않는다.
- **비밀값.** API 키 등은 서버의 `.env` 파일(권한 600)에만 둔다. 저장소에는 커밋하지 않는다.
  - 예외: KIS가 발급한 REST 접근 토큰은 `state/kis_token.json`(권한 600)에 캐시한다. KIS가 토큰 발급을 분당 1회로 제한해서, 재시작할 때마다 새로 받으면 발급이 거절되기 때문이다. 이 파일도 git과 Docker 이미지에서 제외한다.
  - WebSocket 승인키는 메모리에만 두고, 20시간이 지나면 재연결할 때 새로 받는다. 승인키는 구독을 등록할 때만 쓰여서, 연결이 유지되는 동안에는 바꿀 필요가 없다.
- **비용 상한: 월 $100.**
  - AWS Budgets로 $50과 $80에 텔레그램 알림을 보낸다(계획, #23. 아직 없다).
  - $100에 도달하면 그달 남은 기간은 Spot 학습을 멈춘다. 실시간 예측은 계속한다(계획, #23).
  - 예상 비용: 서버 $12, S3 $1 미만, Spot 학습 $3–15(미확인).
  - 지금은 AWS 프로젝트 지출 한도($100)가 걸려 있다. 한도에 닿으면 프로젝트 전체가 일시정지되어 상시 서버도 멈추므로, 위의 "실시간 예측은 계속한다"와 맞지 않는다. Budgets 기반 상한으로 바꿀지는 #23에서 정한다.
- **장애 알림.** 텔레그램 봇으로 보낸다. 대상은 KIS 연결 끊김, 데이터 지연, 장 마감 업로드 실패, 엔진 API 실패, 밤 학습 실패다. 밤 학습 요약, 모델 교체, 은퇴 후보, 서버 자동 업데이트 결과도 보낸다. 전체 목록은 [operations.md](operations.md#6-장애-대응)에 있다. 비용 경고(AWS Budgets)는 아직 없다(#23).

## 10. Fincept 화면

- **구성.** 종목별로 다음을 보여준다.
  - 1분봉 차트에 합의 예측 화살표와 채점 결과(✓/✗)를 겹쳐 표시
  - 알고리즘별 예측 패널: 상승/보합/하락 확률, 기대수익(틱), 빠른·최종 합의, 채점까지 남은 시간
  - 순위표: 오늘/5일/20일 성적과 모델 버전, 상태
  - 매크로 줄: 달러선물, 오늘의 시장 국면
  - 엔진 상태: KIS 연결, 데이터 지연, 어젯밤 학습 결과(교체 여부)
- **신호 알림.** Condorcet 확률이 기준값 이상이고 N개 이상의 알고리즘이 같은 방향이면 데스크톱 알림과 소리를 낸다. 기준값과 N은 화면에서 조정한다. 텔레그램 신호 알림은 옵션이다.
- **언어.** 한국어. 알고리즘 이름은 영어로 쓴다.
- **지금 있는 것 (#20).** 첫 화면 **KRX 4분 예측**이다. Navigate → Trading & Portfolio에서 연다. 명령 팔레트에서 "krx"로 찾아도 된다.
  - 위쪽: 엔진 상태(장 단계, 마지막 봉 마감, 채점 대기, KIS 연결, 지난밤 학습)와 오늘의 특수 상황.
  - 표: 종목마다 기준가와 최신 봉 마감의 예측. 합의(최종·빠른), 알고리즘, 기준 예측 순이다. 열은 방향, 상승·보합·하락 확률, 기대 틱, 모델 버전이다. 상승과 하락이 같은 정수 %로 보이면 방향은 비운다.
  - 화면이 보이는 동안 5초마다 엔진 API(`/v1/status`, `/v1/symbols`, `/v1/symbols/<종목>/latest`)를 읽는다. 실패하면 이유를 보여주고 지난 예측은 지운다.
  - 엔진 주소는 화면 위 칸에 넣는다. 서버는 `http://krx-quant:8080`(Tailscale), 데모 엔진은 `http://127.0.0.1:8090`이다. 공개 fork에는 주소를 넣지 않아서 처음에는 비어 있다.
  - 차트, 순위표, 매크로 줄, 신호 알림은 #21에서 만든다.
