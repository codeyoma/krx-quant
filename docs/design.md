- 작성: 2026-10-08

- 관련 문서: [paid-data.md](paid-data.md) (유료 데이터 조사)

## 1. 목표와 범위

**목표.** KRX 종목의 4분 뒤 가격 움직임을 여러 퀀트 알고리즘이 각자 다른 로직으로 예측하고, 그 예측을 자동 채점해 통계로 보여준다. 결과는 스캘핑할 때 참고 자료로 쓴다. 알고리즘은 매일 스스로 다시 학습한다.

**하지 않는 것.**
- 주문 실행. 엔진에는 주문 코드가 없고, 앞으로도 넣지 않는다.
- 투자 조언. 엔진은 통계 신호만 낸다.

**사용 환경.** macOS(MacBook Pro M4, 16GB)와 Windows. 두 컴퓨터 모두 Fincept Terminal 안의 화면으로 결과를 본다.

## 2. 전체 구조

```
[KIS Open API]
   │ WebSocket(실시간) / REST(조회)
   ▼
[상시 서버: AWS Lightsail 시드니 2GB, Docker]
   수집기 ─► 원본 Parquet(하루 단위) ─► S3 (영구 보관)
   피처 저장소 ─► 알고리즘 N개 ─► Condorcet(합의) ─► 채점·통계(SQLite)
   엔진 API(HTTP/WebSocket) ◄─ Tailscale ◄─ Fincept 화면 (Mac, Windows)
   텔레그램 봇 (장애·비용 알림)

[밤 학습] 거래일 21:30 (상시 서버의 별도 프로세스, 또는 EC2 Spot. KRX_TRAIN_ON, #23)
   S3 데이터 ─► 학습·검증(champion/challenger) ─► 모델 + 검증 리포트 + 승격 목록 ─► S3
   상시 서버가 다음 거래일 08:00에 새 모델로 교체

[예약 작업] 매일 22:30, 밤 학습 뒤 (상시 서버의 별도 프로세스, #215)
   krx-quant 명령(진단, 사전 검증 등) ─► 출력 가림 ─► GitHub 이슈 댓글 + 라벨(ready-for-agent) ─► 에이전트가 읽음
```

학습하는 곳과 실시간으로 예측하는 곳을 분리한다. 학습은 PyTorch·LightGBM 등으로 하고, 실시간 예측은 ONNX Runtime 같은 가벼운 런타임으로 한다. 그래서 학습 장비를 바꿔도 상시 서버는 영향을 받지 않는다. 지금 알고리즘(Newton, Gauss, Granger, Markov)의 모델은 JSON 파라미터라서 엔진이 직접 계산한다. Turing은 LightGBM 트리를 텍스트로 모델 JSON에 넣고, 엔진이 LightGBM으로 그대로 예측한다(종목당 1ms 아래). ONNX는 신경망 알고리즘이 생기면 쓴다.

## 3. 저장소와 upstream 동기화

| 저장소 | 공개 | 내용 |
|---|---|---|
| `codeyoma/FinceptTerminal` | 공개 (GitHub fork는 비공개로 바꿀 수 없음) | Fincept 화면 코드만. 엔진 주소는 설정 파일에서 읽는다. |
| `codeyoma/krx-quant` | 공개 (2026-10-14부터) | 엔진, 알고리즘, 학습 파이프라인, 문서 |

`krx-quant`는 fork를 `fincept/` submodule(`custom` 브랜치)로 포함한다. 그래서 `krx-quant`를 한 번 clone하면 두 저장소를 모두 받는다. 포인터는 언제나 `custom`의 최신 커밋을 가리킨다(#186). fork의 `custom-krx-pointer` workflow가 `custom`에 push 될 때마다 krx-quant에 `repository_dispatch`를 보내고, krx-quant의 `fincept-pointer` workflow가 포인터만 바꾼 커밋을 `main`에 바로 push 한다. 매일 05:30 KST 실행과 손 실행이 놓친 것을 잡는다. 화면이 엔진 변경에 기대면 엔진 PR을 먼저 머지한다. 엔진 코드와 알고리즘 설명은 이 저장소에만 두고, 화면 코드는 엔진이 API로 주는 것을 보이기만 한다. 두 저장소 모두 공개라 비밀값(`.env`), 녹화 시세, 서버 주소는 어디에도 커밋하지 않는다.

> **바뀜** (2026-10-14, #188): 엔진 API 변경과 그에 맞는 화면 버전(포인터)을 한 커밋으로 묶었다 → 포인터는 workflow가 `custom` 최신으로 옮기고, 화면 PR은 포인터를 건드리지 않는다. 이유: 화면 PR 둘이 동시에 열리면 포인터에서 충돌하고, fork PR을 squash 머지한 뒤 포인터를 다시 옮겨야 했다. krx-quant의 CI·배포·엔진은 `fincept/`를 읽지 않아 포인터는 기록일 뿐이다. 사용자가 늘 `custom` 최신을 가리키기로 정했다(#186).

> **바뀜** (2026-10-14, #194): `krx-quant`는 비공개였고, 엔진과 알고리즘 설명이 공개 fork에 새지 않게 나눴다("비공개 저장소의 흔적은 공개 fork에 남지 않는다") → 둘 다 공개다. 나눈 구조(화면 코드만 fork에)는 그대로 둔다. 이유: 비공개 저장소의 GitHub Actions 시간이 바닥났고(공개는 무료), 알고리즘과 모델은 보여도 된다고 정했다(2026-10-14). 공개 전에 git 이력, 이슈, PR에 비밀값, 데이터 파일, 서버 주소가 없는 것을 확인했다.

**fork 브랜치.**
- `main`: upstream 미러. 직접 커밋하지 않는다.
- `custom`: 개인 빌드. 기본 브랜치다. upstream은 릴리스 태그(v4.x)만 merge 하고, rebase는 하지 않는다. 맥과 윈도우가 같은 이력을 공유하기 때문이다.
- `custom/UPSTREAM_BASE`에 현재 기반 태그를 적는다 (시작: v4.5.0).
- `custom-upstream-watch` workflow가 매일 05:00 KST에 `main`을 동기화하고, upstream의 새 릴리스를 반영한다.
  - runner에서 `custom/merge-upstream-release.sh`로 `custom`에 merge 하고, 그 결과(`upstream-merge/<tag>` 브랜치)를 `custom-release`로 시험 빌드한다.
  - 맥과 윈도우 빌드가 통과하면 `custom`에 반영하고 `custom-<tag>-krx.1` 태그로 개인 빌드를 낸다. 설치된 앱은 이 빌드를 업데이트로 받는다(10장의 "개인 빌드").
  - 충돌이나 빌드 실패면 `custom`은 그대로 두고 fork에 issue를 연다. 그때는 손으로 `custom/merge-upstream-release.sh`를 돌린다.
  - 자동 반영에는 fork의 `SYNC_TOKEN` secret이 꼭 있어야 한다(12장). 없으면 merge 결과를 push 하지 못해 issue로 끝난다.
  - 자세한 내용은 fork의 `custom/README.md` "upstream 릴리스 반영"에 있다.
  > **바뀜** (2026-10-12, #94): 매주 월요일 09:00 KST에 새 릴리스를 issue로 알리고 반영은 손으로 했다 → 매일 05:00 KST에 merge·시험 빌드·`custom` 반영·태그까지 자동으로 한다. 이유: upstream이 릴리스를 내면 업데이트가 저절로 돌게 하려고(#93).

**Fincept 수정 원칙.**
- 새 화면 하나와 로컬 CLI LLM provider(#96)만 추가한다. 고치는 upstream 파일은 16개로 제한한다.
  - 화면 등록: `fincept-qt/CMakeLists.txt`(공식 업데이트를 끄는 `FINCEPT_DISABLE_AUTO_UPDATE` 옵션, 빌드 태그 `FINCEPT_CUSTOM_TAG`, 업데이트 도우미 리소스도), `src/app/WindowFrame_Setup.cpp`, `src/app/DockScreenRouter.cpp`, `src/ui/navigation/ToolBar.cpp`, `src/ui/navigation/CommandBar.cpp`
  - 화면 테스트 등록: `fincept-qt/tests/CMakeLists.txt`(`krx_quant.cmake`를 include 하는 한 줄. 테스트는 새 파일 `fincept-qt/tests/krx_quant.cmake`에 등록한다. 그래서 upstream이 파일 끝에 붙이는 테스트와 merge 충돌하지 않는다. #93)
  - 공식 업데이트 대신 개인 빌드 업데이트로 넘기기: `src/services/updater/UpdateService.cpp`
  - 로컬 CLI LLM provider(#96, 10장의 "로컬 CLI LLM"): `src/services/llm/ProviderCatalog.cpp`, `LlmService.h`, `LlmService.cpp`, `LlmFinceptAsync.cpp`, `LlmModelsApi.cpp`, `src/screens/settings/LlmConfigSection_Providers.cpp`, `LlmConfigSection_Profiles.cpp`, `src/services/alpha_arena/ArenaModelRegistry.cpp`, `src/mcp/ProviderToolFormatSelfTest.cpp`. 새 코드는 `src/services/krx_quant/LocalCli*`에 두고, 이 파일들에는 한두 줄짜리 갈래만 넣는다.

  > **바뀜** (2026-10-12, #97): "새 화면 하나만 추가한다", 고치는 upstream 파일 7개 → 로컬 CLI LLM provider도 추가하고 16개(위 LLM 파일 9개). 이유: Fincept의 LLM 기능을 Fincept 크레딧이나 API key 대신 이 컴퓨터에 로그인된 Claude Code·Codex CLI(구독)로 쓰려면 provider 목록, 요청 경로, 설정 화면에 갈래가 필요했다(#96).

- Fincept SQLite migration은 쓰지 않는다. upstream의 다음 번호와 충돌하기 때문이다.
- 개인 빌드에서는 공식 버전 업데이트를 끈다. 대신 fork의 개인 빌드 Release에서 버튼 한 번으로 업데이트한다(#92, 10장의 "개인 빌드").

  > **바뀜** (2026-10-12, #95): "개인 빌드에서는 앱 내 자동 업데이트를 끈다" → 공식 업데이트만 끄고 개인 빌드 Release에서 업데이트한다. 이유: 새 화면 빌드마다 DMG·setup.exe를 받아 직접 다시 설치해야 했다(#92).
- upstream의 예약·릴리스 workflow는 fork에서 disable 했다.

**기타.**
- 라이선스: AGPL-3.0. 개인 사용이므로 문제없다.
- Fincept 로그인: 무료 계정을 그대로 쓴다. 엔진은 로그인과 무관하게 동작한다.

### 4.5 매크로 지표

Macro Collector(`macro.py`, #8)가 거래일마다 07:30(`KRX_MACRO_AT`, 미국 장 마감 뒤)에 아래 지표를 한 번 읽고, 그날의 시장 국면을 정한다. 장중 실시간 피처로는 KIS 실시간 피드(달러선물, KOSPI200 선물, 업종지수, 미국 주간거래, ETF)를 쓴다. 금리와 원자재는 하루 단위 국면 정보로만 쓴다.

| 지표 | 출처 | 코드 |
|---|---|---|
| 원/달러 매매기준율 (`usdkrw`) | 한국은행 ECOS | `731Y001` / `0000001` |
| 국고채 3년 금리 (`ktb3y`) | ECOS | `817Y002` / `010200000` |
| 미국 국채 10년 금리 (`us10y`) | FRED | `DGS10` |

- 출처마다 따로 읽는다. 한 출처가 실패해도 나머지는 기록된다. 한 출처 안에서도 지표 하나가 실패하면 나머지 지표는 남는다. 실패한 출처는 10분 뒤 다시, 그날 아침 3번까지 읽는다. 같은 출처가 3번 연속 실패하면 텔레그램으로 알리고, 다시 응답하면 해제를 알린다. 실패 횟수와 알림은 메모리에만 있어서, 수집기가 다시 시작하면 처음부터 센다.
- VIX는 FRED(`VIXCLS`)가 아니라 Yahoo에서 받는다. FRED는 하루 늦게 올려서 07:30에는 SOX보다 하루 오래된 값이 된다.
- ECOS와 FRED는 무료 API 키가 필요하다(`KRX_ECOS_API_KEY`, `KRX_FRED_API_KEY`). 키가 없으면 그 출처만 건너뛴다. 발급 방법은 [operations.md](operations.md#22-서버-준비)에 있다.
- 값은 그날(KRX 기준) 전의 것만 쓴다. 7일보다 오래된 값은 없는 것으로 본다.
- 등락률은 KRX 전 거래일 아침에 알던 값에서 오늘 아침에 아는 값까지다. 그래서 미국 휴장 다음 날에는 0이고, KRX 연휴 뒤에는 그동안의 미국 장이 모두 더해진다.
- 거래일 07:30부터 개장 전 사이에만 읽는다(수집기 재시작 포함). 개장 뒤에는 그날 국면을 다시 정하지 않는다. 다시 읽기도 개장 전에 끝나는 것만 한다. 예를 들어 08:45에 다시 시작하면 08:45와 08:55에만 읽는다. 읽는 시각(`KRX_MACRO_AT`)이 개장 시각 이후이면 그날은 읽지 않고 로그에 경고를 남긴다.
- 지표 목록은 `macro.py`의 `INDICATORS`에 있다. 지표를 더하려면 이 표와 함께 고친다. 데모 엔진의 가상 값(`demo.py`의 `_OVERNIGHT`)에도 넣어야 데모가 뜬다. 새 출처면 엔진 API 스키마(`schemas/engine-api-v1.json`의 `macro`)의 출처 목록에도 넣는다.

**일일 국면.** 지표를 읽을 때마다 정한다(`regime.py`). 위에서부터 처음 맞는 규칙이 국면이다.

1. `shock`(충격): SOX가 ±3% 이상, VIX가 30 이상, 또는 원/달러가 ±1% 이상 움직였다.
2. `risk_off`(위험회피): SOX가 1% 이상 떨어졌거나, 원화가 0.5% 이상 약해졌다(원/달러 +0.5% 이상).
3. `risk_on`(위험선호): SOX가 1% 이상 올랐고, 원화가 강해졌다(원/달러 하락).
4. `neutral`(중립): 어느 규칙에도 해당하지 않거나, 지표가 하나도 없다. 지표가 하나도 없던 날(이유 `지표 없음`)은 기록은 `neutral`로 남지만, 엔진과 학습과 재생은 국면이 없는 날로 읽는다(`no_regime`, Markov는 기본 전이행렬). 지난 기록도 같다.

   > **바뀜** (2026-10-13, #120): 지표가 하나도 없던 날도 `neutral`로 학습하고 예측했다 → 국면 없는 날로 읽는다. 이유: 매크로 수집이 모두 실패한 날이 진짜 중립 국면으로 학습되고 예측되었다(#78, #84). 일부 지표만 빠진 날은 그대로다.

- SOX는 위의 등락률, VIX는 마지막 종가다. 원/달러는 달러선물 최근월물 종가(전 거래일 장 마감)의 등락률을 먼저 쓴다. 없으면 ECOS 매매기준율(전 거래일 거래로 정해져 하루 더 오래됐다)의 등락률을 쓴다.
- 없는 지표는 어떤 규칙도 만족시키지 않는다.
- 같은 입력이면 늘 같은 국면과 이유가 나온다. 문턱값은 `KRX_REGIME_*` 설정으로 바꾼다.

**경제 캘린더 (#150).** 수집기가 15분마다(`KRX_CALENDAR_EVERY`, 분 단위, 5분 이상, `off`로 끈다) TradingView의 공개 경제 캘린더(`https://economic-calendar.tradingview.com/events`)를 읽는다(`econ_calendar.py`). 미국·한국·중국·일본·유로존·독일·영국(`KRX_CALENDAR_COUNTRIES`)의, 어제 0시(KST)부터 7일 뒤까지의 발표 일정이다. 지표 이름, 국가, 발표 시각, 기간, 실제·예상·이전 값, 단위, 중요도(`low`, `medium`, `high`), 출처가 있다.

### 4.7 저장

- 원본 체결·호가: 하루 단위 Parquet 파일로 저장하고, 장 마감 후 S3에 올린다. 영구 보관한다.
  - 거래일마다 장 마감 15분 뒤와 매일 21:00(NXT·애프터마켓 종료와 20:30 백필 뒤, 밤 학습 전)에 올린다. 파티션마다 파일 하나로 합치고, 다시 올려도 결과가 같다(#6).
  - 서버의 `.env`에는 이 버킷만 읽고 쓰는(삭제 불가) IAM 사용자 키를 둔다. 덮어쓰기는 막을 수 없어서 버킷 버전 관리를 켜고 이전 버전을 30일 보관한다.
- 예측, 채점, 알고리즘 상태, 합의 가중치: 상시 서버의 SQLite(`state/engine.sqlite3`)에 저장한다. 저장 구조는 [engine-api.md](engine-api.md#저장-stateenginesqlite3)에 있다(#9). 방향 말고 다른 종류의 예측과 정답은 따로 둔 표 둘(`kind_predictions`, `kind_answers`)에 저장한다(5장 "예측 종류", #179). 특수 상황 구간도 따로 둔 표 둘(`special_windows`, `special_days`)에 저장한다(5장 "특수 상황", #236).
- 피처와 통계는 저장하지 않는다. 피처는 봉 마감마다 메모리에서 계산하고, 통계는 API를 읽을 때 저장된 예측으로 계산한다.
- 알고리즘, 모델 버전, 실행 기록은 스펙 #1의 SQLite 표 셋 대신 다음처럼 나눠 둔다.
  - **알고리즘:** 이름, 성격 카드, 선언 피처, 피처와 파라미터의 뜻은 코드(`algorithms/`, `features.py`, `/v1/algorithms`)에 있다. 기준 예측과 합의의 카드도 코드(`baselines.py`, `consensus.py`)에 있다(#164). 지금 상태와 상태 이력은 SQLite `statuses`에 있다.
  - **모델 버전:** 서버의 `state/models/`(지금 모델, `versions/`, `history.json`)에 있다. Object Store에는 모델 파일(`models/<알고리즘>/<버전>.json`), 지금 도는 모델(`live.json`), 밤 학습의 검증 리포트(`reports/`)와 승격 목록(`promotions/`)이 있다.
  - **실행 기록:** SQLite `runs`에는 CPU 예산 건너뜀, 일일 점검, 은퇴 후보 알림, 국면 없음, 예산 알림만 남는다. 밤 학습 실행은 Object Store의 `reports/`, `promotions/`, Spot 로그(`training/logs/`)에, 재생과 사전 검증 실행은 따로 만드는 재생 DB에 있다.
  - 위치와 필드는 [operations.md](operations.md#8-저장-위치)에 있다.
- 결측 구간: 지금은 `gaps` 계층의 Parquet로 기록한다(#4). SQLite의 `data_gaps`로 옮기는 일은 아직 하지 않았다.
- 백업: Lightsail 스냅샷을 매일 뜬다.
- 로컬 파일과 Object Store 키의 전체 목록은 [operations.md](operations.md#8-저장-위치)에 있다.

## 5. 예측 정의

- **시간.** KRX 연속매매 09:00–15:20. 시가·종가 동시호가는 제외한다. 예측 시각은 09:01부터, 채점 시각(t + 4분)이 연속매매 안에 드는 15:16까지다(#9).
- **주기.** 1분봉이 마감될 때마다 모든 알고리즘이 모든 종목을 예측한다.
- **기준 가격.** 봉 마감 t의 통합 중간가다. KRX와 NXT를 합친 최우선 매수호가와 최우선 매도호가의 평균이다. NXT가 열리기 전인 09:00:00–09:00:30에는 KRX 호가만 쓴다.
- **대상(정답, 도달 기준, #160, #170).** 4분 안에 그 가격에 시장가로 실제로 거래할 수 있었는가다. 정답은 (종목, 봉 마감)마다 하나이고, 그 봉 마감의 모든 예측자(알고리즘, 기준 예측, 합의)가 같은 정답으로 채점된다. 늦게 표시된 예측도 같다.
  - t의 통합 중간가 ± k틱을 위·아래 목표로 둔다. t부터 4분 안에(받은 시각 기준) 통합 최우선 매수호가가 위 목표 이상이 된 적이 있으면 상승, 아니고 최우선 매도호가가 아래 목표 이하가 된 적이 있으면 하락, 둘 다 아니면 보합이다. 위아래 둘 다 닿으면 상승이다. 뒤집힌 호가는 버리고, 붙은 호가는 센다.

  > **바뀜** (2026-10-14, #193): 대상은 "예측 시점 t의 중간가 대비 t+4분 중간가의 변화"였고, 정답 가격은 통합 중간가, "|변화| < k틱이면 보합"(k틱 이상 오르면 상승, 내리면 하락)이었다(정답 버전 1) → 도달 정답(정답 버전 2). 판정·합의 가중치·통계·화면의 ✓/✗가 모두 이것 하나로 채점한다. 이유: 4분 동안 그 가격에 시장가로 실제로 거래할 수 있었는지가 사용자가 알고 싶은 것이다(2026-10-14 인터뷰와 리뷰, #160). 옛 정답은 4분 사이에 목표까지 갔다가 돌아온 창을 보합으로 쳤고, 녹화일(10-12·13)에 보합이 약 60%였다(도달 정답은 약 50%). 옛 정답의 값(`outcomes`의 기준 A·B)은 DB에 계속 쓰인다. 옛 엔진으로 되돌려도 그대로 돌게 하려고다.
- **출력.** P(상승), P(보합), P(하락), 기대수익(틱). 기대수익은 지금처럼 4분 뒤 중간가 변화의 기대값이다.
- **보합 범위 k.** k는 왕복 거래비용 이상이 되도록 현재가와 호가단위표로 자동 계산한다. 도달 정답의 목표까지의 거리다.
- **도달 정답의 세부(#160, #167).**

  > **바뀜** (2026-10-14, #193): 이 항목은 "도달 정답 기록(#160, #167). 위 정답(4분 뒤 중간가 변화)과 함께 봉 마감마다 새 정답을 기록한다. 아직 판정·합의·화면의 ✓/✗는 위 정답으로 한다. 전환은 #170에서 한다"였다 → 도달 정답이 곧 정답이다(위 "대상"). 이유: #160의 마지막 단계(전환)다.

- **시간 예산.**
  - 알고리즘 하나는 한 번 예측하는 데 최대 10초까지 쓸 수 있다(`KRX_ALGORITHM_SECONDS`).

  - 알고리즘 하나의 한도는 전체 예산보다 작아야 한다(설정 검사). 그래서 한도를 다 쓰는 알고리즘이 하나 있어도 나머지 알고리즘에 예산이 남는다(기본값이면 20초).
  - 시간 초과나 CPU 예산으로 예측이 빠진 날은, 장 마감 뒤 일일 점검 때 알고리즘별 횟수를 텔레그램으로 한 번 알린다. 알고리즘을 가볍게 하거나 서버를 늘리라는 뜻이다.

  > **바뀜** (2026-10-09, #37): "순위가 낮은 알고리즘부터 건너뛰고, 잦으면 서버를 늘리라고 경고한다" → 순위와 상관없이 늦게 등록된 것부터 건너뛰고, 텔레그램 경고는 없다. 이유 기록 없음(PR #37 본문은 텔레그램 경고를 넣지 않았다고만 적었다).

  > **바뀜** (2026-10-12, #73): 알고리즘 하나의 한도 30초 → 10초. 전체 예산(30초)과 같으면 안 된다는 설정 검사를 더했다. 경고는 로그에만 → 예산 때문에 예측이 빠진 날 하루 한 번 텔레그램(#37에서 빠진 경고를 되살렸다). 이유: 한도와 전체 예산이 같아서, 한 알고리즘이 한도를 다 쓰면 뒤에 등록된 알고리즘이 모두 건너뛰어졌다(#71). 봉 마감은 1분마다이고 최종 합의는 한도까지 기다리므로, 늦어도 +30초는 표시 시점 기준(B) 성적에 불리하다.
- **합의.**
  - 빠른 합의: 알고리즘 계산을 시작하고(봉 마감 직후) 2초 안에 끝난 정식 알고리즘만 쓴다.
  - 최종 합의: 정식 알고리즘이 모두 끝나거나, 실패하거나, 각자의 시간 예산(10초)에 걸리면 낸다. 그래서 늦어도 계산 시작 +10초쯤이다.

    > **바뀜** (2026-10-12, #73): 늦어도 +30초쯤 → +10초쯤. 이유: 알고리즘 하나의 한도가 10초로 줄었다(위).
  - 가중치 규칙과 저장 방식은 [engine-api.md](engine-api.md#예측)에 있다(#18).

  > **바뀜** (2026-10-10, #42): 빠른 합의 "봉 마감 +2초" → "계산 시작부터 2초". 이유: 엔진이 이미 2초 늦게 돌면 빠른 합의가 늘 비기 때문이다. 가중치 규칙의 바뀐 점은 [engine-api.md](engine-api.md#예측)의 합의 메모에 있다.
- **특수 상황.**
  - VI 단일가매매 중에는 예측하지 않는다.
  - 4분 구간 안에 VI, 서킷브레이커, 사이드카가 끼면 그 예측은 "특수"로 따로 채점한다. 기본 통계에서는 뺀다.
  - VI는 KIS VI 현황을 REST로 조회해 안다. 서킷브레이커와 사이드카는 녹화한 지수와 선물로 거래소 규칙대로 판정한다. 판정 규칙은 [engine-api.md](engine-api.md#채점)에 있다(#12).
  - 엔진은 알게 된 구간(서킷브레이커는 단계, VI는 종류와 함께)을 SQLite `special_windows`에 남기고, 그 전의 지난날은 시작할 때 녹화로 채운다. 화면은 기간의 구간을 `GET /v1/symbols/{symbol}/special`로 읽어 차트에 칠한다(#236).

### 예측 종류 (#179)

엔진은 방향(상승·보합·하락, 위의 도달 정답) 말고 다른 종류의 예측도 같은 봉 마감에 같은 시장 보기로 낸다. 변동폭(#177, #180)과 장벽(#178, #183)을 위한 축이다. #179가 축을 넣었고, #180이 첫 종류인 변동폭(아래 "변동폭")을, #183이 둘째 종류인 장벽(아래 "장벽")을 등록했다. 등록된 종류는 방향, 변동폭, 장벽이다(`kind_registry.py`의 `KINDS`). 테스트에는 시험용 종류도 있다. 규칙의 세부와 API는 [engine-api.md](engine-api.md#예측-종류-179)에 있다.

> **바뀜** (2026-10-15, #197): "#179는 축만 넣었다. 그래서 지금 등록된 종류는 방향 하나이고(`kinds.py`의 `KINDS`), 다른 종류는 테스트의 시험용 종류로만 돈다" → 방향과 변동폭이 등록되어 있고, 목록은 `kind_registry.py`에 있다. 이유: 변동폭이 첫 종류다(#177). 변동폭 모듈(`ranges.py`)이 `kinds.py`의 틀 위에 서므로, 목록을 따로 두어야 두 모듈이 서로를 읽지 않는다.

> **바뀜** (2026-10-15, #208): "등록된 종류는 방향과 변동폭이다" → 방향, 변동폭, 장벽. 이유: 장벽이 둘째 종류다(#178).

- **종류 등록.** 종류마다 한곳(`kinds.Kind`)에 선언한다.
  - 이름, 세 클래스의 이름과 순서(첫째·가운데·셋째), 화면용 한국어 이름.
  - 행동 클래스: 정밀도·커버리지를 셀 클래스. 방향은 상승·하락이고, 변동폭은 양 끝(작음·큼)이다.
  - 정답 함수와 정답 버전. 1분봉만 있는 날의 정답 규칙(학습용. 없으면 그런 날은 그 종류를 학습하지 않는다).
  - 장벽이 있는 종류(장벽, #183)는 장벽 폭 규칙. 엔진이 봉 마감에 그날과 전 거래일의 1분봉으로 폭을 한 번 정하고, 정답 함수와 1분봉 규칙이 그 폭을 받는다.
  - 기준 예측, 세 확률 말고 내는 출력 필드(뜻과 단위)와 그 검사, 추가 통계.
  - 이름과 클래스 이름은 소문자 영어다(URL과 출력의 `p_<클래스>` 키에 들어간다). 기준 예측의 이름은 모든 종류와 방향의 예측자 이름과 겹치지 않는다.
- **방향은 그대로 돈다.** 방향도 첫 종류로 등록되지만, 예측·정답·기준 예측·합의·신호는 지금 표와 코드 그대로다(`predictions`, `outcomes`, `touches`, `baselines.py`, `consensus.py`). 다른 종류가 있어도 방향 예측의 저장, 채점, 순위표는 없을 때와 같다(재생 테스트가 확인한다).
- **출력.** 핵심은 세 클래스의 확률이다(합 1). 예측 클래스는 가장 큰 확률이고, 동률이면 가운데 클래스, 그다음 첫 클래스다(방향의 보합, 상승과 같은 규칙이다). 저장과 API의 출력은 `p_<첫 클래스>`, `p_<가운데>`, `p_<셋째>`와 종류의 추가 필드다. 분포가 아니거나, 선언한 추가 필드와 다르거나, 값이 유한하지 않거나, 종류의 검사를 어기면 그 알고리즘의 그 회차는 `error`다(지금 규칙과 같다).
- **알고리즘.** 알고리즘 규약에 `kind`가 생겼다. 없으면 방향이라 지금 알고리즘은 바뀌지 않는다. 알고리즘은 한 종류에만 속한다. 다른 종류의 알고리즘은 `algorithms.KIND_ALGORITHMS`에 등록한다(지금은 변동폭의 `mandelbrot`, #181과 장벽의 `breiman`, #184). 엔진은 그것들을 방향 알고리즘과 같은 작업 스레드, 같은 시간 한도(`KRX_ALGORITHM_SECONDS`), 같은 CPU 예산으로 돌린다. 방향 알고리즘 뒤에 등록되므로 예산이 모자라면 먼저 건너뛴다. 이름은 모든 알고리즘과 기준 예측 사이에서 하나뿐이어야 한다(상태, 모델 파일, 사전 검증 리포트가 이름으로 묶인다). 등록 검사(고유 피처, 같은 피처 조합)는 같은 종류 안에서만 본다.

  > **바뀜** (2026-10-15, #198): "다른 종류의 알고리즘은 `algorithms.KIND_ALGORITHMS`에 등록한다(지금은 없다)" → 변동폭의 `mandelbrot`이 등록되어 있다. 이유: 변동폭의 첫 모델이다(#177).

  > **바뀜** (2026-10-15, #209): "(지금은 변동폭의 `mandelbrot`, #181)" → 장벽의 `breiman`도 등록되어 있다. 이유: 장벽의 첫 모델이다(#178).
- **기준 예측.** 봉 마감마다 종류의 기준 예측이 모든 종목을 한 번에 낸다. 알고리즘들이 계산을 시작한 뒤에 내서 방향 알고리즘을 늦추지 않는다. 기준 예측이 아는 것은 봉 마감 중간가, 호가단위, 보합 폭 k, 방금 끝난 창(t − 4분 → t)의 그 종류 정답(채점할 수 없었으면 없음), 그날 끝난 창들의 클래스별 정답 수다. 낼 수 없는 봉 마감은 `no_previous`다. 표에서 내는 기준 예측(변동폭의 `range-climate`, `kinds.TableBaseline`, #180)은 방향의 시간대 기후처럼 밤 학습이 그 종류의 정답으로 다시 맞춘 표를 08:00 교체가 설치하고, 엔진은 그 표로 낸다. 그 예측의 모델 버전은 표의 버전이다.
- **정답.** (종류, 종목, 봉 마감, 정답 버전)마다 하나다. 그 봉 마감의 그 종류 예측자가 모두 같은 정답으로 채점된다(#160 선례). 시장 보기가 도달 정답과 같은 호가를 같은 규칙으로 따라간다(`kinds.QuoteLog`, #167의 창 추적을 일반화했다).
  - 받은 시각 기준 t 이상 t + 4분 미만에 받은 WebSocket 통합 1호가(통합 호가 `H0UNASP0`와 통합 체결 `H0UNCNT0`에 실린 1호가)와 통합 체결.
  - 뒤집히거나 한쪽만 있는 호가는 버리고, 붙은 호가는 쓴다.
  - 봉 마감 중간가가 없거나, REST 대체 호가를 받았거나, WebSocket 호가가 60초 넘게 끊겼거나, 엔진이 그 창을 따라가는 중에 다시 시작했으면 채점할 수 없다. 이유의 이름도 도달 정답과 같다.
  - 종류의 정답 함수는 그 창(봉 마감 중간가, 호가단위, k, 봉 마감 직전 1호가, 받은 호가와 체결)으로 클래스와 경로 요약을 낸다. 공통 규칙이 채점할 수 없다고 한 창은 정답 함수가 무엇을 내든 클래스가 없다.
  - t + 4분에 한 번 쓴다. 예측하지 않은 봉 마감(VI 등)의 창에도 쓴다. 정답 함수가 실패한 종류는 로그만 남긴다. 방향과 다른 종류는 그대로 간다.
- **특수 상황.** 그 봉 마감에 알던 VI·서킷브레이커·사이드카, 또는 그 뒤에 알게 된 것(어느 판이든)이 4분에 닿으면 그 정답이 특수다. 방향 예측의 특수 표시, 학습에서 빼는 봉 마감과 같다. VI 중인 종목은 그 종류의 예측자도 모두 `vi`인 빈 예측이다.
- **저장.** 방향의 표는 그대로 두고, 다른 종류는 새 표 둘(`kind_predictions`, `kind_answers`)에 둔다. DB 버전(`user_version`)은 올리지 않는다(`blocks`, `touches` 선례: 옛 엔진으로 되돌려도 DB가 열린다). 예측마다 그 봉 마감의 k(봉 마감 중간가의 보합 폭, 예측자가 받은 값)를 함께 두고 API와 스트림으로 준다(`flat_ticks`, #200). 모델의 출력이 아니라 `kind_predictions`의 열이다. 그 열도 DB 버전을 올리지 않고 더한다(옛 DB에는 엔진이 열 때 더하고, 옛 엔진은 그 열을 비워 둔 채 쓴다). 장벽이 있는 종류는 그 봉 마감의 장벽 폭 w도 같은 방식의 열(`width_ticks`, #183)에 둔다. 장벽이 없는 종류는 비어 있다. 봉 마감 통합 중간가와 그 호가단위도 같은 방식의 열(`anchor`, `tick`, #210)에 둔다. 그 종류 정답의 기준 가격(경로의 `anchor`, `tick`)과 같은 값이라, 장벽은 정답 전에도 U·L을 안다.
- **통계.** 3클래스 통계(맞힘률, Brier, 보정 곡선, lift, 거래일 단위 lift, 운 보정)는 방향과 같은 코드로 낸다(`stats.py`의 lift·FDR, `kind_stats.py`). 정밀도와 커버리지는 그 종류의 행동 클래스로 센다. lift는 그 종류의 기준 예측 대비다. 닿음 손익은 방향의 것이라 없다. 종류의 추가 통계는 항목마다 `extra`로 붙는다. 추가 통계는 그 예측자의 채점된 예측과 함께 그 종류 기준 예측들의 것도 받는다(#180: 변동폭의 `range-climate` 대비 pinball loss 차이). 장벽의 추가 통계는 장벽 손익이다(#183). 순위표와 판정은 그 종류의 정답(정답 버전)으로 학습한 모델의 예측만 센다. 기본값 모델의 예측은 세지 않는다(방향의 #170 규칙과 같다).
- **상태.** 수습·정식·벤치·은퇴·복제를 종류마다 그 종류의 기준 예측으로 판정한다. 판정일과 신뢰수준은 7.5와 같다. 복제는 같은 종류의 먼저 등록된 알고리즘과만, 첫 클래스 확률 − 셋째 클래스 확률의 상관으로 본다. 다른 종류에는 합의(Condorcet), 신호 알림, 텔레그램 신호가 없다. 그래서 정식 상태는 화면 표시와 판정 기록에만 쓰인다.
- **학습.** 다른 종류의 알고리즘도 같은 경로를 탄다: `krx-quant fit`, 밤 학습(champion/challenger를 그 종류 세 클래스의 log loss로), 08:00 교체, `rollback`, 사전 검증. 녹화된 날은 엔진과 같은 시장 보기 창과 정답 함수로, 1분봉만 있는 날은 종류의 1분봉 규칙으로 정답을 만든다. 표본에서 빼는 봉 마감(VI, 특수)은 방향과 같다. 모델의 정답 버전(`target_version`)은 그 종류의 정답 버전이다.
- **API.** `GET /v1/kinds`(종류 목록), `/v1/algorithms`의 `kind`, `GET /v1/leaderboard?kind=`(기본은 방향이고 지금 응답과 같다), 알고리즘의 `/stats`(그 알고리즘의 종류로), `GET /v1/symbols/{종목}/kinds/{종류}/latest`와 `…/predictions`, 스트림 이벤트 `kind_prediction`·`kind_answer`. 옛 화면은 모르는 스트림 이벤트를 무시하므로 새 이벤트는 모든 연결에 보낸다. 화면은 #182에서 종류를 고른다(10장).

### 변동폭 (#177, #180)

첫 다른 종류다(`ranges.py`, 이름 `range`). 봉 마감 t부터 4분 동안 통합 중간가가 얼마나 움직일지(최고 − 최저, 틱)를 비용 기준 세 구간의 확률과 분위수로 낸다. 범위 기반 변동성(Parkinson 1980, CARR)을 중간가로 잰 것이다. 체결가는 매수·매도 호가를 오가며 범위를 부풀린다(bid-ask bounce). 움직임이 비용을 넘을 만큼 클지, 손절·익절을 몇 틱에 둘지 보려는 것이다. 기준 예측 둘과 첫 모델 `mandelbrot`(#181, 아래 "첫 모델")이 예측한다. `mandelbrot`은 사전 검증을 통과해야 돈다. 화면은 #182다(10장의 "예측 종류"). 정의의 세부와 API는 [engine-api.md](engine-api.md#변동폭-177-180)에 있다.

> **바뀜** (2026-10-15, #198): "지금은 기준 예측 둘만 예측한다. 첫 모델 `mandelbrot`은 #181" → 첫 모델 `mandelbrot`이 등록되어 있다(사전 검증 뒤 수습). 이유: #181이 넣었다.

- **정답(정답 버전 1).** 기준 가격은 t의 통합 중간가(기준가 규칙)다. 받은 시각 기준 t 이상 t + 4분 미만에 받은 유효한 통합 1호가(도달 정답과 같은 호가, 위 "예측 종류"의 "정답")의 중간가와 기준 가격 중 최고 − 최저를 기준 가격의 호가단위로 나눈 것이 변동폭 r이다(반 틱 단위). k는 기준 가격의 보합 폭이다. 작음 r < k, 보통 k ≤ r < 2k, 큼 r ≥ 2k다. 작음은 중간가로 봐도 4분 안에 어떤 왕복 매매로도 비용을 넘을 수 없었다는 뜻이다. 채점할 수 없는 경우와 특수 상황은 도달 정답과 같다.
- **경로.** r, k, 호가단위, 기준 중간가, 최고·최저 중간가와 그것을 처음 받은 시각, 위로 간 폭(최고 − 기준)과 아래로 간 폭(기준 − 최저), 받은 호가 수, 60초 끊김 여부, 진단용 최고 매수·최저 매도호가.
- **출력.** 작음·보통·큼의 확률(`p_small`, `p_medium`, `p_large`, 합 1)과 r의 분위수 `q10`, `q50`, `q90`(틱, 0 ≤ q10 ≤ q50 ≤ q90)이다. 어기면 `error`다.
- **기준 예측.** `range-climate`: 종목 × 30분 시간대마다 최근 20거래일 변동폭 정답의 구간 비율을 확률로, r의 10·50·90% 분위수를 분위수로 낸다. 밤 학습이 매일 다시 맞추고 08:00 교체가 설치한다. 변동성의 장중 계절성만 맞혀서 이기는 모델을 거른다. `range-persist`: 직전 창(t − 4분 → t)의 r을 같은 규칙으로 구해, 지금 k로 나눈 구간을 확률 1로, q10 = q50 = q90 = r로 낸다. 그 창을 채점할 수 없으면 예측하지 않는다(`no_previous`). 변동폭의 가장 약한 lift는 이 둘 대비 lift 중 작은 것이다.
- **통계.** 3클래스 통계는 위 "예측 종류"대로이고, 정밀도·커버리지는 행동 클래스 작음·큼으로 센다. 추가 통계(`extra`)는 분위수마다 pinball loss(평균과 정규근사 95% 구간, 거래일 단위), q10~q90 구간 적중률(이상적으로 80%, Wilson 95%), q50의 평균 절대 오차(틱), `range-climate` 대비 pinball loss 차이(짝 단위, 거래일 단위)다. 마지막은 설명용이고 판정에는 쓰지 않는다. 판정은 3클래스 lift로 한다.
- **학습 정답.** 녹화된 날은 정답 모듈로 호가에서 정확히 만든다(실시간·재생 채점과 같다). 1분봉만 있는 날은 r ≈ max(0, (t의 종가와 t부터 1분봉 4개의 최고 고가 − 최저 저가) ÷ 호가단위 − c)로, 기준 가격과 k는 t의 종가로 정한다. c는 체결가의 호가 튐 보정이다. c는 1이다(`ranges.BAR_C`): 1분봉 범위가 중간가 범위보다 약 1틱 크다는 #177의 실측(005930 1분봉 중앙 3틱, 녹화일 중간가 중앙 1–2틱)으로 골랐고, 녹화일의 호가 정답과 견줘 확정했다(#203). `krx-quant diagnose` 7절(2026-10-12 – 10-16의 5거래일)에서 정답 구간과 같은 비율이 c = 1 85.5%, c = 0 59.2%(5,481창)였고, 종목마다 c = 1이 더 많이 같았다(000660 84.2%, 005930 86.6%, 009150 85.6%). 세부는 [engine-api.md](engine-api.md#변동폭-177-180)에 있다. 녹화일에서는 방향처럼 VI 중인 봉 마감과 4분이 특수 상황에 닿는 봉 마감을 표본에서 뺀다. 밤 학습 리포트와 텔레그램 요약에 정답 출처별(녹화 호가, 1분봉) 표본 수가 남는다.

- **지난 정답.** 위 "예측 종류"의 "지난 정답"대로 2026-10-12부터 채운다. 녹화일마다 정답이 약 1,100개(376 봉 마감 × 3종목)다.
- **첫 모델 `mandelbrot`(#181, `algorithms/mandelbrot/`).** HAR 방식(Corsi 2009) 로그 범위 회귀다. 이름은 변동성 군집("큰 움직임 뒤에 큰 움직임")을 처음 짚은 Mandelbrot(1963)에서 왔다. 세부와 손계산 예는 [engine-api.md](engine-api.md#mandelbrot-변동폭-181)에 있다.
  - 고유 피처: `range_4`, `range_20`, `range_60`(봉 마감 전 4·20·60분 1분봉의 (고가 − 저가) 평균, 틱. 체결이 없는 분은 0, 개장 뒤 그만큼 안 됐으면 개장부터)과 `range_prev_day`(전 거래일 같은 30분 시간대의 평균, 틱). 1분봉으로 만들어 녹화일과 백필 날에 모두 있다. 전 거래일은 녹화일이어도 그날의 백필 1분봉에서 읽는다. 방향 알고리즘은 이 넷을 읽지 않는다(Turing도 뺀다). 방향 예측은 그대로다.
  - 회귀: log(1 + r)를 위 넷과 `relative_volume`, `spread_ticks`(녹화일만)로 최소제곱 회귀한다. 입력은 모두 log(1 + x)에서 학습 평균을 뺀 값이고, 모르는 입력은 평균(0)으로 채운다. 개장부터 센 30분 시간대(`minutes_since_open`, 13칸)마다 절편을 둔다.
  - 스프레드가 없을 때의 모델: 스프레드를 넣은 회귀(`book`, 스프레드를 아는 봉 마감 = 녹화일)와 뺀 회귀(`bars`, 모든 봉 마감)를 함께 학습한다. 봉 마감에 스프레드를 알면 `book`, 모르면 `bars`로 낸다.
  - 예측: 회귀값 + 그 회귀의 학습 잔차 경험 분포(분위수 101개로 남긴다)가 log(1 + r)의 예측 분포다. 분위수 q10·q50·q90은 그 분포의 10·50·90% 값을 exp(·) − 1로 틱으로 돌린 것(0 아래는 0), 작음은 log(1 + k) 아래, 큼은 log(1 + 2k) 이상의 몫이다. 같은 분포에서 나오므로 구간 확률과 분위수가 서로 맞는다.
  - 학습 구간 20거래일. 기본 모델은 1/3씩과 분위수 0·k·2k다. 봉 마감에 k를 모르면(기준가 없음) 예측하지 않는다(`no_book`).

### 장벽 (#178, #183)

둘째 다른 종류다(`barriers.py`, 이름 `barrier`). 봉 마감 t마다 종목별로, t의 통합 중간가 ± 폭 w에 둔 위·아래 장벽 중 4분 안에 어느 쪽에 먼저 닿을지를 위 먼저·시간 만료·아래 먼저의 확률로 낸다. López de Prado의 삼중 장벽(*Advances in Financial Machine Learning* 3장)이다: 가로 장벽은 변동성의 1배(대칭), 비용 k보다 좁지 않고, 시간 장벽은 4분이다. 스캘핑 매매 하나("들어가서 익절선이나 손절선에 먼저 닿거나 시간이 다 되면 나온다")와 바로 이어진다. 방향 예측은 순서를 보지 않고 폭이 늘 k라서 이것과 다르다. 기준 예측 둘과 첫 모델 `breiman`(#184, LightGBM 3분류, 아래 "첫 모델")이 예측한다. `breiman`은 사전 검증을 통과해야 돈다. 화면은 #185다. 정의의 세부와 API는 [engine-api.md](engine-api.md#장벽-178-183)에 있다.

> **바뀜** (2026-10-15, #209): "지금은 기준 예측 둘만 예측한다. 첫 모델 `breiman`(LightGBM 3분류)은 #184" → 첫 모델 `breiman`이 등록되어 있다(사전 검증 뒤 수습). 이유: #184가 넣었다.

- **폭 w.** t 전에 끝난 1분봉 종가의 1분 변화(틱, 기준 가격의 호가단위)의 지수가중 표준편차(span 100, López de Prado의 기본값) σ̂₁을 구한다. 변화는 전 거래일 연속매매 봉의 것 다음에 그날 개장부터의 것을 잇는다(밤사이는 변화가 아니다). 그래서 개장 직후에는 전 거래일 끝의 봉들이 정하고, 그날 봉이 쌓일수록 그날 것이 정한다. 4분 변동성 σ̂₄ = σ̂₁ × √4, w = max(k, σ̂₄를 반올림한 틱). 두 날 합쳐 봉이 20개 미만이면 w = k다. U = 기준 중간가 + w틱, L = 기준 중간가 − w틱(기준이 반 틱이면 장벽도 반 틱).
- **폭은 엔진이 정한다.** 시장 보기가 봉 마감의 창을 열 때 그 봉 마감의 스냅숏과 같은 봉으로 한 번 정한다. 그 봉 마감의 모든 장벽 예측, 정답, 피처(`barrier_width` = w, `barrier_sigma` = w ÷ σ̂₄)가 같은 w다. 알고리즘은 w를 바꾸지 않는다. 1분봉은 녹화일과 백필 날 모두 체결로 만들고, 전 거래일 봉은 늘 그날의 백필 1분봉이라 두 날의 폭이 같은 방식으로 정해진다. 방향 알고리즘은 이 두 피처를 읽지 않는다(Turing도 뺀다).
- **폭의 자리.** 예측 항목의 `width_ticks`(`kind_predictions`의 열)다. #178은 `output.width_ticks`로 적었지만, #200이 엔진이 붙이는 봉 마감의 값(k)을 `output` 밖의 열로 둔 뒤라 같은 이유로 그쪽을 따랐다. 출력 계약은 세 확률뿐이고, 예측하지 않은 항목(`no_previous`, `vi`)에도 그 봉 마감의 w가 있다. 봉 마감 중간가와 호가단위도 예측 항목의 `anchor`, `tick`(#210)이라 정답 전에도 U = anchor + w × tick, L = anchor − w × tick이다.
- **정답(정답 버전 1).** 받은 시각 기준 t 이상 t + 4분 미만에 받은 유효한 통합 1호가(도달 정답과 같은 호가) 중 매수 1호가 ≥ U를 처음 받은 시각과 매도 1호가 ≤ L을 처음 받은 시각 중 먼저인 쪽이 위 먼저·아래 먼저다. 둘 다 없으면 시간 만료다. 둘이 같은 받은 시각이면 순서를 몰라 채점할 수 없다(`ambiguous`). 체결가만 장벽을 넘은 것은 닿음이 아니다(#160과 같은 이유). 그 밖의 채점 불가와 특수 상황은 도달 정답과 같다.
- **경로.** w, σ̂₄, k, 호가단위, 기준 중간가, U, L, 왕복 비용(틱), t의 매수·매도 1호가, 위·아래 처음 닿은 시각과 그때의 매수·매도 1호가, t + 4분 직전의 매수·매도 1호가, 받은 호가 수, 끊김 여부. 장벽 손익과 진단을 이것으로 계산한다.
- **출력.** `p_up_first`, `p_timeout`, `p_down_first`(합 1). 행동 클래스는 위 먼저·아래 먼저, 가운데 클래스는 시간 만료다.
- **기준 예측.** `barrier-climate`: 종목 × 30분 시간대마다 최근 20거래일 장벽 정답의 세 클래스 비율을 낸다. 밤 학습이 매일 다시 맞추고 08:00 교체가 설치한다. 시간대와 변동성만 맞혀서 이기는 모델을 거른다. `barrier-persist`: 직전 창(t − 4분에 정한 폭과 장벽으로 t − 4분 → t)의 정답을 시장 보기가 따라간 창에서 같은 규칙으로 구해 확률 1로 낸다. 그 창을 채점할 수 없으면 예측하지 않는다(`no_previous`). 장벽의 가장 약한 lift는 이 둘 대비 lift 중 작은 것이다.
- **통계.** 3클래스 통계는 위 "예측 종류"대로이고, 정밀도·커버리지는 위 먼저·아래 먼저로 센다. 추가 통계(`extra`)는 연구용 장벽 손익이다: 위 먼저 예측은 t의 매도 1호가에 사서 U(위가 먼저), 그 순간의 매수 1호가(아래가 먼저), t + 4분 직전의 매수 1호가(시간 만료)에 판다. 아래 먼저 예측(인버스 가정)은 t의 매수 1호가에 팔아 L, 그 순간의 매도 1호가, t + 4분 직전의 매도 1호가에 되산다. 시간 만료 예측은 거래하지 않는다. 왕복 비용(매도세 + 수수료 × 2)을 틱으로 바꿔 뺀다. 거래 수, 합계, 거래당 평균과 정규근사 95% 구간을 전체와 롱·숏별로 낸다. #160의 닿음 손익처럼 1호가에 전부 체결된다고 보는 값이다. 판정은 3클래스 lift로 한다.
- **학습 정답.** 녹화된 날은 정답 모듈로 호가에서 정확히 만든다(실시간·재생 채점과 같다). 1분봉만 있는 날은 #160의 1분봉 규칙(종가 위치와 1틱 여유)에 순서를 더한다: 기준 가격·k·w는 t의 종가와 그때까지의 1분봉(전 거래일 포함)으로 정하고, t 뒤 1분봉 4개 중 고가 ≥ 종가 + (w + 1 + [위치 = −1])틱인 첫 봉과 저가 ≤ 종가 − (w + 1 + [위치 = +1])틱인 첫 봉 중 먼저 닿은 분이 정답이다. 같은 분이면 순서를 알 수 없어 그 표본은 학습에서 뺀다(`same minute`). 녹화일에서 이 규칙과 호가 정답의 클래스 일치율은 95.2%(5,475창)이고, 같은 분 양쪽 닿음은 0.1%다(#203, `krx-quant diagnose` 8절, 2026-10-12 – 10-16의 5거래일). 종목별로 000660 94.2%, 005930 96.6%, 009150 94.7%다. #160의 도달 정답 1분봉 규칙(93%)보다 높아 규칙은 그대로다. 세부는 [engine-api.md](engine-api.md#장벽-178-183)에 있다. 녹화일에서는 방향처럼 VI 중인 봉 마감과 특수 상황 봉 마감을 표본에서 뺀다. 밤 학습 리포트와 텔레그램 요약에 정답 출처별(녹화 호가, 1분봉) 표본 수와 뺀 표본 수(이유별: `same minute`, `vi`, `special`, 채점할 수 없는 창, 정답 없음)가 남는다(#184).

## 6. 채점과 통계

방향 말고 다른 종류의 통계는 같은 3클래스 통계를 그 종류의 클래스, 행동 클래스, 기준 예측으로 낸다(5장 "예측 종류", #179). 변동폭은 분위수 통계도 낸다(5장 "변동폭", #180). 장벽은 연구용 장벽 손익을 낸다(5장 "장벽", #183). 아래는 방향의 것이다.

**채점 기준 하나(도달 정답, #170).** 모든 예측과 합의를 그 봉 마감의 도달 정답(5장) 하나로 채점한다. 순위표, 알고리즘 통계, 상태 판정, 합의 가중치, 사전 검증, 재생 요약, 진단, 화면의 ✓/✗가 모두 같다. 예측이 늦게 표시되어도 정답은 같다. 늦게 뜬 신호가 그 사이 이미 닿은 목표를 맞힌 것인지는 진단의 "표시 전에 이미 닿은 맞음"으로 본다.

> **삭제됨** (2026-10-14, #193): 채점 기준 두 가지. (A) 봉 마감 기준: t의 중간가에서 t+4분 중간가까지, 모델 실력을 본다. (B) 표시 시점 기준: 신호가 화면에 표시된 시각의 중간가에서 t+4분 중간가까지, 신호를 보고 움직일 수 있는 시점에서 출발한 성적(중간가로 재므로 스프레드와 체결은 들어가지 않는다), 화면 맨 위에는 (B). 수습 판정은 B, 합의 가중치는 A, 순위표와 차트는 고른 것을 썼다. 이유: 기준이 곳마다 달랐고, 둘 다 4분 뒤 한 점의 중간가라 그 사이에 그 가격에 거래할 수 있었는지를 보지 않았다(#160). 대신: 도달 정답 하나. 옛 A·B 값은 `outcomes`에 계속 쓰여 DB에 남는다.

  > **바뀜** (2026-10-13, #117): (B)를 "실제로 신호를 따라 매매했을 때의 성적"이라고 했다 → 표시 시점에서 출발한 중간가 성적. 이유: 스프레드와 체결이 빠져 있어 실제 매매 성적이 아니다(#78, #81).

**판정과 가중치는 새 정답 모델의 예측만(#170).** 모델은 자기를 학습한 정답 버전을 갖는다(정답 버전 2: 도달 정답). 수습·정식·벤치 판정과 합의 가중치는 도달 정답으로 학습한 모델이 낸 예측만 본다. 기본값(학습 전) 모델과 옛 정답 모델의 예측은 통계에는 나오지만 판정과 가중치에는 들어가지 않는다. 기준 예측은 모두 들어간다. 바꾸는 날의 수습은 7.5에 있다.

**헤드라인 지표.** 95% 신뢰구간을 함께 보여준다.
- 방향 정밀도: 상승·하락이라고 예측한 것 중 맞은 비율. 커버리지(방향을 예측한 비율)와 함께 본다.
- 기준 예측 대비 개선폭(lift). 기준 예측은 "항상 보합", "직전 4분 방향"(직전 창의 도달 정답), "비율대로 무작위"(그날 4분이 지난 창의 도달 정답 비율), "시간대 기후"(종목 × 30분 시간대의 학습 창 최빈 방향, `baseline-climate`) 네 가지다(정답 버전 2, #169). 시간대 기후는 시간대와 변동성만 맞혀서 이기는 모델을 거르려는 기준이다. 정답 버전 1에서는 앞의 셋이 옛 정답으로 낸다. lift는 같은 종목·봉 마감끼리 짝지은 3클래스 정답률 차이다. 순위는 lift 중 가장 작은 것의 신뢰구간 하한으로 정한다(#11). 상태 판정은 같은 lift를 거래일 단위로 본 하한으로 한다(#79). 정의는 [engine-api.md](engine-api.md#통계와-순위표)에 있다.
- 닿음 손익(틱, 연구용, #170): 정답과 같은 규칙의 손익이다. 상승 예측은 t의 매도 1호가에 사서, 위 목표에 닿으면 그 가격에, 아니면 t+4분 직전의 매수 1호가에 판다. 하락 예측은 인버스 상품을 가정해 반대로 한다(t의 매수 1호가에 팔고, 아래 목표에 닿으면 그 가격에, 아니면 4분 직전의 매도 1호가에 되산다). 보합은 거래하지 않는다(0). 왕복 비용(매도세 0.20% + 수수료 × 2, 기본 0.23%)을 틱으로 바꿔 뺀다. 1호가에 전부 체결된다고 본 값이라 따라 했을 때의 손익이 아니다. 핵심 지표는 맞힘률과 lift이고, 이 열은 "맞혔는데 손해"가 왜 생기는지 보이려는 것이다. 폭 k에서는 위 목표에 닿아 팔아도 k틱 − 스프레드의 절반만 벌어 비용에 못 미친다([engine-api.md](engine-api.md#통계와-순위표)).

  > **바뀜** (2026-10-14, #193): 중간가 손익(방향을 낸 모든 예측을 시작 중간가에서 목표 중간가까지 재고 매도세와 수수료를 뺌, 하락은 공매도, 스프레드와 체결 없음) → 닿음 손익. API 필드(`pnl`)의 이름은 그대로다. 이유: 폭 k에서는 맞혀도 손익이 0에 가까워, 정답과 같은 규칙으로 재야 맞힘과 손익의 차이가 보인다(#160, QUANT LETTER 거래비용 예시).

  > **바뀜** (2026-10-13, #117): "비용 반영 가상손익" → "중간가 손익(연구용)". 이유: 따라 했을 때의 손익으로 읽히기 쉬웠다(#78, #81).

**상세 지표.**
- 3클래스 정확도
- Brier 점수와 보정도
- 분해: 종목별, 30분 시간대별, 모델 버전별, 기간별(오늘/5일/20일)

**운 보정.** 알고리즘이 많으면 운으로 상위에 오르는 경우가 생긴다. 이를 막기 위해 다음을 적용한다.

**예측 방식과 실패 조건(#164).** 카드의 두 칸을 줄인 것이다. 카드 글 전체는 각 모듈(기준 예측은 `baselines.py`, 합의는 `consensus.py`)에 있고 `/v1/algorithms`로 화면에 간다([engine-api.md](engine-api.md#get-v1algorithms)). 도달 정답 기준이다(#170). 정규분포 방식은 공통 함수가 4분 변화의 정규분포를 4분 동안의 움직임(브라운 운동)으로 보고 닿을 확률로 바꾼다: 상승은 매수 1호가가 위 목표(+k틱)에 4분 안에 닿을 확률(반사 원리, 거리는 k틱 + 봉 마감 스프레드의 절반), 하락은 매도 1호가가 아래 목표에 닿을 확률 × 위에 닿지 않을 확률, 나머지가 보합이다(k: 보합 범위, 폭은 최소 0.5틱).

> **바뀜** (2026-10-14, #193): 카드 글과 아래 표가 "지금 정답(4분 뒤 중간가 변화) 기준. 정규분포 방식은 공통 함수가 4분 변화의 정규분포에서 +k틱 이상을 상승, −k틱 이하를 하락, 그 사이를 보합으로 낸다"였다 → 도달 정답 기준(위). 기준 예측 줄은 "한 클래스에 확률 1(늘 보합, 직전 4분 방향, 그날 비율대로 무작위)", 실패 조건 "늘 보합: 보합 범위를 넘는 움직임. 직전 방향: 되돌림과 잦은 반전. 무작위: 늘 운"이었다. 이유: 정답이 도달 정답으로 바뀌었다(#160). 정답 버전 1로 돌리면 카드 글은 맞지 않는다.

> **바뀜** (2026-10-14, #191): 정답 버전 2(`KRX_TARGET_VERSION=2`)에서만: 정규분포 방식의 공통 함수가 끝점 확률(4분 뒤 +k틱 이상) → 닿을 확률(반사 원리. 거리는 k틱 + 봉 마감 스프레드의 절반, p_up = P(위), p_down = P(아래)·(1 − p_up)). 다섯 알고리즘의 코드는 그대로다. 기준 예측은 직전 창의 도달 정답, 도달 정답 비율, 시간대 기후(`baseline-climate`) 넷이다. 아래 표의 글은 버전 1 기준이고, 카드와 함께 #170에서 고친다. 이유: 표류가 없으면 4분 안에 +k에 닿을 확률은 끝점 확률의 약 2배라서, 끝점 확률로는 새 정답에서 보합을 늘 높게 낸다(#160). 식은 [engine-api.md](engine-api.md#공통-정규분포-함수-normal_forecast-169)에 있다.

| 기준 예측 | 한 클래스에 확률 1(늘 보합, 직전 창의 도달 정답, 그날 도달 정답 비율대로 무작위, 시간대 기후) | 늘 보합: 4분 안에 목표에 닿는 움직임. 직전 방향: 닿은 뒤 되밀림과 잦은 반전. 무작위: 늘 운. 기후: 학습 창의 시간대 버릇과 다른 날 |

피처와 파라미터의 이름마다 뜻(설명, 단위, 언제 아는지)도 엔진이 준다(`feature_meanings`, `param_meanings`). 예: `velocity`는 틱/분, 봉 마감에 안다. Markov의 `iv_cut.0`은 %, 밤 학습이 정하고 녹화 5거래일 전에는 없다.

**Markov의 옵션 IV 국면(#53).** 규칙과 문턱값은 다음과 같다. 자세한 것은 [engine-api.md](engine-api.md#markov)에 있다.
- **ATM IV(`atm_iv`).** 봉 마감 전 10분 안에 받은 옵션 체결(`H0IOCNT0`, 등가격 ±2 행사가 콜·풋)에서 옵션마다 마지막 체결의 델타를 본다. 델타가 0.5에 가장 가까운 콜과 −0.5에 가장 가까운 풋의 내재변동성(%)을 평균한다(똑같이 가까운 옵션이 여럿이면 그 IV들의 평균). 옵션의 내재변동성은 봉 마감 전 1분 체결의 중앙값이고, 그 1분에 체결이 없으면 마지막 체결의 값이다(#76). 한쪽만 있으면 그쪽 값이고, 둘 다 없으면 값이 없다. 고르는 범위는 수집기가 시작할 때 구독한 행사가(전일 종가 기준 등가격 ±2)다. 장중에 크게 움직이면 가장 가까운 것도 등가격에서 멀어진다.

  > **바뀜** (2026-10-12, #77): 옵션의 IV는 마지막 체결 하나 → 봉 마감 전 1분 체결의 중앙값(없으면 마지막 체결). 이유: 체결 하나의 IV가 튀어 IV 국면이 흔들렸다(#76).

- **국면.** ATM IV가 아래 경계보다 낮으면 낮음, 위 경계 이상이면 높음, 그 사이는 보통이다.
- **문턱값(경계).** 고정값이 아니라 학습한다. 학습 기간(20거래일)의 녹화된 봉 마감 ATM IV를 셋으로 똑같이 나누는 두 값(3분위)이다. IV가 있는 날이 5거래일보다 적으면 경계를 두지 않는다. 그동안 Markov는 IV를 모르는 것처럼 동작한다. 경계는 녹화가 쌓이면서 그 시기의 IV 수준에 맞춰진다. KOSPI200 IV의 고정 문턱값은 시기마다 수준이 달라 근거가 약하다.
- **쓰는 곳.** 낮음과 높음 국면마다 1분 움직임의 배율을 하나씩 배운다. 그 국면에서 4국면의 평균과 표준편차에 이 배율을 곱한다. 보통 국면의 배율은 1로 둔다(4국면 그대로, IV를 모를 때와 같다). 전이행렬은 지금처럼 매크로 국면의 것이다. 배우는 방법은 [engine-api.md](engine-api.md#markov)에 있다.
- **IV를 모를 때.** 백필만 있는 날, 옵션 체결이 10분 넘게 없을 때, 경계가 없는 모델(예전 모델 포함)에서는 배율이 1이다. #53 전과 같은 예측이다.

**Gauss의 학습 결과(#162).** 2026-10-14에 확인했다. 버그가 아니라 학습 기간에 되돌림 신호가 없었다.
- **관찰.** 지금까지 학습한 모델 네 개(학습 창 2026-09-03..2026-10-02부터 2026-09-08..2026-10-08까지)가 모두 `{"speed": 0, "weight": 0, "threshold": 0}`이다. 그래서 기대 움직임은 언제나 0이다. 상승·하락 확률이 같은 정규분포(폭 = 1분 변동성 × √4, 최소 0.5틱)만 낸다. 2026-09-08..2026-10-08의 22,560개 봉 마감에서 가장 큰 확률은 98.7%가 보합이었다. 나머지는 상승·하락 확률이 같았다. 방향 정보는 없다.
- **재현.** S3의 백필 1분봉으로 같은 학습 코드를 돌리면 같은 버전 `gauss-20261008-c0ec81`, 같은 파라미터, 같은 log loss 0.6097이 나온다.
- **되돌림이 없다.** 모든 θ에서 4분 움직임을 VWAP 괴리에 원점 회귀한 기울기가 0 근처다(θ = 0에서 +0.0023, 상관 +0.008). 되돌림이면 음수여야 한다. 그래서 `ou_speed`가 κ = 0으로 자른다. 자르지 않은 값도 κ ≈ −0.0006/분이라 숨은 신호는 없다.
- **당일 속도(`reversion_speed`)도 정보가 없다.** 당일 속도로 낸 되돌림 방향의 적중률은 49.6%다(10,875번). w를 0에서 1로 올리면 log loss가 0.6097에서 0.6286으로 계속 커진다. 그래서 w = 0이다.
- **θ = 0은 의미 없는 동률이다.** κ = 0, w = 0이면 어느 θ에서나 예측이 같다. 같은 손실 중 격자의 첫 값(θ = 0)이 남는다. 예측에는 영향이 없다.
- **하루 안의 되돌림도 아니다.** 날마다 그날 평균을 빼고 회귀하면 기울기가 −0.025..−0.050이다. 그러나 1분 변화량의 순서를 섞은 랜덤워크에서도 같은 크기(−0.018..−0.056)가 나온다. 짧은 표본에서 평균을 빼면 생기는 편향이고, 그날 평균은 장중에 알 수도 없다.
- **그대로 둔다.** 밤 학습은 매일 κ와 w를 다시 맞춘다. 되돌림이 생기면 스스로 κ > 0을 고른다. 모델을 바꿀지, 벤치로 뺄지는 #162에서 정한다.

- 예비 후보: Hurst 지수로 추세 지속과 되돌림을 판정해 둘 사이를 전환하는 방향 알고리즘. Markov와 역할이 겹쳐 v1에서는 뺐다.

  > **바뀜** (2026-10-15, #198): "예비 후보: Mandelbrot. Hurst 지수로 …" → 후보는 그대로이고, Mandelbrot이라는 이름은 변동폭의 첫 모델(위 표)이 쓴다. 이 후보를 넣게 되면 다른 이름을 쓴다(알고리즘 이름은 하나뿐이어야 한다). 이유: 변동폭 spec(#177)이 변동성 군집을 처음 짚은 Mandelbrot(1963)의 이름을 첫 모델에 붙였다.
- 알고리즘끼리는 서로의 출력을 보지 않는다. 출력을 합치는 것은 Condorcet뿐이다.

### 7.2 알고리즘 모듈 규약

- 위치: `src/krx_quant/algorithms/<name>/`. 규약, 등록 검사, 피처, 학습 명령은 [engine-api.md](engine-api.md#알고리즘)에 있다(#10).
- 각 모듈은 공통 인터페이스를 따른다. 사용하는 피처 선언, `fit`, `predict`, 모델 버전.
- 알고리즘은 한 종류의 예측만 한다(`kind`, 없으면 방향, #179). 다른 종류의 알고리즘은 그 종류의 정답으로 학습하고 그 종류의 세 확률과 출력 필드를 낸다(5장 "예측 종류").
- 각 모듈에는 **성격 카드**를 둔다. 과학자, 성격, 핵심 로직, 고유 피처, 학습 방법, 예측 방식(세 확률을 만드는 방법), 실패 조건(틀리기 쉬운 장)을 한국어로 적는다. 카드 글은 도달 정답 기준이다(#170). 정답의 이름은 공통 문구(`cards.TOUCH_LABEL`), 정규분포 방식의 확률은 `forecasts.NORMAL_CLASSES`에 있다.

  > **바뀜** (2026-10-14, #193): "카드 글은 지금 정답(4분 뒤 중간가 변화) 기준이고, 정답이 바뀌면(#160) 고친다" → 도달 정답 기준으로 고쳤다. 이유: 정답이 바뀌었다(#160).
- 각 모듈은 모델이 가질 수 있는 모든 파라미터의 뜻(설명, 단위, 언제 정해지는지)을 둔다(`PARAM_MEANINGS`). 피처의 뜻(설명, 단위, 언제 아는지)은 피처 저장소의 레지스트리 옆(`features.py`의 `FEATURE_MEANINGS`)에 둔다. 뜻이 빠지면 테스트가 실패한다.
- 기준 예측 넷(정답 버전 2, 기본: `baseline-climate`까지, #169. 버전 1은 셋)과 합의 둘도 같은 형식의 카드를 가진다(`baselines.py`, `consensus.py`). "늘 보합"은 버전 2에서 같은 규칙에 도달 정답의 카드를 쓴다(#170).

  > **바뀜** (2026-10-14, #189): 카드는 과학자, 핵심 로직, 고유 피처, 학습 방법이었다 → 예측 방식과 실패 조건을 더하고, 피처와 파라미터마다 뜻을, 기준 예측과 합의에도 카드를 둔다. 이유: 상세 창의 "학습·예측 방식"이 무엇을 정답으로 배우고 확률을 어떻게 만드는지 다 말하게 하려고(2026-10-14 인터뷰, QUANT LETTER의 카드 형식).
- 피처는 공용 피처 저장소가 1분에 한 번만 계산한다. 알고리즘은 그 결과를 공유한다.
- 엔진은 예측 종목 말고도 선행 시리즈(KOSPI200·달러 선물, 지수, 미국 주간거래, ETF)의 1분봉을 피드에서 따로 만든다. 피처는 봉 마감 시점의 봉만 본다(#15).

### 7.3 개성 검사

- 등록할 때: 피처 조합이 같은 종류의 기존 알고리즘과 같거나 고유 피처가 하나도 없으면 거부한다. 고유 피처는 같은 종류에서 먼저 등록된 알고리즘이 쓰지 않는 피처여야 한다(#10, #179).
- 수습 중: 같은 종류의 기존 알고리즘과의 예측 상관이 0.9를 넘으면 "복제"로 표시하고 합의에서 뺀다. 방향은 p_up − p_down, 다른 종류는 첫 클래스 확률 − 셋째 클래스 확률의 상관이다.

> **바뀜** (2026-10-15, #196): 등록 검사와 복제 판정은 모든 기존 알고리즘과 견줬다 → 같은 종류의 알고리즘과만 견준다. 방향 알고리즘끼리는 그대로다. 이유: 종류마다 맞히는 것이 달라, 다른 종류의 알고리즘이 같은 피처를 쓰거나 비슷하게 움직여도 성격이 겹치는 것이 아니다(#177 "예측 종류").
- 상태(수습, 정식, 벤치, 은퇴, 복제)와 전환 규칙은 [engine-api.md](engine-api.md#상태-관리-17)에 있다(#17).

### 7.4 새 알고리즘 추가 절차

1. 모듈과 성격 카드(예측 방식과 실패 조건 포함), 파라미터의 뜻을 작성한다. 새 피처를 더하면 그 뜻도 `FEATURE_MEANINGS`에 넣는다.
2. `ALGORITHMS`(다른 종류의 알고리즘은 `KIND_ALGORITHMS`, #179)에 등록하고 머지한다. 개성 검사(`register`, `register_kind_algorithms`)는 이때 한다. 배포된 엔진은 이 알고리즘을 돌리지 않고 사전 검증을 기다린다. 첫 일일 점검 때 텔레그램으로 한 번 알린다.
3. 서버의 예약 작업이 사전 검증을 돌린다: `krx-quant prevalidate <이름>`(#24). 녹화가 10거래일 이상이 된 밤부터 기다리는 알고리즘을 밤마다 하나씩 돌리고 결과를 #204에 댓글로 남긴다(#204, [operations.md](operations.md#새-알고리즘-사전-검증-24)). 손으로 다시 돌릴 수도 있다. 녹화된 최근 20거래일(적어도 10거래일)을 재생해 실시간과 같은 채점·통계를 내고, 시간 예산, 기존 알고리즘과의 예측 상관, 피처 고유성을 확인한다. 기준은 [engine-api.md](engine-api.md#사전-검증-24)에 있다. 재생 결과는 별도 DB에 쓰여서 공식 성적에 들어가지 않는다.
4. 통과하면 엔진이 다음 봉 마감부터 수습으로 돌린다. 하나라도 기준을 넘지 못하면 등록되지 않는다. 고친 뒤 다시 돌린다. 공식 성적은 실시간 결과만 인정한다.

> **바뀜** (2026-10-11, #57): 사전 검증 도구가 없어서 `krx-quant replay <날짜>`로 하루씩 돌려 보고, `ALGORITHMS`에 등록하면 바로 수습으로 돌았다 → `krx-quant prevalidate <이름>`이 최근 20거래일을 한 번에 재생해 판정하고, 통과해야 엔진이 돌린다. 이유: #24("통과해야 수습으로 등록된다"). 이 전에 등록된 Newton, Gauss, Granger, Markov, Turing은 검증 없이 돈다.

> **바뀜** (2026-10-15, #228): 3단계는 사람이 서버에서 장 시간 밖에 `prevalidate`를 돌렸다 → 서버의 예약 작업이 녹화 10거래일부터 밤마다 하나씩 돌리고 결과를 #204에 남긴다. 이유: 날짜를 기억해 손으로 돌리지 않으려고(#214).

### 7.5 상태 관리

| 상태 | 합의 참여 | 진입 조건 |
|---|---|---|
| 수습 | X | 새로 등록되고 사전 검증을 통과함(#24) |
| 정식 | O | 수습 판정일(`KRX_PROBATION_REVIEW_DAYS`, 기본 10·20·40거래일째)에만 판정: 기준 대비 lift의 거래일 단위 신뢰구간(`KRX_REVIEW_CONFIDENCE`, 기본 98.3%) 하한 > 0 (자동) |

| 은퇴 | X (예측 중단, 기록 보존) | 수습·벤치 판정일 목록의 마지막 날(기본 수습 40거래일, 벤치 60거래일)이 지나도 정식이 되지 못함 → 은퇴 후보 → 사용자 승인 |
| 복제 | X (예측·채점은 계속) | 수습 중 먼저 등록된 알고리즘과 예측 상관 > 0.9 (자동, 상관이 내려가면 수습으로) |

> **바뀜** (2026-10-13, #123): 수습은 10거래일부터 매일, 벤치 복귀는 매일 95% 하한으로 판정했고 수습에 끝이 없었다 → 수습 10·20·40일째와 벤치 20·40·60일째에만 98.3% 하한으로 판정하고, 수습 40일·벤치 60일이 지나도 정식이 못 되면 은퇴 후보 알림을 한 번 보낸다(설정으로 바꿀 수 있다). 이유: 매일 다시 보면 실력이 없는 알고리즘도 운으로 통과하기 쉬웠다(#78의 합성 실험: lift 0인 알고리즘의 34%가 20일 안에, 47%가 60일 안에 승격). 세 번 보는 판정을 합쳐도 운으로 통과할 확률이 한 번 본 95% 판정(한쪽 2.5%)을 넘지 않게, 한 번마다 98.3%로 본다(본페로니, #87). 숫자는 사용자와 정했다.

> **바뀜** (2026-10-11, #57): 수습 진입 조건 "새로 등록됨" → "새로 등록되고 사전 검증을 통과함". 이유: #24. 검증을 기다리는 알고리즘은 상태가 없고, 예측도 순위표에도 나오지 않는다.

- 벤치에서 최근 20거래일 lift의 거래일 단위 하한이 0보다 커지면 정식으로 돌아간다. 판정 통계와 세부 규칙은 [engine-api.md](engine-api.md#상태-관리-17)에 있다(#17).
- **정답이 바뀌는 날(#170).** 판정은 도달 정답으로 학습한 모델의 예측만 본다(6장). 이 엔진을 처음 배포한 날, 엔진이 DB를 처음 열 때 은퇴가 아닌 모든 알고리즘을 한 번 수습으로 돌린다(이유 `the target changed to the touch target (#170): probation restarts with a model trained on it`). 옛 정답 판정은 그날 멈춘다. 수습은 알고리즘마다 도달 정답 모델로 처음 예측한 거래일부터 센다. 그날 밤 학습이 도달 정답 모델을 성적 비교 없이 올리므로(8장), 보통 다음 거래일 08:00 교체가 올린 날이다. 학습이 실패해 교체되지 않은 알고리즘이나 휴일 배포는 실제로 올라간 날까지 세지 않는다. 그동안 상세 창의 `stage`는 `counted_from`이 비어 있다. 정식이 없으므로 첫 판정(수습 10거래일째)까지 합의는 "합의 대상 없음"이고 신호도 없다. 새로 등록된 알고리즘도 같은 규칙이라, 기본값 모델로 돈 날은 세지 않는다.
- 정식 승격은 lift 신뢰구간 하한으로 판정한다. 순위표의 FDR 보정 q값은 판정에 쓰지 않는다.
- 다른 종류의 알고리즘(#179)도 같은 표와 날짜로 판정한다. lift는 그 종류의 기준 예측 대비이고, 그 종류의 정답으로 학습한 모델의 예측만 센다(5장 "예측 종류"). 정식이 되어도 합의가 없어서 화면 표시와 판정 기록에만 쓰인다.
- 판정에 쓰는 하한은 거래일 단위다. 하루의 짝 차이 평균을 값 하나로 보고, 날들의 평균에 t분포 구간을 쓴다. 매분 예측을 독립으로 세는 순위표의 짝 단위 하한은 설명용이다.

  > **바뀜** (2026-10-12, #91): 정식 승격과 벤치 회복의 하한: 짝 단위(정규근사) → 거래일 단위(t분포). 이유: 4분 정답이 1분마다 겹치고 종목들이 같은 시장 움직임을 타서, 짝 단위 하한은 실제 lift가 0인 알고리즘도 자주 0 위로 올렸다(합성 실험 13–19%, #78). 판정 시점은 #87에서 정한다.

## 8. 학습

- 학습은 그날 1분봉 백필(20:30)과 업로드(21:00)가 끝난 뒤 시작한다. 기본은 Lightsail 수집기가 21:30에 별도 프로세스로 돌린다(#22). EC2 Spot으로 옮길 수도 있다(`KRX_TRAIN_ON=spot`, #23).
  - EventBridge Scheduler가 평일 21:30에 one-time Spot 인스턴스를 띄운다.
  - 인스턴스는 ECR의 엔진 이미지로 `krx-quant train --from-store`를 한 번 돌리고 스스로 종료한다.
  - 기본은 CPU 인스턴스(`m6i.large`)이고, 신경망 알고리즘이 있을 때만 GPU 인스턴스를 쓴다.
  - 인스턴스에는 비밀값이 없다. 서버가 S3에 올린 설정과 휴장일 달력으로 학습하고, 결과도 S3에만 쓴다. 텔레그램 요약은 서버가 S3에서 결과를 보고 보낸다.
  - 운영 절차는 [operations.md](operations.md#밤-학습을-ec2-spot으로-옮기기-23)에 있다.
  - **지금 계정에서는 Spot을 쓰지 못한다(2026-10-14, #23).** AWS Settings 프로젝트로 만든 계정(9장)은 AWS가 관리하는 조직의 서비스 제어 정책이 Spot을 막는다. `DenySpotMarketType`은 `ec2:InstanceMarketType`이 `spot`인 `RunInstances`를 거부한다. 스택을 배포하고 시험으로 띄우다 확인했다. 그래서 밤 학습은 상시 서버에서 계속하고(`KRX_TRAIN_ON=server`), 스택은 지웠다. 같은 `m6i.large`를 온디맨드로 띄우는 것은 허용된다(dry-run으로 확인). Spot을 쓰려면 고급 기능을 활성화하고 정책을 바꿔야 한다. 그러면 지출 한도가 사라지고 되돌릴 수 없다. 서버 메모리가 학습에 모자라면 온디맨드 EC2와 고급 기능 중에서 다시 정한다.
- 각 알고리즘은 롤링 구간 데이터로 walk-forward 학습을 한다. 기본 구간은 20거래일이고 Turing은 60거래일이다.
- 녹화된 날은 녹화 이벤트로 학습한다. 1분봉, 선행 묶음, 기준가(중간가)가 엔진이 본 것과 같고, 정답도 실전 채점과 같다. 백필만 있는 날은 1분봉 종가로 학습한다([engine-api.md](engine-api.md#학습)).
- 정답 버전 2(`KRX_TARGET_VERSION=2`, #169, 기본은 #170부터)이면 학습 정답이 도달 정답이다. 녹화된 날은 엔진의 도달 정답 모듈이 녹화 호가로 정확히(엔진이 기록하는 정답과 같다), 백필만 있는 날은 1분봉 규칙(종가 기준, 1틱 여유와 종가 위치에 따른 1틱, 다음 봉 시가는 정답에만)으로 만든다. 밤 학습 리포트와 텔레그램 요약에 정답 출처별 표본 수가 남고, 밤 학습이 시간대 기후 기준 예측의 표(`baseline-climate`, 최근 20거래일)도 다시 맞춘다.

  > **바뀜** (2026-10-14, #191): 정답 버전 2에서만: 학습 정답이 4분 뒤 중간가(녹화일)·종가(백필일) 클래스 → 도달 정답(녹화일은 호가, 백필일은 1분봉 규칙). 이유: 4분 안에 그 가격에 시장가로 거래할 수 있었는지가 사용자가 알고 싶은 것이고(#160), 1분봉 날도 새 정답에 가깝게 학습해야 최근 20거래일로 바로 다시 학습할 수 있다.
- 새 모델(challenger)이 학습에 쓰지 않은 최근 3거래일에서 현재 모델(champion, 서버가 돌리는 모델)보다 log loss가 낮을 때만 교체한다. 다만 champion이 그 밤과 다른 정답 버전으로 학습한 모델이면(기본값과 버전이 기록되기 전 모델은 버전 1로 친다) 성적 비교 없이 교체한다(#170). 정답이 바뀐 뒤 첫 밤에 모든 알고리즘이 새 정답 모델로 바뀌게 하려고다. 리포트에 `forced: true`가, 텔레그램 요약에 "승격(정답 바뀜, 성적 비교 없이)"이 남는다.

  > **바뀜** (2026-10-14, #193): "낮을 때만 교체한다"에 정답 버전이 다르면 강제 승격을 더했다. 이유: 옛 정답 모델이 새 정답의 검증에서도 이기면 새 정답 모델이 영영 올라가지 않고, 수습도 시작되지 않는다(#160 "강제 승격").
- 모델은 자기를 학습한 정답 버전을 갖는다(`target_version`, #170). 학습 표본의 피처에 도달 정답의 항(봉 마감 스프레드의 절반)이 있으면 2, 없으면 1이다. 기본값 모델은 없음(`null`)이다. 버전 2 모델의 버전 문자열에는 정답 버전이 해시에 들어가, 같은 파라미터라도 버전 1 모델과 이름이 다르다.
- 다른 종류의 알고리즘(#179)은 그 종류의 정답으로 학습한다. 녹화된 날은 엔진과 같은 시장 보기 창과 그 종류의 정답 함수로, 1분봉만 있는 날은 그 종류의 1분봉 규칙으로 만든다. champion/challenger는 그 종류 세 클래스의 log loss로 견주고, 모델의 정답 버전은 그 종류의 정답 버전이다. 그 버전이 다른 champion은 성적 비교 없이 바꾼다(위와 같은 규칙). 방향 알고리즘과 기후 표를 학습한 뒤에 학습하고, 리포트에 `kind`와 그 종류의 정답 출처별 표본 수가, 텔레그램 요약에 종류마다 한 줄이 남는다.
- 다른 종류의 표에서 내는 기준 예측(변동폭의 `range-climate`, #180, 장벽의 `barrier-climate`, #183)은 방향의 기후 표 다음에, 그 종류의 정답(최근 20거래일, 그 밤까지)으로 매일 다시 맞추고 성적 비교 없이 승격한다. 08:00 교체가 설치한다. 리포트는 그 종류의 알고리즘의 것과 같은 형식(`kind`, 정답 버전, 정답 출처별 표본 수)이다.
- 전 거래일 시간대 범위(`range_prev_day`, #181)와 장벽 폭의 전 거래일 봉(#183)은 녹화일이든 백필 날이든 전 거래일의 백필 1분봉에서 읽는다(엔진, 재생, 사전 검증, 지난 정답 채우기도 같다). 밤 학습은 그 날의 종목 1분봉도 S3에서 캐시로 받는다.
- 결과 모델(지금은 JSON 파라미터, 신경망이 생기면 ONNX), 검증 리포트, 승격 목록을 S3에 올린다. EC2에서는 끝나면 인스턴스가 스스로 종료한다.
- 모델은 무엇으로 배웠는지를 값으로 함께 가진다(#165): 학습 기간(첫날·마지막 날), 표본 수, 학습 데이터로 잰 손실, 정답 출처별 날 수(녹화된 날·1분봉만 있는 날). 엔진 API가 지금 모델의 이 값과, 가장 최근 밤의 그 알고리즘 검증 리포트(새 모델과 지금 모델의 검증 손실, 승격 여부와 이유)를 보인다([engine-api.md](engine-api.md#get-v1algorithms)).
- 상시 서버는 다음 날 08:00에 새 모델로 교체한다.
- 07:30까지 학습이 끝나지 않으면 기존 모델을 그대로 쓴다.
- Spot 인스턴스가 중간에 회수되면 체크포인트(알고리즘별 검증 리포트)부터 다시 시작한다. 00:30에 스케줄러가 한 번 더 띄워 이어 간다.
- 모델 버전 이력을 남기고 `krx-quant rollback <알고리즘>` 한 번으로 되돌릴 수 있다. 모든 예측에는 모델 버전을 기록한다. 운영 절차는 [operations.md](operations.md#밤-학습과-모델-교체-22)에 있다.

> **바뀜** (2026-10-11, #67): "#23에서 EC2 Spot으로 옮긴다" → 서버와 Spot 중에서 고른다(`KRX_TRAIN_ON`, 기본 서버). 이유: Spot은 AWS 비용이 들어 사용자가 스택(`deploy/training.yaml`)을 배포하고 켠다.

> **바뀜** (2026-10-10, #45): "매일 16:00 KST에 EventBridge Scheduler가 EC2 Spot을 띄우고, 모델은 ONNX" → 거래일 21:30(`KRX_TRAIN_AT`)에 상시 서버의 수집기가 별도 프로세스로 학습하고, 모델은 JSON 파라미터다. EC2 Spot은 #23으로 미뤘다. 이유: 그날 1분봉은 20:30에 백필하고 21:00에 올린다. 16:00에 학습하면 전날까지의 봉만 본다(PR #45). 16:00을 원하면 하루 늦은 데이터로 `KRX_TRAIN_AT=16:00`을 쓴다.

## 9. 인프라와 비용

- **상시 서버.** Lightsail 시드니(`ap-southeast-2`) 2GB, 월 $12. IPv4 주소가 있는 요금제여야 한다. KIS 서버에 IPv6 주소가 없기 때문이다. 엔진은 Docker로 띄운다.
  - 서울이 아니라 시드니인 이유: 2026-10-08에 AWS의 새 가입 방식(AWS Settings 프로젝트)으로 계정을 만들었다. 이 방식에서는 프로젝트마다 리전이 하나뿐이고, 연락처 주소의 국가에 따라 오하이오·스톡홀름·시드니 중 하나로 정해진다. 서울을 쓰려면 고급 기능을 활성화해야 하는데 되돌릴 수 없어서, 시드니에 둔다.
  - KIS까지 왕복 지연이 100ms 넘게 늘어나지만, 4분 뒤를 예측하는 데는 무시할 만하다.
  - 학습용 EC2 Spot과 S3도 같은 리전에 둔다. 리전 사이 데이터 전송 요금을 피하기 위해서다.
  - Lightsail은 버스트형 CPU다. CPU가 모자라면 기준선이 높은 요금제($44: vCPU 2개, 기준선 30%. $84: vCPU 4개, 40%)나 비버스트형 EC2로 옮긴다. $24(4GB)는 $12와 CPU가 같아서(vCPU 2개, 기준선 20%) 메모리가 모자랄 때만 도움이 된다. 재는 법은 [operations.md](operations.md#cpu-여유-재기)에 있다.

    > **바뀜** (2026-10-12, #75): "부하가 늘면 4GB($24) 요금제나 비버스트형 EC2로" → CPU는 $44 이상이나 EC2, 4GB는 메모리만. 이유: AWS Lightsail 기준선 표에서 $12와 $24는 vCPU 수와 기준선이 같다(PR 리뷰에서 확인).
  - 로컬 개발은 호스트에서 `uv run`으로 한다(README "개발 환경"). 컨테이너는 서버, Spot 학습(ECR 이미지), 로컬 연기 시험(`deploy/smoke-local.sh`)에서만 쓴다.

## 10. Fincept 화면

- **구성.** 종목별로 다음을 보여준다.
  - 1분봉 차트에 합의 예측 화살표와 채점 결과(✓/✗)를 겹쳐 표시
  - 알고리즘별 예측 패널: 상승/보합/하락 확률, 기대수익(틱), 빠른·최종 합의, 그 예측이 보는 4분(봉 마감부터 채점 시각까지)

    > **바뀜** (2026-10-16, #244): 채점까지 남은 시간 → 그 예측이 보는 4분. 이유: 아래 종목 목록의 바뀜과 같다.

  - 순위표: 오늘/5일/20일 성적과 모델 버전, 상태
  - 매크로 줄: 달러선물, 오늘의 시장 국면
  - 엔진 상태: KIS 연결, 데이터 지연, 어젯밤 학습 결과(교체 여부)
- **신호 알림.** Condorcet 확률이 기준값 이상이고 N개 이상의 알고리즘이 같은 방향이면 데스크톱 알림과 소리를 낸다. 기준값과 N은 화면에서 조정한다. 텔레그램 신호 알림은 옵션이다.
- **언어.** 한국어. 알고리즘 이름은 영어로 쓴다.
- **경제 캘린더 (#150).** KRX 화면에 엔진 주소(`krx_quant/base_url`)를 넣으면, 대시보드의 Economic Calendar 위젯은 Fincept 서버(`api.fincept.in/macro/upcoming-events`, 크레딧을 쓴다) 대신 엔진의 `/v1/calendar`를 읽는다(4.5의 "경제 캘린더"). 시각은 KST로 보인다. 엔진 주소가 없으면 원래대로 Fincept 서버를 읽는다. 자세한 것은 `fincept/custom/README.md`의 "경제 캘린더"에 있다.
- **Fincept 공통 UI 한국어 (#132).** Settings → General → Interface language에서 **한국어**를 고르면 기존 내부 언어 팩과 같은 방식으로 즉시 적용된다. 선택은 SQLite settings의 `general.language=ko_KR`에 저장되고 다음 실행에도 유지된다. 기존 공통 팩 전체와 최신 설정·탐색 문구를 한국어로 제공하며, 팩 밖의 신규·고정 문구는 영어로 보일 수 있다. 언어 팩과 검증 방법은 `fincept/custom/README.md`의 "한국어 언어 팩"을 따른다. 용어와 문체는 국내 증권사 HTS/MTS와 KRX·DART 표기(PER, 평가손익, 평균단가, 매입금액, 계좌/계정, 증권사, 모의투자/실전투자, 가상자산, 샤프지수 등)를 따른다. 기준은 `fincept/custom/korean-glossary.md`다.

  > **바뀜** (2026-10-13, codeyoma/FinceptTerminal#31): 직역 위주의 금융 용어(P/E 비율, 미실현 손익, 취득 원가, 브로커, 모의 거래, 암호화폐 등)와 번역투 → 업계 표기와 자연스러운 문장으로 약 1,200개 항목을 고쳤다. 환산하지 않은 시세 표시 `(원 단위)`는 `(거래 통화)`가 됐다. 이유: 국내 금융 화면의 표기와 달랐고, KRW 표시 통화가 생긴 뒤 `원`이 원화로 읽혔다.
- **Fincept 표시 통화 (#138, #142).** 같은 설정의 Display currency(표시 통화)에서 **₩ South Korean Won (KRW)**을 고른다. 선택은 SQLite settings의 `general.currency=KRW`에 저장된다. ECB 일일 참고환율의 교차 비율로 출처 통화가 확인된 시장·관심종목·대시보드·현재 포트폴리오·주식 리서치 금액을 환산한다. 설정에 환율 출처·기준일·갱신 상태를 표시한다. 검증한 캐시는 `general.fx_rates_v1`이며 7일을 넘으면 환산하지 않는다. 환율·원 통화가 없으면 원래 금액/통화를 유지하고, 혼합 단위 포트폴리오 합계는 표시하지 않는다. 지수·수량·비율·주문·출처가 불확실한 과거 기록은 원 단위를 유지한다. 적용 범위와 예외, 저장 키는 `fincept/custom/README.md`의 "원화 표시 통화"를 따른다.

  > **바뀜** (2026-10-13, codeyoma/FinceptTerminal#26): 표시 통화는 계산기·분석의 기호만 바꿨다 → 확인된 출처 통화의 금액에 일일 참고환율을 적용한다. 이유: 사용자가 실제 원화 금액 환산을 요청했다. 원본 데이터와 주문 단위는 유지한다.

"일" 뒤의 "주 월 년" 버튼(#112)은 엔진이 KIS에서 받아 저장한 끝난 주·월·년봉(`candles?period=week|month|year`, 기간의 첫날로 날짜를 붙임: 월요일, 1일, 1월 1일)을 읽고, 그 뒤의 기간(이번 주·달·해, 엔진이 아직 저장하지 않은 지난 기간)은 일봉(오늘 봉 포함)을 묶어 만든다. 그래서 지금 봉도 실시간으로 움직인다. 엔진은 오늘이 든 기간의 봉을 주지 않는다. 일·주·월·년 보기에는 아이콘이 없고, 최신 봉을 읽은 뒤에 그린다. 고른 보기와 차트 모양은 종목마다 앱 설정(`krx_quant/chart/<종목코드>/view`, `…/style`)에 남고, 종목을 고르면 그 종목의 것으로 바뀐다(#221). 처음 여는 종목은 1분·캔들이다. 툴바는 `[1분 ▾] 일 주 월 년 │ [차트 모양] [+ 보조지표] [그리기]`이고, 오른쪽 끝에 `[휴지통] [톱니]`가 있다. 차트 모양(#221)은 바, 캔들, 라인, 영역, 하이킨아시, 투명캔들, 베이스라인이다. 하이킨아시는 봉을 하이킨아시 봉으로 그리되 현재가 선과 거래량 색은 원래 봉의 것이다. 베이스라인의 기준값은 분 보기에서 전일 종가(읽은 봉 중 가장 최근 날 첫 봉 앞의 종가. 없으면 첫 봉 시가), 일·주·월·년 보기에서 화면 첫 봉의 종가다. 아이콘·호버·4분 구간은 시간축 모양 모두에서 같다. 렌코(종가, 박스 ATR(14)), 카기(반전폭 ATR(14)), 포인트 앤 피겨(박스 ATR(14), 반전 3칸), 라인 브레이크(3줄)는 시간축 없는 모양이다(#225). 지금 보기의 봉의 종가로 벽돌을 만들어 벽돌 순서로 한 칸씩 그린다. 축과 십자선에는 벽돌을 끝낸 봉의 시각을 보이고, 벽돌의 거래량은 그 벽돌을 만든 봉들의 합이다. ATR(14)는 지금 보기의 봉 중 마지막 봉(만들어지는 중일 수 있다)을 뺀 봉으로 센 마지막 값(원 단위로 반올림)이다. 그래서 새 봉이 시작되거나 앞의 봉을 더 읽거나 보기·종목을 바꿀 때만 다시 세고, 지금 봉이 움직이는 동안 다른 일로 차트를 다시 그려도(지표 켜기, 예측 갱신) 크기와 벽돌은 그대로다(#233). 그 모양을 고른 동안 톱니 메뉴에서 크기(박스·반전폭은 원, 라인 브레이크는 줄 수)를 바꾸거나 ATR(14)로 되돌린다. 크기는 종목마다 앱 설정 `krx_quant/chart/<종목코드>/brick_sizes`(JSON 객체)에 남는다. 벽돌은 시작한 봉에 따라 달라진다. 그래서 그 보기의 봉을 180개 이상(엔진에 그만큼 없으면 있는 만큼) 읽은 뒤의 첫 봉에서 시작하고, 그 시작을 종목과 보기마다 한 번 정한다. 그 뒤에 앞의 봉을 더 읽어도 벽돌은 바뀌지 않고, 벽돌 차트를 왼쪽으로 스크롤해도 앞의 봉을 읽지 않는다. 시간축 없는 모양에서는 예측 아이콘, 호버, 4분 구간, 날짜 구분선, 그린 것, 선택 합의 성적을 숨기고 `그리기`, 휴지통, 날짜 구분선 항목을 비활성으로 둔다. 시간축 모양으로 돌아오면 다시 보인다. 지표는 벽돌의 OHLCV로 센다. 실제 시각이 필요한 VWAP와 고정된 VWAP는 벽돌에서 그리지 않는다(보조지표 패널에서 비활성, 툴팁 "시간축 없는 차트에서는 쓰지 않는다", 켠 것과 설정은 남음). AD 라인과 OBV는 첫 벽돌이 0이다. 변환, 크기, 시작은 화면 코드의 순수 함수(`ChartBricks`, 합성 봉 테스트)이고, 자세한 규칙은 fork의 `custom/README.md`("차트 모양")에 있다. 톱니 메뉴의 "날짜 구분선"(#221, 기본 켬, 모든 종목에 하나, `krx_quant/chart_day_separator`)을 켜면 분 보기에서 KST 날짜가 바뀐 뒤 첫 봉(보통 08:00 NXT 봉) 한 칸을 가격 칸과 하단 칸 전체 높이의 회색 띠로 칠한다. 일·주·월·년 보기와 시간축 없는 모양(#225)에서는 비활성이다. 분 보기(1분과 N분)는 그날 첫 봉과 마지막 봉 사이에 체결이 없어 봉이 없는 분(N분 칸)마다 빈 봉을 둔다(#236). 빈 봉은 한 칸을 차지하지만 캔들도 거래량 막대도 없다. 그래서 서킷브레이커처럼 거래가 멈춘 시간만큼 차트에 빈 칸이 생기고 시각이 건너뛰지 않는다. 그날 첫 봉 앞과 마지막 봉 뒤, 두 날 사이는 채우지 않는다. 다만 오늘 장이 열려 있는 동안(엔진 상태의 `session`의 `open`부터 `close` 전까지, `now` 기준)은 오늘 마지막 봉 뒤의 칸도 엔진 시계까지 다 지난 칸마다 빈 봉으로 채운다. 그래서 진행 중인 서킷브레이커나 VI, 체결이 드문 종목의 조용한 시간도 지난 만큼 1분에 한 칸씩 자라며 보인다. 장이 끝나면(`close` 뒤) 그날은 첫 봉에서 마지막 봉까지로 돌아가고, 오늘 첫 봉이 아직 없으면 자라지 않는다. 빈 봉이었던 칸에 나중에 실제 봉이 오면 그 봉이 칸을 차지한다. 그날 안의 다른 빈 시간(NXT 장전 08:50–09:00, 종가 동시호가 15:20–15:30, 체결이 드문 종목의 빈 분)은 그대로 보인다. 거래 없는 분 뒤에 새 봉이 오면 그 사이가 곧바로 채워지고, 앞의 봉을 더 읽어도 같은 규칙으로 채운다. 빈 봉의 호버 상자는 그 칸의 시각과 "체결 없음"이고("09:20–09:21 · 체결 없음"), 아이콘과 4분 구간은 없다. 빈 봉은 칸으로는 세고 값으로는 쓰지 않는다. 보조지표는 실제 봉으로만 세어 값이 바뀌지 않고, 선은 빈 봉을 건너 앞뒤 실제 봉을 잇는다(TradingView의 기본 선 `plot.style_line`처럼). 그리기의 시각과 봉 위치 변환은 빈 칸을 세어 멈춘 시간 안의 점도 제 칸에 놓이고, 자석은 빈 봉에 붙지 않는다. 맞춤의 최근 60봉은 최근 60칸이고, 날짜 구분선은 그날 첫 실제 봉에 칠한다. 베이스라인 기준값, 하이킨아시, 매물대는 실제 봉으로 세고, 시간축 없는 모양의 벽돌은 빈 봉을 쓰지 않는다. 분 보기에는 엔진이 아는 특수 상황(#236, `GET /v1/symbols/{symbol}/special?from=&to=`: 그 종목의 VI와 시장 전체의 서킷브레이커·사이드카)을 옅은 세로 띠로 가격 칸과 하단 칸에 칠하고 이름표를 단다("서킷브레이커 1단계", "사이드카", VI는 KIS가 알린 종류로 "정적 VI"·"동적 VI"·"정적·동적 VI"). 색은 종류마다 하나다(서킷브레이커 빨강, 사이드카 노랑, VI 파랑). 아직 끝나지 않은 구간의 띠는 엔진이 예상한 끝이 아니라 엔진 시계까지 그려 시계와 함께 자란다. 띠 안의 봉 호버 상자에 그 구간("서킷브레이커 1단계 09:06–09:36")이 붙고(새로 붙는 실시간 봉도), N분 보기에서도 빈 봉과 띠 안의 봉에는 상자가 나온다. 일·주·월·년 보기와 시간축 없는 모양에는 그리지 않는다. 화면은 읽은 1분봉의 첫 날부터 엔진의 오늘까지(엔진이 한 번에 답하는 60일까지) 묻고, 종목을 고르거나 앞의 봉을 더 읽어 날이 바뀌면 곧바로, 화면이 보이는 동안 60초마다 다시 읽는다. 그 응답이 없는 엔진(404)이면 띠가 없다. 톱니 메뉴의 "특수 상황 표시"(기본 켬, 모든 종목에 하나, `krx_quant/chart_special`)로 띠와 호버 줄을 끈다(빈 봉은 그대로다). 채우기와 띠·호버 줄은 화면 코드의 순수 함수(`ChartSlots`, 합성 봉 테스트)이고, 자세한 규칙은 fork의 `custom/README.md`("빈 봉", "특수 상황 표시")에 있다. 툴바의 `+ 보조지표`(#222)는 두 칸 패널을 연다. 왼쪽은 `상단 지표` 12종과 `하단 지표` 25종(#223) 목록이고(세로로 스크롤된다), 체크 원으로 켜고 끈다. 오른쪽은 고른 지표의 이름, `?` 도움말, 설명 한 줄, 설정(기준값, 기간·배수, 선마다 색·굵기. 이동평균선·지수이동평균선은 `기간 추가`와 X)이다. 바꾸면 바로 그린다. 상단 지표와 기본값은 이동평균선(단순 5·20·60·120, 종가), 일목균형표(전환 9, 기준 26, 선행 52, 이동 26. 선행스팬은 마지막 봉 뒤 26봉까지), 볼린저 밴드(20, 2σ, 종가), 슈퍼트렌드(ATR 10, 배수 3), 매물대분석(보이는 봉, 가격대 24칸, VWAP는 (고가+저가+종가)/3으로, KST 날짜가 바뀐 첫 봉부터 다시 센다. 읽은 봉에 그날이 다 있을 때만(그 앞 날짜의 봉도 읽었거나 엔진에 더 앞의 봉이 없을 때) 그리고, 중간부터 읽었을 수 있는 첫 날은 비우며 범례에 "그날 첫 봉을 읽지 않아 비움"을 보인다. 틀린 값을 그리지 않고, 앞을 더 읽어도 그려진 값은 바뀌지 않는다. 분봉에서만 그린다: 일·주·월·년 보기에서는 목록에서 흐리고 툴팁이 "분봉에서만"이며, 켜 둔 것은 그리지 않되 남는다. 고정된 VWAP는 차트를 눌러 고른 기준 봉부터 세고, 기준 표시를 드래그해 옮긴다(범례에서 숨긴 동안은 다시 고르지 않는다). 기준은 시각으로 남아, 보기를 바꾸면 그 시각이 든 봉이 기준이다. 슈퍼트렌드와 SAR는 TradingView의 `ta.supertrend`, `ta.sar`와 같은 식이다. 하단 지표(#223)와 기본값(괄호 안 마지막은 가이드선)은 거래량(막대, 상승색·하락색), 매스 인덱스(EMA 9, 합 25. 27, 26.5), 모멘텀(10, 종가), 볼륨 오실레이터(짧은 5, 긴 10), 볼린저 밴드 %B(20, 2σ. 1, 0), 볼린저 밴드폭(20, 2σ), 스토캐스틱(14, 3, 3 슬로우. 80, 20), 스토캐스틱 RSI(RSI 14, 스토캐스틱 14, K 3, D 3. 80, 20), 윌리엄스 R(14. −20, −80), 이격도(20. 100), 일중 강도 지수(21. 0), 체이킨 오실레이터(3, 10. 0), 트릭스(18, 시그널 9. 0), 프라이스 오실레이터(짧은 10, 긴 21, 단순. 0), AD 라인, ADX(14), ATR(14), CCI(20. 100, −100), DMI(14. +DI, −DI, ADX), MACD(12, 26, 9. 0), MFI(14. 80, 20), OBV, ROC(9. 0), RSI(14. 70, 30), RMI(14, 모멘텀 5. 70, 30)다. RSI·RMI·ATR·DMI·ADX는 Wilder 평균, MACD·트릭스·매스 인덱스·볼륨 오실레이터·체이킨 오실레이터는 EMA이고, 둘 다 처음 N개 값의 단순 평균에서 시작한다. AD 라인과 OBV는 어디서부터 세느냐에 따라 값이 달라지므로, 날마다 다시 세는 VWAP와 달리 읽은 봉에 기대지 않는 시각에서 0이 되게 센다: 분 보기는 마지막 봉 날짜의 0시, 일·주·월·년 보기는 마지막 봉 해의 1월 1일이고, 그 시각부터의 첫 봉이 0, 그 앞 봉은 거꾸로 뺀다. 둘 중 하나를 켜면 그 시각보다 앞의 봉까지 읽고(목표는 종목과 보기마다 한 번 정한다, 상한 2,000봉), 그 시각부터의 봉을 다 읽기 전에는(그 앞 봉을 읽었거나 엔진에 더 앞이 없을 때까지) VWAP처럼 비우고 범례에 이유("그날(그해) 첫 봉을 읽지 않아 비움", 상한에 닿으면 "… 2,000봉보다 앞이라 비움")를 보인다. 그래서 그린 값은 앞의 봉을 더 읽어도 바뀌지 않고, 날(또는 해)이 바뀔 때만 선 전체가 한 번 오르내린다. 하단 지표마다 가격 칸 아래 칸 하나를 켠 순서대로 쌓는다. 칸 경계를 드래그해 높이를 바꾸고(처음 100px, 40–1000px), 높이는 종목마다 `krx_quant/chart/<종목코드>/pane_heights`(JSON 객체)에 남는다. 가격 칸은 200px 아래로 줄지 않고, 칸이 많아 모자라면 차트가 패널보다 길어져 세로로 스크롤된다. 가이드선은 그 칸의 점선이고 축 범위에 늘 든다. 숨긴 하단 지표의 칸은 빈 채 남는다. 지표는 화면이 원래 봉(하이킨아시라도)으로 센다(엔진은 지표를 주지 않는다). 칸마다 왼쪽 위 범례에 지표마다 이름, 설정값, 십자선 위치(없으면 마지막 봉)의 값이 있고, 마우스를 올리면 숨기기·설정·삭제 버튼이 나온다. 숨긴 지표는 켠 채 그리지 않는다. 켠 지표의 앞 기간 중 가장 긴 것(기본 이동평균선 120이면 119봉)만큼 첫 화면(60봉) 앞의 봉을 지난 날 스크롤과 같은 읽기로 더 읽는다. 앞의 모든 봉에 기대는 재귀 지표는 더 읽어도 값이 거의 바뀌지 않을 만큼 읽는다: 지수이동평균선은 가장 긴 기간의 4배(남는 무게 약 e^-8), 슈퍼트렌드는 ATR 기간의 10배, 파라볼릭 SAR는 100봉이다. 하단 지표는 계산 단계마다 더한다: EMA는 기간의 4배, Wilder 평균은 기간의 8배(남는 무게 약 e^-8), 고정 기간은 기간 − 1이다(기본값으로 MACD 140, RSI 112, ADX·DMI 224, 트릭스 252, 스토캐스틱 RSI 129). AD 라인과 OBV는 앞 기간 대신 위의 0점 시각 앞까지 읽는다. 그래도 TradingView처럼 더 읽으면 조금 바뀔 수 있다. VWAP를 켠 분 보기는 첫 화면의 가장 이른 날짜 0시 앞(그 전 날짜의 봉)까지 읽어 화면의 날들이 다 있게 한다. 이 목표는 종목과 보기마다 첫 화면에서 한 번 정하고, 읽은 첫 봉으로 다시 정하지 않는다. 고정된 VWAP의 기준 봉이 읽은 봉보다 앞이면 그 봉까지 읽는다. 상한은 모두 그 보기의 봉 2,000개(엔진 `limit`의 최대)이고, 엔진에 더 앞이 없으면 앞부분을 비운다. 지금 봉이 1초마다 움직이면 지표의 마지막 값도 움직이고, 봉 마감과 더 읽기 때 전체를 다시 센다. 켠 지표와 설정값은 종목마다 `krx_quant/chart/<종목코드>/indicators`(JSON), 고정된 VWAP의 기준은 `…/vwap_anchor`(ISO 8601)에 남는다. 처음 여는 종목은 이동평균선(5·20·60·120, 종가)과 거래량을 켠다. 하단 지표를 끄면 그 칸이 없어진다. 키의 형식과 계산은 fork의 `custom/README.md`("보조지표")에 있다. 툴바의 `그리기`(#224)는 도구 12종(추세선, 반직선, 수평선, 수직선, 크로스, 사각형, 타원, 피치포크, 피보나치 되돌림, 피보나치 채널, 피보나치 속도 저항 팬, 텍스트)과 구분선, `자석`의 메뉴다. 도구를 고르고 가격 칸을 도구가 받는 수만큼(수평선·수직선·크로스·텍스트 1점, 피치포크·피보나치 채널 3점, 나머지 2점) 누르면 그려지고 커서로 돌아간다. Esc로 취소한다. 도구를 고른 동안 가격 칸의 클릭은 그리기이고, 그 밖에는 1분 보기의 아이콘 클릭과 호버가 전과 같다. 그린 것을 누르면 골라져 점마다 손잡이가 보이고, 드래그로 통째로 또는 한 점을 옮긴다. 더블클릭하면 색·굵기·선 종류(실선·점선·파선) 팝업이 열리고, Delete나 Backspace로 지운다. 텍스트는 찍으면 입력창이 열리고 더블클릭으로 다시 고친다. 자석(모든 종목에 하나, 앱 설정 `krx_quant/chart_magnet`)을 켜면 찍거나 끄는 점이 아래 봉의 가운데와, 그 봉의 시가·고가·저가·종가 중 가까운 값에 붙는다(하이킨아시여도 원래 봉의 값). 점은 시각과 가격이라 보기를 바꿔도 같은 자리다. 봉 안에서는 그 봉의 장 시간(평일 08:00–20:00) 중 지난 만큼의 자리(일봉은 14:00이 가운데)이고, 봉 사이(밤)는 두 봉의 경계다. 분 보기에서 그날 안의 거래 없는 분은 빈 봉이라(#236) 그 칸에 놓인다. 읽은 봉 밖은 그 사이의 장 시간을 그 보기의 봉 길이로 센 어림이고, 그린 것 때문에 앞의 봉을 더 읽지는 않는다. 그린 것은 종목마다 앱 설정 `krx_quant/chart/<종목코드>/drawings`(JSON 배열, 시각은 KST ISO 8601)에 남는다. 휴지통은 지금 종목의 그린 것을 "그린 것 N개를 지울까요?"로 확인한 뒤 모두 지우고, 그린 것이 없으면 비활성이다. 시간축 없는 모양(#225)에서는 그린 것을 숨기고 `그리기`와 휴지통을 비활성으로 둔다. 페이지가 그리기·고르기·드래그·키를 맡아 봉 위치를 bridge로 화면에 넘기고, 화면이 시각으로 바꿔 저장한 뒤 다시 보낸다. 도구, 저장 형식, 시각과 봉 위치의 변환, 자석은 화면 코드의 순수 함수(`ChartDrawings`, 합성 봉 테스트)이고, 키의 형식과 자세한 동작은 fork의 `custom/README.md`("그리기")에 있다. 툴바의 나머지(일별 수급 지표)는 spec #220과 그 하위 이슈(#226)를 따른다. 지금 만들어지는 봉은 스트림의 `bar` 이벤트(#110)로 1초마다 움직이고(N분 보기는 묶은 마지막 봉, 일·주·월·년 보기는 오늘이 든 봉), 현재가 선도 같이 움직인다. 1분 보기에서는 봉 마감마다 합의의 예측 클래스 아이콘(▲ 상승, ▼ 하락, ● 보합)을 예측을 만든 봉 위에 두고, 결과(✓ 맞음, ✗ 틀림, ? 채점 전·채점 불가)를 붙인다. 순위표에서 모델을 체크하지 않았으면 최종 합의, 체크했으면 **선택 합의**(#159)다. 선택 합의는 체크한 모델 중 그 봉 마감에 예측을 낸(`ok`) 모델의 세 확률을 똑같은 무게로 평균한 것이다(이름순으로 더함). 방향은 가장 큰 확률이고 동률이면 보합, 그다음 상승이다. 같은 방향 수는 각 모델의 가장 큰 확률 방향으로 센다. 하나도 예측하지 않은 봉에는 아이콘이 없다. 오늘의 봉은 모델 결과가 올 때마다 다시 계산한다. 지난 아이콘은 늦게 온 결과까지 넣은 사후 평균이라 그 시각의 신호와 다를 수 있다. 기준 예측은 체크해도 평균·방향별 수·`n/m`에 넣지 않고 호버의 비교 줄로만 보인다(#166). 모델 없이 기준 예측 하나만 체크하면 그 기준의 예측을 아이콘으로 그리고, 기준 예측만 둘 이상이면 아이콘이 없다. 특수 상황이 낀 예측은 흐리게 그린다. 신호였던 봉의 아이콘은 크고 진하다(#106, 합의의 `votes`와 화면의 알림 기준). 선택 합의는 알림 기준(확률, 같은 방향 수. 차트에서는 "체크한 모델 중")을 그대로 쓰고, 그 봉이 특수 상황이거나 같은 봉 마감의 최종 합의에 `blocked`가 있으면 크게 그리지 않는다. `no_members`는 막힘이 아니다. 선택 합의로는 알림을 보내지 않는다. 차트·호버·고정 패널의 ✓/✗는 **봉 마감의 정답** 하나를 따른다: 그 (종목, 봉 마감)에서 채점된 아무 예측의 도달 정답(`outcome.touch`, 5장)이다. 도달 정답이 없는 이전 엔진의 예측은 기준 A로 본다. 1분 보기에서 캔들(그 봉의 세로 구간 어디든, 거래량 칸 등 하단 칸 포함)에 마우스를 올리면 상자가 나온다: 첫 줄 `HH:mm 봉 → HH:mm 목표 · 정답`(채점 전, 채점 불가와 이유, 또는 `정답 상승 (09:32:30 닿음)`·`정답 보합`), 체크한 모델이 있으면 선택 합의 한 줄(방향, 세 확률, 방향별 모델 수, `n/m 모델`, 결과, 신호면 "신호"), 체크한 모델마다 한 줄(이름, 지금 상태(마지막 순위표), 방향, 세 확률, 결과. 그 봉에 예측이 없으면 "예측 없음", `ok`가 아니면 상태 글자), 맨 아래 늘 최종 합의 한 줄(`ok`가 아니면 "합의 대상 없음" 같은 상태 글자). 예측이 하나도 없는 봉은 첫 줄과 "예측 없음"만이다. 마우스를 올린 동안 그 봉의 4분 구간(#167)을 옅게 칠하고, 도달 정답이 기록돼 있으면 위·아래 목표를 그 구간에 가로선으로 긋고 처음 닿은 곳(초 단위 위치)에 점을 찍는다. 끝나지 않은 창은 점선으로 오른쪽 빈칸까지 그린다. 변동폭을 고른 동안(#182)은 상자가 변동폭의 것이다: 첫 줄은 `10:26 봉 → 10:30 목표 · 정답 11틱 · 큼`(실제 변동폭 r과 그 구간), 그 아래 그 봉 마감의 변동폭 예측자(알고리즘, 기준 예측)마다 한 줄(이름, 지금 상태, 가장 큰 구간과 그 확률, `q10~q90 1~6틱`, 정답 구간과 같으면 ✓)이다. 4분 구간에는 정답이 나온 뒤 실제 최고·최저 중간가를 가로선 둘로 긋고 처음 받은 곳에 점을 찍는다. 장벽을 고른 동안(#185)은 상자가 장벽의 것이다: 첫 줄은 `10:26 봉 → 10:30 목표 · 정답 위 먼저 (10:29:28 닿음) · w 6틱`(먼저 닿은 장벽과 그 시각, 둘 다 안 닿았으면 `정답 시간 만료`, 그 봉 마감의 폭 w), 그 아래 그 봉 마감의 장벽 예측자마다 한 줄(이름, 지금 상태, 예측 클래스, 세 확률, 정답 클래스와 같으면 ✓)이다. 4분 구간에는 위 장벽 U(초록)와 아래 장벽 L(빨강)을 가로선으로 긋고, 정답이 나오면 각 장벽에 처음 닿은 곳에 점을 찍는다(U는 매수 1호가가 U 이상이 된 때와 그 매수 1호가, L은 매도 1호가가 L 이하가 된 때와 그 매도 1호가. 둘 다 닿았으면 점도 둘이다). U·L은 정답의 것, 정답 전에는 예측과 함께 온 봉 마감 중간가와 호가단위(예측 항목의 `anchor`, `tick`, #210)로 센 것이다. 4분이 끝나기 전에는 구간처럼 점선이다. 그 값을 주지 않는 옛 엔진(#210 전)이면 정답 전에는 구간만 칠한다. 봉 마감에 이벤트가 몰려 다시 그려져도 상자는 그대로다. 체크한 모델이 있으면 차트 머리줄에 `선택 합의 (3) · 맞음 52% · 늘 보합 61% · ▲ 맞음 40% (52) · ▼ 맞음 45% (60) · 310개 4거래일 · 특수 12개 제외`가 나온다: 보이는 구간(줌·스크롤을 따라 바뀜)에서 4분이 다 지나 채점된 봉 중 선택 합의가 맞은 비율, 같은 봉들에서 "늘 보합"이 맞았을 비율, ▲·▼라고 한 봉 중 맞은 비율과 그 수(#166), 봉 수와 거래일 수(겹치는 창은 독립 표본이 아니다)다. 채점 전·채점 불가 봉은 세지 않고, 특수 상황 봉은 세지 않되 따로 센다. 설명용 성적이고, 정식 판정은 순위표의 거래일 단위 구간이다. WebEngine이 없는 빌드는 "차트를 열 수 없음"만 보인다.

**녹화 실측 (2026-10-12, #7).** 실시간 피드를 처음 하루 통째로 녹화한 날이다(그 전 날짜에는 투자자별 추정 가집계만 있다). 옵션 체결(`H0IOCNT0`)은 이날 만기 지난 월물을 구독해 비어 있었다(#114에서 고침). 그래서 옵션 몫은 아래 수에 없다. 수는 S3에 올라간 그날 파티션의 행이다. 받은 KIS 메시지(WebSocket 프레임)는 `raw` 층에 한 행씩, 메시지를 풀어 낸 레코드는 `events` 층에 한 행씩 있다. 체결 메시지 하나에 체결이 여러 건 들어 오기도 해서 레코드가 메시지보다 많다.
