# 엔진 API v1과 예측·채점 규칙

엔진은 1분봉이 마감될 때마다 종목별로 4분 뒤 통합 중간가의 방향을 예측하고, 4분 뒤 채점한다. 결과는 `state/engine.sqlite3`에 저장하고 HTTP JSON API로 보여준다. Fincept 화면은 이 API만 읽는다.

지금은 기준 예측 3종(#9), 알고리즘 Newton(#10), Gauss(#13), Granger(#15), Markov(#14), Kalman(#25), Shannon(#26), Poisson(#27), Turing(#16, 호가 피처는 #55), 합의 Condorcet(#18)이 예측한다. Kalman, Shannon, Poisson은 사전 검증(#24)을 통과해야 실시간에서 돈다. 화면은 REST로 지금 상태를 읽고, WebSocket 스트림(`/v1/stream`)으로 바뀌는 것을 바로 받는다. 응답 형식은 JSON 스키마 `schemas/engine-api-v1.json`으로 고정한다(아래 "계약").

## 예측

- **예측 시각 t.** 연속매매 중 1분봉이 마감되는 매 분이다. 첫 회차는 개장 1분 뒤(09:01)다. 마지막 회차는 채점 시각(t + 4분)이 아직 연속매매 안에 드는 15:16이다. 연초 첫 거래일과 수능일은 그날 일정에 맞춰 10:01부터다. 휴장일에는 예측하지 않는다.
- **입력.** t 전에 엔진이 받은 데이터만 쓴다. 실시간에서 회차가 늦게 돌아도 같다. 봉 마감 뒤에 받은 이벤트가 오면, 엔진은 그 이벤트를 반영하기 전의 1분봉을 그 봉 마감용으로 따로 둔다. 모든 데이터는 엔진이 받은 시각(`received_at`)으로 줄을 세운다. t와 같은 순간에 받은 데이터는 t 뒤의 것으로 본다. 나중에 t를 돌아볼 때도(예: 4분 뒤 직전 4분 변화) 같다. 그래서 실시간과 재생의 결과가 같고, t 뒤의 데이터를 잘라내도 t의 예측은 바뀌지 않는다.
- **저장.** 기준 예측은 한 봉 마감의 것(모든 종목 × 3종)을 한 번에 저장한다. 알고리즘은 각자 모든 종목을 다 예측한 순간에 저장한다. 저장한 순간이 표시 시각(`displayed_at`)이다.
- **기준 예측 3종.** 모든 알고리즘이 넘어야 하는 기준이다. 셋 다 한 클래스를 확률 1로 예측한다.

| 이름 | 예측 |
|---|---|
| `baseline-flat` | 항상 보합 |
| `baseline-persist` | 직전 4분(t − 4분 → t) 중간가 변화를 채점과 같은 규칙으로 분류해, 그 방향이 이어진다고 본다. 기대수익은 그 변화의 틱 수다. 중간가를 모르면 보합이다. |
| `baseline-random` | 그날 이미 채점된 봉의 클래스 비율(각 클래스에 1을 더한 값)대로 무작위로 뽑는다. 종목과 t로 시드를 정해서, 같은 입력이면 늘 같은 값이 나온다. |

- **알고리즘.** 등록된 알고리즘(지금은 `newton`, `gauss`, `granger`, `markov`, `kalman`, `shannon`, `poisson`, `turing`)이 종목마다 예측한다. `kalman`, `shannon`, `poisson`은 사전 검증을 통과해야 돈다(#24). 규약과 추가 방법은 아래 "알고리즘"에 있다.
  - 알고리즘은 작업 스레드에서 돈다. 그래서 오래 걸려도 녹화를 막지 않는다.
  - 한 봉 마감에 알고리즘 하나가 모든 종목을 예측하는 데 10초(`KRX_ALGORITHM_SECONDS`)를 넘기면, 그 회차는 `status`가 `timed_out`인 빈 예측으로 남고 채점하지 않는다. 그 계산이 끝날 때까지는 다음 회차도 `timed_out`이다.
  - 예외를 던지거나 확률이 분포가 아니면 `error`로 남는다.
  - 알고리즘이 읽는 데이터가 봉 마감에 없으면 그 종목은 예측하지 않고(`NotPredicted`) 이유를 `status`로 남긴다: 호가가 없으면 `no_book`(#25). 확률이 비어 있고 채점하지 않으며 합의에서도 빠진다. 다른 종목은 그대로 예측한다.
  - 알고리즘마다 걸린 시간을 재 둔다. 다음 회차에 예상 시간의 합이 CPU 예산(`KRX_CPU_BUDGET_SECONDS`, 기본 30초)을 넘으면, 늦게 등록된 알고리즘부터 그 회차를 건너뛴다. 순위는 보지 않는다. 건너뛴 기록은 `runs` 테이블에 `cpu_budget`으로 남고, 로그에 경고가 남는다.
  - 알고리즘 하나의 한도는 CPU 예산보다 작아야 한다. 같거나 크면 설정 오류다. 한도를 다 쓴 알고리즘은 예상 시간이 한도로 잡히는데, 그래도 나머지 알고리즘에 예산이 남는다(기본값이면 20초).
  - 장 마감 10분 뒤 일일 점검 때, 그날 `timed_out`인 봉 마감이나 CPU 예산으로 건너뛴 회차가 있으면 텔레그램으로 한 번 알린다(`[알림] <날짜> 예산 때문에 예측이 빠진 알고리즘이 있습니다. 시간 초과(…): <이름> N회. CPU 예산(…)으로 건너뜀: <이름> N회. …`). 보낸 기록은 `runs`에 `budget_report`로 남아서, 점검이 엔진 재시작 뒤 다시 돌아도 또 보내지 않는다. 보내지 못한 알림은 그날 점검이 다시 돌 때(점검이 중간에 실패한 뒤 재시작)만 다시 보내고, 다음 날 점검은 다음 날 것만 센다. 엔진이 꺼져 있어 놓친 날의 점검을 나중에 돌리면 그날 날짜로 보낸다.

  > **바뀜** (2026-10-12, #73): `KRX_ALGORITHM_SECONDS` 기본 30초 → 10초, 한도 < CPU 예산 검사, "텔레그램 알림은 없다" → 하루 한 번 알림. 이유: 한도와 예산이 같아 한 알고리즘이 한도를 다 쓰면 뒤의 알고리즘이 모두 건너뛰어졌고, 운영자가 알 길이 로그뿐이었다(#71).
  - 건너뛸 때마다 그 알고리즘의 예상 시간을 절반으로 줄인다. 그래서 곧 다시 돌려 시간을 새로 잰다. 한 번 건너뛰었다고 계속 빠지지는 않는다.

  > **바뀜** (2026-10-09, #37): 설계(design.md 5장)는 "순위가 낮은 알고리즘부터 건너뛰고, 잦으면 서버를 늘리라고 경고한다"였다 → 늘 늦게 등록된 것부터 건너뛰고, 텔레그램 경고는 없다. 이 문서에 있던 "순위가 생기면 순위가 낮은 쪽부터"는 구현된 적이 없다. 이유 기록 없음.
- **합의(Condorcet, #18).** 봉 마감마다 두 합의를 낸다. 각각 하나의 예측(`algorithm`이 `consensus-fast`, `consensus-final`)으로 저장되고 채점된다(`consensus.py`).
  - 빠른 합의: 알고리즘 계산을 시작하고(봉 마감 직후) 2초 안에 끝난 정식 알고리즘으로 낸다. 엔진이 늦게 돌아도 2초는 기다린다.
  - 최종 합의: 정식 알고리즘이 모두 끝나거나, 실패하거나, 각자의 시간 예산(`KRX_ALGORITHM_SECONDS`, 10초)에 걸리면 바로 낸다. 정식이 아닌 알고리즘은 기다리지 않는다.

    > **바뀜** (2026-10-12, #73): 시간 예산 30초 → 10초. 그래서 최종 합의도 늦어도 계산 시작 +10초쯤 나온다. 이유: 위 시간 예산 메모와 같다(#71).
  - 구성원은 정식(`active`) 알고리즘뿐이다. 수습, 벤치, 은퇴, 복제는 빠진다. 구성원이 없으면 `status`가 `no_members`인 빈 예측으로 남는다. 구성원은 있는데 그때까지 결과가 하나도 없으면(계산 중, 시간 초과, 실패, 그 종목을 예측하지 않음(`no_book`)) `none_finished`다. VI 중인 종목은 `vi`다.
  - 합치는 방법은 선형 결합이다. 세 확률과 기대수익을 구성원 가중치로 평균한다. 그 시점에 결과가 있는 구성원의 가중치만 합이 1이 되게 다시 나눈다.
  - `model_version`은 가중치 버전이다(`condorcet-<계산한 날>`, 계산 전에는 `condorcet-equal`).
- **합의 가중치.** 종목 × 30분 시간대(봉 마감 09:01–09:30은 `09:00`) 칸마다 매일 상태 점검 직후(보통 15:40) 다시 계산한다.
  1. 최근 5일과 20일(예측이 있는 날) 각각에서, 모든 구성원이 예측한 봉 마감에 대해 합의의 로그손실이 가장 작아지는 가중치를 EM으로 구한다. 기준 A(봉 마감 → 4분 뒤)로 본다. 기준 B는 구성원마다 자기 표시 시각에서 채점해서, 같은 봉 마감인데 구성원마다 정답이 다를 수 있기 때문이다. 특수 예측은 뺀다.
  2. 두 기간 모두에서 균등(1/구성원 수)보다 높아야 올라간다. 이때는 둘 중 작은 값을 쓴다. 두 기간 모두 낮으면 둘 중 큰 값을 쓰고, 엇갈리면 균등이다. 꾸준히 낮은 쪽이 내놓은 몫은 꾸준히 높은 쪽에만 비율대로 준다(그런 쪽이 없으면 나머지에 고르게). 최근에만 좋은 알고리즘은 가중치가 오르지 않는다.
  3. 20일의 봉 마감 수 n만큼만 믿고 나머지는 균등 쪽으로 당긴다. 맞춘 가중치에 n / (n + 200), 균등 가중치에 200 / (n + 200)을 준다.
  - 가중치가 없는 칸은 균등하게 친다. 계산 뒤에 정식이 된 알고리즘은 균등한 몫(1/구성원 수)을 받고, 나머지 구성원은 남은 몫을 계산된 비율대로 나눈다.
  - 빠른 합의 시각은 테스트에서 줄일 수 있다(`Timing`). 재생에서는 알고리즘이 도는 동안 재생 시계가 멈춰 있어서, "2초 안에 끝난" 여부는 실제로 걸린 시간으로 정한다. 시간 예산과 같다. 같은 이유로 재생에서는 빠른 합의와 최종 합의의 `displayed_at`이 같다.
  - 합의도 순위표에 다른 알고리즘처럼 나오고, 운 보정(FDR)의 검정 묶음에 들어간다.

  > **바뀜** (2026-10-10, #42): 사용자와 합의한 설계에서 바뀐 점이다. PR #42 본문의 "기준 B"는 머지 전에 기준 A로 바뀌었다.
  > - 빠른 합의: "봉 마감 +2초" → "계산 시작부터 2초". 이유: 엔진이 이미 2초 늦게 돌면(또는 재생의 표시 지연) 빠른 합의가 늘 빈다.
  > - 기간 결합: "두 기간 가중치 중 작은 값, 그다음 합이 1이 되게 나누기" → 위 2번의 꾸준함 규칙. 이유: 구성원이 둘이면 작은 값을 다시 나누는 과정이 최근에만 좋은 알고리즘에 가중치를 몰아줬다.
  > - 맞추는 기준: 기준 B → 기준 A. 이유: 기준 B는 구성원마다 자기 표시 시각에서 채점해서, 한 봉 마감에 한 구성원의 상승 확률과 다른 구성원의 하락 확률을 섞을 수 있다(dcd1837).
  > - 계산 뒤에 정식이 된 구성원: 균등보다 작은 몫 → 균등한 몫(1/구성원 수). 이유 기록 없음.
  > - 저장: `consensus_weights` 한 테이블(`computed_at` 포함, 023e4ce) → `consensus_fits`와 `consensus_weights`(57ef592). 이유 기록 없음. 같은 커밋에서 가중치 계산을 상태 점검 기록(`runs`의 `review`)보다 먼저 하게 했다. 그래서 계산이 실패하면 재시작 뒤 다시 한다.
  > - 구성원은 있는데 결과가 없으면 `no_members`가 아니라 `none_finished`로 남긴다(57ef592). 실패한 계산도 결과 없음으로 친다. 이유 기록 없음.

## 기준가 (통합 중간가)

- KRX와 NXT를 합친 최우선 매수호가와 최우선 매도호가의 평균이다. 통합 호가(`H0UNASP0`), 통합 체결(`H0UNCNT0`)에 실린 최우선 호가, 통합 호가가 REST로 바뀌었을 때의 호가 스냅샷(`FHKST01010200`)을 쓴다.
- NXT가 열리기 전인 개장 후 30초(보통 09:00:00–09:00:30)에는 KRX 호가만 쓴다. KRX 호가는 KRX 전용 체결(`H0STCNT0`)에 실린 최우선 호가다.
- 최우선 매도호가와 매수호가가 같은 호가(locked)는 정상이다. 그 가격이 중간가다. 매도호가가 매수호가보다 낮은 호가(crossed)와 한쪽이 빈 호가는 쓰지 않는다.
- 어떤 시각의 중간가는 그 시각 바로 전까지 받은 마지막 호가로 정한다. 60초 넘게 새 호가가 없으면 중간가를 모르는 것으로 본다. 통합 호가 피드의 지연 판정 기준과 같다.
- 연속매매 밖(개장 전, 종가 동시호가, 장 마감 후)에는 중간가가 없다.

## 채점

- **보합 범위 k.** t의 중간가에서 왕복 거래비용(매도 거래세 0.20% + 수수료율 × 2)을 덮는 가장 작은 틱 수다. 틱은 KRX 호가단위표(2023-01-25부터 코스피·코스닥 공통)를 따른다. 수수료율은 `KRX_FEE_PERCENT`(편도, %, 기본 0.015)다.
  - 예: 81,200원은 비용 186.76원, 호가단위 100원이라 k = 2다.
- **클래스.** 변화가 k틱 이상이면 상승, −k틱 이하면 하락, 그 사이는 보합이다.
- **두 기준.** (A) 봉 마감 기준은 t의 중간가 → t + 4분 중간가다. (B) 표시 기준은 예측이 저장되어 API에 보인 시각(`displayed_at`)의 중간가 → t + 4분 중간가다.
- **채점 불가.** 필요한 중간가를 모르면 그 기준은 채점하지 않고, `unscorable`에 빠진 중간가를 적는다. 예: `missing mid: target`. 예측 자체는 그대로 남는다.
- 엔진이 재시작되어도 채점 대기 중인 예측은 이어서 채점한다. 엔진이 꺼져 있던 동안의 회차는 예측이 없다.
- **특수 상황(#12).** `special.py`가 판정한다.
  - **VI.** 수집기가 종목마다 VI 현황(`FHPST01390000`)을 5초마다 조회한다(`KRX_VI_POLL_SECONDS`, 시가 동시호가부터 장 마감까지). 응답에는 그날의 VI마다 발동 시각과 해제 시각이 있다. VI가 걸려 있는 동안(`vi_cls_code`가 `N`이 아니거나 해제 시각이 없을 때)은 적어도 3분 동안 이어진다고 본다(단일가 2분 + 임의 연장 최대 30초에 여유를 둔 값).
  - **VI 중에는 예측하지 않는다.** t에 VI 중인 종목은 모든 예측자(기준 예측과 알고리즘)가 `status` `vi`인 빈 예측으로 남고 채점하지 않는다. t 전에 받은 VI 현황으로 판정한다.
  - **서킷브레이커(코스피).** 녹화하는 코스피 지수(`H0UPCNT0` `0001`, REST 대체 포함)의 전일 대비 등락률로 거래소 규칙대로 판정한다. 8% 이상 하락이 1분 이어지면 1단계, 15% 이상이면서 1단계 때보다 1%p 더 떨어진 상태가 1분 이어지면 2단계, 20%(2단계보다 1%p 더)면 3단계다. 각 단계는 하루 한 번이다. 1·2단계는 발동 시각부터 30분(매매 정지 20분 + 단일가 10분), 3단계는 그날 끝까지다.
  - **사이드카(코스피).** KOSPI200 최근월물 선물(`H0IFCNT0`, REST 대체 포함)의 전일 대비 등락률이 ±5% 이상인 상태가 1분 이어지면 발동 시각부터 5분이다. 하루 한 번이다.
  - **시간 제한.** 개장 후 5분 동안은 둘 다 발동하지 않는다. 장 종료 40분 전(보통 14:50)부터는 사이드카와 서킷브레이커 1·2단계가 발동하지 않는다. 3단계는 장 끝까지 발동한다. 1분 지속은 이 시간 안에서만 센다. 그래서 선물이 08:45부터 이미 5% 넘게 벌어진 날은 09:05부터 1분을 세어 09:06에 사이드카로 판정한다. 이 시간 제한은 뉴스와 증권사 설명 기준이다. 유가증권시장 업무규정 원문은 확인하지 못했다 ⚠.

    > **바뀜** (2026-10-09, #40): 처음 버전(d56b0e7)은 거래소의 시간 제한을 일부러 넣지 않았다. "시장이 그만큼 움직였으면 정지가 없어도 특수로 보는 것이 맞다"고 봤다 → 위의 시간 제한을 따른다. 이유: 08:45부터 벌어진 선물 갭이 주식시장이 열기도 전에 그날 한 번뿐인 사이드카를 써 버렸다(bec0265).
  - 서킷브레이커와 사이드카는 KIS 신호를 읽지 않고 녹화한 지수와 선물로 판정한다. 그래서 재생에서도 같게 판정한다. 코스닥 서킷브레이커·사이드카는 아직 보지 않는다(지금 종목은 모두 코스피다).
  - 판정 상태(1분 지속, 발동한 단계)는 메모리에만 둔다. 엔진이 장중에 재시작하면 그 뒤에 받은 것으로 다시 판정한다. 1분봉과 같다.
  - 특수 표시는 한 번 붙으면 지우지 않는다. 해제를 몰라 3분으로 본 VI가 실제로 더 일찍 끝났어도 그 사이 표시한 예측은 특수로 남는다. 보수적인 쪽을 골랐다.
  - **특수 표시(`special`).** t → t + 4분 구간이 VI(그 종목), 서킷브레이커나 사이드카(모든 종목) 구간과 겹치면 `true`다. 예측을 저장할 때 이미 알던 구간으로 표시하고, 나중에 알게 된 구간(조회 실패로 늦게 받은 VI 등)도 받는 즉시 겹치는 예측을 채점 여부와 상관없이 표시한다. 기본 통계에서는 뺀다.

## 통계와 순위표

채점된 예측으로 성적을 낸다(`stats.py`). 한 기준(A 또는 B)으로 본다. 그 기준의 클래스가 정해진 예측만 센다. 예측 클래스는 세 확률 중 가장 큰 쪽이다. 동률이면 보합, 그다음 상승을 고른다.

| 지표 | 정의 | 신뢰구간 |
|---|---|---|
| 3클래스 정답률 (`accuracy`) | 예측 클래스가 실제와 같은 비율 | Wilson 95% |
| 방향 정밀도 (`precision`) | 상승·하락을 예측한 것 중 맞은 비율 | Wilson 95% |
| 커버리지 (`coverage`) | 상승·하락을 예측한 비율 | Wilson 95% |
| Brier 점수 (`brier`) | 세 클래스의 (확률 − 실제 0/1)² 합의 평균. 0이 완벽, 2는 확신하고 틀림 | 정규근사 95% |
| 중간가 손익(연구용, `pnl`) | 상승·하락 예측을 그 방향으로 시작 중간가에 사고(팔고) 목표 중간가에 판(산) 틱 수에서 왕복 비용(매도세 + 수수료 × 2, 틱)을 뺀 값. 거래 수, 합계, 거래당 평균. 아래 "중간가 손익" | 거래당 평균에 정규근사 95% |
| 보정 곡선 (`calibration`, `calibration_by_class`) | 확률을 0.1 간격 10구간으로 나눠, 구간별 평균 확률과 그 클래스가 실제로 일어난 비율. `calibration`은 세 클래스를 합친 것, `calibration_by_class`는 상승·보합·하락 각각이다. 방향별 보정은 클래스별 곡선을 본다 | 구간마다 Wilson 95% |
| lift | 같은 종목·봉 마감의 기준 예측과 짝지어, 정답(1/0) 차이의 평균 | 정규근사 95%, 한쪽 p값(설명용). 거래일 단위(`by_day`): t분포 95%, 한쪽 p값 |

- **lift**: 기준 3종(`baseline-flat`, `baseline-persist`, `baseline-random`) 각각에 대해 낸다. "항상 보합"을 이기려면 보합도 맞히고 방향도 맞혀야 한다. 확률을 분산해서 생기는 이득은 들어가지 않는다.
  - 짝이 30쌍보다 적으면 검정하지 않는다(`p`가 `null`). 정규근사가 너무 거칠기 때문이다.
  - 짝 단위 구간과 p값은 매분 예측을 서로 독립인 표본으로 센다. 그러나 4분 정답은 1분마다 겹치고(한 봉 마감의 정답 구간이 다음 세 봉 마감의 것과 겹친다), 종목들은 같은 시장 움직임을 함께 탄다. 그래서 이 구간은 실제보다 좁다. 설명용이고 상태 판정에는 쓰지 않는다.
  - **거래일 단위(`by_day`)**: 같은 lift를 거래일마다 나눠, 하루의 짝 차이 평균을 값 하나로 본다. 날들의 평균에 t분포(자유도 = 날 수 − 1) 95% 구간과 한쪽 p값을 쓴다. 짝이 없는 날은 세지 않고, 날마다 같은 무게다. 날마다 값이 모두 같으면 퍼짐이 없어 구간이 그 값 하나다. `n`은 날 수다. 날이 2일보다 적으면 `null`이다(`today`는 늘 `null`). 상태 판정(수습 → 정식, 벤치 → 정식)은 이 하한으로 한다. 합성 실험(실제 lift 0, 10거래일 × 375분 × 3종목)에서 짝 단위 하한이 0을 넘은 비율은 13–19%였고, 거래일 단위는 2.5%로 명목 수준이었다(#78).
  - 기준 B에서는 예측마다 자기 표시 시각의 중간가로 채점한다. 그래서 같은 봉 마감이라도 늦게 표시된 예측은 다른 출발점에서 채점된다. 화면에 늦게 뜬 신호는 그만큼 불리하다는 뜻이고, 의도한 것이다.
- **중간가 손익(`pnl`, 연구용)**: 따라 했을 때의 손익이 아니다.
  - 방향(상승·하락)을 낸 모든 예측을 매분 한 번씩 거래한 것으로 친다. 손익을 계산한 거래 집합은 텔레그램 신호 알림의 집합과 다르다.
  - 하락은 공매도로 계산한다.
  - 시작과 끝을 모두 중간가로 잰다. 스프레드, 호가 잔량, 체결은 반영하지 않는다. 1틱 스프레드만 내도 거래당 1틱을 더 잃는다. 예: 81,200원, k = 2틱(200원) 상승이 중간가 기준 주당 +13.24원이면, 매도 호가(ask)에 사고 매수 호가(bid)에 팔 때는 −86.76원이다(#78).
  - 정답 문턱 k는 매도세와 수수료만 덮는다. 스프레드는 덮지 않는다. 그래서 "상승" 정답이 곧 이익 나는 거래는 아니다.
  - 종목별 봉 마감 스프레드 실측(2026-10-12·13, `krx-quant diagnose`, #90): 봉 마감마다 그 전 1분 안에 받은 마지막 통합 호가(`H0UNASP0`)의 스프레드다. 종목마다 이틀 동안 봉 마감 752번(하루 376번)이다. 005930과 000660은 늘 1틱이었다. 009150은 p90까지 1틱, p99와 최대가 2틱이었다. 그래서 세 종목 모두 호가에 사고팔면 거래당 1틱쯤을 더 잃는다고 보면 된다.

  > **바뀜** (2026-10-13, #117): 이름 "가상손익" → "중간가 손익(연구용)", 위 설명을 더했다. API 필드 `pnl`의 이름과 계산은 그대로다. 이유: 따라 했을 때의 손익으로 읽히기 쉬웠다(#78, #81).
- **운 보정**: 순위 후보(아래)의 lift 검정(알고리즘 × 기준)만 모아 Benjamini–Hochberg로 보정한 q값을 낸다. lift가 0보다 크고 q ≤ 0.05이면 `significant`가 `true`다. 함께 검정하지 않은 lift(후보가 아니거나, 상세 통계의 분해 항목)는 `q`와 `significant`가 `null`이다.
- **순위**: 세 lift 중 가장 작은 것의 신뢰구간 하한(`lift.low`)으로 정렬한다. 즉 "모든 기준보다 낫다"를 얼마나 확실히 말할 수 있는지로 줄을 세운다. 짝 단위 하한이라 하루 안에서도 순위를 매길 수 있지만, 위처럼 실제보다 확실해 보인다. 상태 판정에 쓰는 것은 거래일 단위의 가장 약한 하한(`lift.day_low`)이다. 후보는 채점된 예측도, 기준 3종과의 짝도 각각 `KRX_MIN_SAMPLE`(기본 200) 이상인 알고리즘이다. 나머지는 `unranked`에 둔다. 등록됐지만 아직 채점된 예측이 없는 알고리즘도 `unranked`에 나온다.
- **상태와 순위**: 순위는 상태(수습, 벤치 등)를 보지 않는다. 수습 알고리즘도 조건을 채우면 순위에 오른다. 항목의 `status`로 상태를 본다.

  > **바뀜** (2026-10-09, #38): 운 보정 묶음이 "한 순위표 안의 모든 lift 검정"에서 "순위 후보의 lift 검정만"으로 줄었다. 순위 후보에는 채점 수뿐 아니라 기준 3종과의 짝 수도 `KRX_MIN_SAMPLE` 이상이어야 한다는 조건이 붙었다. 함께 검정하지 않은 lift의 `q`·`significant`는 `false`가 아니라 `null`이다(209ede2). 이유: `null`은 "오해를 부르는 `false` 대신"이다. 묶음을 줄인 이유는 기록 없음.
- **보정 곡선**: 합친 곡선은 방향별 오차를 숨긴다. 상승만 일어난 날 세 확률을 모두 1/3로 낸 예측은 합친 곡선에서 0.3–0.4 구간의 실제 비율이 1/3이라 완벽해 보인다. 클래스별 곡선에서는 상승이 1.0, 보합·하락이 0이다.

  > **바뀜** (2026-10-13, #119): 보정 곡선은 세 클래스를 합친 것 하나였다 → 클래스별 곡선(`calibration_by_class`)도 낸다. 합친 곡선은 그대로 둔다. 이유: 합친 곡선이 방향별 보정 오차를 숨겼다(#78, #83).
- **제외 건수(`excluded`)**: 같은 질의(기간, 종목, 채점 기준)에서 통계에 들지 않았거나 따로 센 예측 수다. 순위표 항목(기준 예측 포함)과 상세 통계의 `overall`에 붙는다.
  - `special`: 그 기준으로 채점된 예측 중 4분 구간에 VI·서킷브레이커·사이드카가 낀 것. `special=exclude`(기본)면 통계에서 뺀 수이고, `special=include`면 통계에 넣은 수다.
  - `unscorable`: 예측은 했지만 그 기준으로 채점하지 못한 것(필요한 중간가를 모름). 채점을 기다리는 예측은 세지 않는다.
  - `status`: 예측하지 않은 회차의 상태별 수(`vi`, `no_book`, `timed_out`, `error`, 합의의 `no_members`, `none_finished`). 없는 상태는 오지 않는다.

  > **바뀜** (2026-10-13, #119): 무엇이 빠졌는지 응답에 없었다 → `excluded`. 이유: 특수 상황, 채점 불가, 예측하지 않은 회차가 몇 건인지 알 수 없었다(#78, #83).
- **신뢰구간이 없는 경우**: 값이 하나뿐인 평균(예: 거래 1건의 손익)은 `low`와 `high`가 `null`이다.
- **계산**: 통계는 이벤트 루프 밖의 작업 스레드에서 DB를 읽고 계산한다. 읽기는 읽기 전용 연결을 따로 써서, 엔진이 쓰는 동안에도 녹화와 예측을 붙잡지 않는다. 같은 질문의 결과는 새 예측이나 채점이 저장될 때까지 다시 계산하지 않고 그대로 준다.
- **기간**: `today`는 엔진 시계의 오늘이다. `5d`·`20d`는 예측이 있는 최근 5일·20일이다.
- **특수 예측**: 4분 구간에 VI·서킷브레이커·사이드카가 낀 예측(`special`, 위 "채점")은 기본으로 뺀다. `special=include`로 넣을 수 있다.

| `outcomes` | `prediction_id`, `target_at`(t + 4분), `mid_close`(A), `mid_display`(B), `mid_target`, `flat_ticks`(k), `class_a`, `class_b`(`up`/`flat`/`down`), `special`, `unscorable`, `scored_at`(채점 전에는 비어 있음) |
| `touches` | `symbol`, `bar_close`, `target_version`(지금 2), `class`(`up`/`flat`/`down`, 채점할 수 없으면 비어 있음), `unscorable`(`missing mid`, `rest quotes`, `silent quotes`, `restarted`), `path`(JSON: 아래 `touch`의 경로 필드), `scored_at`. 봉 마감의 도달 정답(#160, #167). 예측이 아니라 (종목, 봉 마감)마다 하나고, 예측하지 않은 봉 마감(VI 등)에도 있다. `blocks`처럼 따로 둔 표라 옛 엔진도 DB를 연다. 이미 있는 봉 마감은 덮어쓰지 않는다 |
| `runs` | `id`, `kind`(`cpu_budget`: CPU 예산으로 건너뜀, `review`: 일일 상태 점검, `retire_candidate`: 은퇴 후보 알림, `budget_report`: 그날 예산 때문에 빠진 예측을 알림(#71), `no_regime`: 그날 매크로 국면이 없거나 엔진이 모르는 이름이어서 기본 전이행렬로 돈 날, 첫 봉 마감에 하루 한 번(`detail`에 `(unknown: <이름>)`), `start`: 수집기가 엔진을 시작함(`detail`은 JSON: `commit`, `fee_rate`, `signal_rule`(`min_probability`, `min_agree`, 끄면 `null`), `algorithm_seconds`, `cpu_budget_seconds`. 성적을 코드와 설정별로 가르는 근거, #85), `signal_sent`: 보낸 텔레그램 신호, `signal_blocked`: 막힌 텔레그램 신호(둘 다 판정할 때마다 하나씩, `detail`은 JSON, 아래 "텔레그램 신호 알림", #80)), `at`, `algorithm`, `detail` |
| `statuses` | `id`, `algorithm`, `at`, `previous`, `status`, `reason`: 알고리즘 상태 이력(#17) |
| `consensus_fits` | `version`, `computed_at`: 합의 가중치를 계산한 기록(#18). 엔진은 시작할 때 마지막 버전을 읽는다. |
| `consensus_weights` | `version`, `symbol`, `slot`, `algorithm`, `weight`: 그 버전의 칸별 가중치 |

시각은 KST ISO 8601 문자열이다. 스키마 버전은 `PRAGMA user_version`에 있다(지금 4). 엔진이 시작할 때 예전 버전의 DB를 데이터를 지키며 올린다. 더 새 버전의 DB는 거부하고 시작하지 않는다(`... was written by a newer engine (schema N)`). 그래서 스키마를 올린 엔진을 배포한 뒤에는 옛 커밋으로 되돌려도 엔진이 뜨지 않는다([operations.md](operations.md#4-업데이트-배포) 4장).

## API

서버에서는 Tailscale 주소의 8080 포트로만 열린다. 맥과 윈도우에서 `http://krx-quant:8080/v1/...`로 읽는다.

- 시각은 KST ISO 8601 문자열이다(예: `2026-10-12T09:31:00+09:00`).
- 응답은 UTF-8 JSON이다(`Content-Type: application/json; charset=utf-8`). 사람이 읽기 쉽게 두 칸 들여쓰고, 한글을 `\u` 이스케이프 없이 그대로 보낸다.
- 오류는 `{"error": "..."}`다. 모르는 종목은 404, 잘못된 `limit`은 400이다.

### 계약 (JSON 스키마, #19)

- `schemas/engine-api-v1.json`이 모든 `/v1` 응답의 형식이다(JSON Schema 2020-12). 엔드포인트마다 `$defs`에 정의가 하나씩 있다: `status`, `symbols`, `latest`, `predictions`, `bars`, `algorithms`, `algorithm_detail`, `leaderboard`, `algorithm_stats`, `consensus`, `macro`, `calendar`, 오류는 `error`. 스트림의 메시지는 `event`(종류마다 `prediction_event` 등)다.
- 스키마에 없는 필드는 계약 위반이다(모든 객체가 닫혀 있다). 그래서 필드를 더하거나 바꾸면 스키마도 같이 고친다. 시각은 `+09:00`이 붙은 ISO 8601이어야 한다.
- 계약 테스트(`tests/test_api_contract.py`)가 세 모드의 엔진에 모든 엔드포인트, 질의 변형, 오류 응답을 물어 스키마로 검사한다. 빈 재생 엔진(값이 `null`인 경우), 데모 엔진(필드가 찬 경우), 가짜 KIS 위의 실시간 수집기다. 라우트마다 스키마 정의가 있는지도 확인한다(`tests/api_schema.py`의 `ROUTES`). 그래서 엔드포인트를 더하면 `ROUTES`와 스키마에 함께 넣어야 테스트를 지난다.
- 스트림 테스트(`tests/test_api_stream.py`)는 받은 메시지마다 `event` 정의로 검사한다. 실시간 수집기의 계약 테스트도 스트림을 함께 검사한다.
- 화면은 이 스키마와 데모 엔진(`krx-quant demo-engine`)으로 만든다. 데모 엔진도 같은 계약 테스트를 지난다.

### `GET /v1/symbols`

예측하는 종목과 지금의 기준가다.

```json
{"symbols": [{"symbol": "005930", "mid": 81250.0, "tick": 100, "flat_ticks": 2}]}
```

중간가를 모르면 `mid`, `tick`, `flat_ticks`가 `null`이다.

### `GET /v1/symbols/{symbol}/latest`

종목의 가장 최근 봉 마감에 나온 예측들이다.

```json
{
  "symbol": "005930",
  "bar_close": "2026-10-12T09:31:00+09:00",
  "predictions": [
    {
      "algorithm": "baseline-flat",
      "model_version": "v1",
      "bar_close": "2026-10-12T09:31:00+09:00",
      "displayed_at": "2026-10-12T09:31:00.004120+09:00",
      "target_at": "2026-10-12T09:35:00+09:00",
      "status": "ok",
      "blocked": null,
      "votes": null,
      "pooled": null,
      "p_up": 0.0,
      "p_flat": 1.0,
      "p_down": 0.0,
      "expected_ticks": 0.0,
      "outcome": null
    }
  ]
}
```

`outcome`은 채점 전에는 `null`이고, 채점 뒤에는 다음과 같다. `status`가 `ok`가 아닌 예측은 확률, 기대수익, `target_at`, `outcome`이 모두 `null`이다. 채점하지 않기 때문이다. 합의 예측(`consensus-fast`, `consensus-final`)도 같은 목록에 다른 예측처럼 온다. 합의 예측의 `votes`는 그 합의에 들어간 정식 알고리즘을 각자의 방향(가장 큰 확률, 동률이면 보합, 그다음 상승. 채점과 같다)으로 센 것이다: `{"up": 2, "flat": 1, "down": 0}`(#106). 다른 예측, 구성원이 없거나 아무도 끝내지 못한 합의, 이 필드가 생기기 전에 만든 합의는 `null`이다. 스트림의 `consensus` 이벤트에도 같은 항목으로 온다. `pooled`는 그 합의에 확률을 보탠 정식 알고리즘 이름이다(등록 순서, #107). 화면의 "합의 포함 여부"는 이것으로 정한다. `null`인 경우는 `votes`와 같다.

```json
{
  "mid_close": 81250.0,
  "mid_display": 81250.0,
  "mid_target": 81550.0,
  "flat_ticks": 2,
  "class_a": "up",
  "class_b": "up",
  "special": false,
  "unscorable": null,
  "scored_at": "2026-10-12T09:35:00.003000+09:00",
  "touch": {
    "target_version": 2, "class": "up", "unscorable": null,
    "anchor": 81250.0, "tick": 100, "k": 2, "upper": 81450.0, "lower": 81050.0,
    "bid_start": 81200.0, "ask_start": 81300.0, "bid_end": 81200.0, "ask_end": 81300.0,
    "upper_at": "2026-10-12T09:32:30+09:00", "upper_price": 81500.0, "upper_dwell": 1.5, "upper_size": 1200.0,
    "lower_at": null, "lower_price": null, "lower_dwell": null, "lower_size": null,
    "max_bid": 81500.0, "max_bid_at": "2026-10-12T09:32:30+09:00",
    "min_ask": 81300.0, "min_ask_at": "2026-10-12T09:31:00.100000+09:00",
    "trade_high": 81500.0, "trade_low": 81200.0
  }
}
```

`touch`는 그 봉 마감의 도달 정답이다(#160, #167, 기록만). 그 봉 마감의 모든 예측이 같은 것을 가진다. 이 필드가 생기기 전에 채점된 예측은 `null`이다.

- `class`: 4분 안에(받은 시각 기준) 통합 최우선 매수호가가 `upper`(= `anchor` + `k`·`tick`) 이상이 된 적이 있으면 `up`, 아니고 최우선 매도호가가 `lower` 이하가 된 적이 있으면 `down`, 아니면 `flat`. 채점할 수 없으면 `null`이고 `unscorable`이 이유다.
- `anchor`: 봉 마감의 통합 중간가(기준 가격 규칙). `bid_start`·`ask_start`: 봉 마감 전에 받은 마지막 통합 1호가. `bid_end`·`ask_end`: 4분 안에 받은 마지막 1호가.
- `upper_at`·`upper_price`: 위 목표에 처음 닿은 받은 시각과 그때 매수호가. `upper_dwell`: 처음 닿은 뒤 매수호가가 목표 아래로 내려갈 때까지의 초(내려가지 않으면 4분 끝까지). `upper_size`: 그때 매수 1호가 잔량(통합 호가 피드에서만, 체결에 실린 호가면 `null`). `lower_*`는 아래 목표의 같은 값(매도호가 기준).
- `max_bid`·`min_ask`: 4분 안의 최고 매수호가와 최저 매도호가, 그 시각. `trade_high`·`trade_low`: 4분 안의 통합 체결 고가·저가(체결가 기준 정답과 견주는 진단용).
- 아직 학습, 상태 판정, 합의, 통계, 신호, 화면의 ✓/✗는 `class_a`·`class_b`로 한다. 전환은 #170에서 한다.

### `GET /v1/symbols/{symbol}/predictions?limit=N&algorithm=A&before=T`, `?bar_close=T`

최근 N개 봉 마감의 예측과 채점 결과다. 응답은 `{"symbol": "005930", "predictions": [...]}`이다(`latest`와 달리 맨 위에 `bar_close`가 없다). `predictions`는 최신 봉 마감부터 오고, 항목 형식은 `latest`의 `predictions` 항목과 같다.

`bar_close`(ISO 8601 시각, 오프셋 포함. 예: `2026-10-12T09:31:00+09:00`, URL에서는 `+`를 `%2B`로)를 주면 그 봉 마감의 모든 예측(알고리즘, 기준 예측, 빠른·최종 합의와 채점 결과)만 온다(#107). 이때 `limit`은 쓰지 않고, `algorithm`을 함께 주면 그 알고리즘만 온다. 그 봉 마감에 예측이 없으면 빈 목록이다. 오프셋이 없거나 시각이 아니면 400이다.
- `limit`: 1–1000, 기본 100. 예측 개수가 아니라 봉 마감 개수다.
- `algorithm`: 주면 그 알고리즘만 온다.
- `before`: 주면 그 시각보다 앞선 봉 마감만 온다(ISO 8601, 오프셋 포함. 날을 넘는다, #108). 화면은 차트를 지난 날로 스크롤할 때 `algorithm=consensus-final&before=<가장 오래된 봉>`으로 그 봉들의 아이콘을 읽는다. 오프셋이 없거나 시각이 아니면 400이다.

### `GET /v1/symbols/{symbol}/bars`, `?before=T&limit=N`

인자가 없으면 엔진이 통합 체결로 만든 오늘의 1분봉이다. 끝난 봉만 오래된 것부터 온다. 봉 시각은 체결 시각(거래소 시각) 기준 그 분의 시작이다. 늦게 도착한 체결도 체결 시각의 봉에 들어간다. 엔진이 재시작하면 그 전의 봉은 없다.

```json
{"symbol": "005930", "bars": [{"start": "2026-10-12T09:30:00+09:00", "open": 81000, "high": 81400, "low": 81000, "close": 81100, "volume": 19, "trades": 4}]}
```

`before`나 `limit`을 주면(#108) `before`보다 앞서 시작한 봉을 날을 넘어 최대 `limit`개, 오래된 것부터 준다. 차트를 왼쪽으로 스크롤해 지난 날을 볼 때 쓴다.

- `before`: ISO 8601 시각, 오프셋 포함(URL에서는 `+`를 `%2B`로). 없으면 지금이다. 오프셋이 없거나 시각이 아니면 400이다.
- `limit`: 1–2000, 기본 400. 거래일 하루는 1분봉 최대 720개(08:00–20:00)다. 범위 밖이면 400이다.
- 지난 날의 봉은 백필이 저장한 날짜별 1분봉 파일(`bars` 계층, [events.md](events.md#bars-1분봉-rest-백필))에서 읽는다. 이 봉은 체결 수를 모르므로 `trades`가 `null`이다. 파일이 없는 날(백필 전, 휴장일)은 건너뛴다.
- 오늘은 엔진 메모리의 봉이다. 그날 파일이 생기면(20:30 백필) 오늘도 파일에서 읽는다. 그래서 장중 재시작으로 메모리에 빠진 오늘 봉은 20:30 백필 뒤에 채워진다. 그 전에는 비어 있고, 고치지 않는다.
- 데이터 디렉터리가 없는 재생 엔진은 오늘 봉만 준다.

> **바뀜** (2026-10-13, #108): 오늘의 1분봉만 줬다 → `before`·`limit`으로 지난 날의 봉도 준다(백필 파일). 이유: 차트를 지난 날로 스크롤한다(#100).

### `GET /v1/symbols/{symbol}/candles?period=day|week|month|year&before=T&limit=N`

서버에 저장한 일·주·월·년봉(#111, #112)을 `before`보다 앞서 시작한 것만 최대 `limit`개, 오래된 것부터 준다. 차트의 "일·주·월·년" 보기가 처음에 읽고, 왼쪽 끝에 닿으면 가장 오래된 봉의 날로 `before`를 줘서 더 읽는다.

```json
{"symbol": "005930", "period": "day", "venue": "UN", "candles": [{"date": "2026-10-08", "open": 80900, "high": 81700, "low": 80500, "close": 81250, "volume": 12873000}]}
```

- `period`: `day`, `week`, `month`, `year`. 없거나 다른 값이면 400이다.
- `date`는 봉의 기간이 시작하는 날(KST)이다: 일봉은 그날, 주봉은 그 주의 월요일, 월봉은 1일, 년봉은 1월 1일. KIS가 어느 날로 붙였든 이렇게 맞춘다.
- `before`: ISO 8601 시각, 오프셋 포함. 없으면 지금이다. 일봉은 그날 00:00 KST에 시작한 것으로 본다. 오프셋이 없거나 시각이 아니면 400이다.
- `limit`: 1–2000, 기본 400. 범위 밖이면 400이다.
- 오늘이 든 봉은 주지 않는다: 오늘의 일봉, 이번 주·달·해의 봉. 20:30 뒤 저장된 뒤에도 그렇다. 화면이 오늘의 1분봉과 실시간 봉, 그리고 이번 기간의 지난 일봉으로 만든다.
- 가격은 수정주가다. `venue`는 봉이 온 시장이다: `UN`(통합 KRX+NXT)이면 화면은 오늘 봉을 그날의 모든 1분봉으로, `KRX`면 09:00–15:30 봉으로 만든다. 저장된 봉이 없으면 `venue`는 `null`, `candles`는 빈 목록이다.
- 파일은 [events.md](events.md#candles-일주월년봉-rest-111-112)의 `candles` 계층이다. 데이터 디렉터리가 없는 재생 엔진은 빈 목록을 준다. 데모 엔진은 종목마다 10-08까지 만든 일봉 500개와, 그 일봉을 묶은 끝난 주·월·년봉을 준다.

### `GET /v1/algorithms/{name}`

등록된 알고리즘 하나다(#19). `/v1/algorithms` 항목과 같고, 서버에 설치된 모델 이력 `model_history`가 붙는다. 등록된 알고리즘이 아닌 이름(기준 예측, 합의 포함)은 404다. 성적은 `/v1/algorithms/{name}/stats`에 있다.

```json
{
  "name": "newton",
  "card": {"scientist": "Isaac Newton", "character": "추세 추종"},
  "model": {"version": "newton-default", "params": {"damping": 0.5, "threshold": 1.0}, "trained": null, "trained_until": null},
  "status": {"status": "probation", "since": "2026-10-12T08:00:00+09:00", "history": []},
  "model_history": [
    {"at": "2026-10-13T08:00:00+09:00", "version": "newton-20261012-abc123", "why": "promotion 2026-10-12"},
    {"at": "2026-10-13T09:10:00+09:00", "version": null, "why": "rollback from newton-20261012-abc123"}
  ]
}
```

- `model_history`: `state/models/history.json`(#45)에서 그 알고리즘의 항목이다. 오래된 것부터 온다. `why`는 `fit`, `promotion <밤 날짜>`, `rollback from <버전>`, `installed before`(이력이 생기기 전에 깔려 있던 모델)다. `version`이 `null`이면 기본 모델로 돌아간 것이다. 한 번도 설치하지 않았으면 빈 목록이다. 재생에는 서버 상태가 없어서 늘 빈 목록이다. 데모 엔진은 Newton에 가상 이력(학습 설치, 롤백)을 보인다.
- `model`은 엔진이 지금 돌리는 모델이다. 설치나 롤백 직후 1분 안에는 `model_history`의 마지막과 다를 수 있다(엔진이 모델 파일을 30초마다 본다).

### `GET /v1/leaderboard?symbol=&period=&basis=&special=`

순위표다.
- `symbol`: 종목 또는 `all`(기본)
- `period`: `today`(기본), `5d`, `20d`
- `basis`: `b`(기본, 표시 시점 기준), `a`(봉 마감 기준)
- `special`: `exclude`(기본) 또는 `include`

잘못된 값은 400이다.

```json
{
  "symbol": "all", "period": "today", "days": ["2026-10-12"], "basis": "b", "special": "exclude",

      "accuracy": {"value": 0.52, "low": 0.49, "high": 0.55, "n": 1128},
      "precision": {"value": 0.55, "low": 0.45, "high": 0.65, "n": 96},
```

### `GET /v1/consensus`

합의의 구성과 가중치다.

```json
{
  "names": ["consensus-fast", "consensus-final"],
  "version": "condorcet-20261012", "computed_at": "2026-10-12T15:40:00+09:00",
  "members": ["newton"],
  "fast_seconds": 2.0,
  "weights": {"005930": {"09:00": {"newton": 1.0}}}
}
```

- `members`는 지금의 정식 알고리즘이다. `weights`는 마지막으로 계산한 칸별 가중치다(그때의 구성원).
- 합의의 성적은 순위표와 `/v1/algorithms/consensus-final/stats`에서 다른 알고리즘처럼 볼 수 있다.

### `GET /v1/algorithms/{name}/stats?symbol=&period=&basis=&special=`

알고리즘 하나(기준 예측도 된다)의 상세 통계다. 질의 값은 순위표와 같다. 모르는 이름은 404다.
- 맨 위에는 `algorithm`(이름)과 질의 값 `symbol`, `period`, `days`(실제로 쓴 날짜 목록), `basis`, `special`, 그리고 `min_sample`이 온다. 순위표 응답의 맨 위와 같다.
- `overall`: 같은 질의의 순위표 항목(순위, q값, `excluded` 포함)에 `calibration`과 `calibration_by_class`(`up`, `flat`, `down`)를 더한다. 곡선은 10구간이고, 구간마다 `low`, `high`, `count`, `mean_p`와 `observed`(실제 비율과 Wilson 구간)가 있다.
- `by_symbol`, `by_slot`, `by_model_version`: 종목별, 30분 시간대별, 모델 버전별 항목이다. 시간대는 예측한 봉의 시작 시각 기준이다(`"09:00"`은 09:01–09:30 마감). 이 항목들의 lift는 함께 검정하지 않으므로 `q`와 `significant`가 `null`이다. 거래일 단위 값(`by_day`)은 이 항목들에도 있다.
- 예전에 예측한 적이 있는 알고리즘과 합의(`consensus-fast`, `consensus-final`)는 그 기간에 예측이 없어도 404가 아니라 빈 통계(`n` 0)를 낸다.

  > **바뀜** (2026-10-10, #51): 합의는 한 번도 예측하지 않은 엔진에서 404였다 → 기준 예측처럼 늘 아는 이름이다. 이유: 계약 테스트가 빈 엔진에서 404를 찾았다. 화면은 합의 성적을 늘 물을 수 있어야 한다.

### `GET /v1/macro`

그날의 매크로 지표와 국면이다(#8, #19). 수집기가 `macro` 계층에 기록한 것을 읽는다([design.md](design.md#45-매크로-지표)).

```json
{
  "day": "2026-10-12",
  "decided_at": "2026-10-12T07:30:02+09:00",
  "regime": "risk_off",
  "reasons": ["SOX -1.4% (-1% 이하)"],
  "readings": [
    {"indicator": "sox", "label": "필라델피아 반도체지수", "source": "yahoo", "series": "^SOX", "as_of": "2026-10-09", "value": 12620.8, "change_pct": -1.4}
  ],
  "failed": {},
  "skipped": ["fred"]
}
```

- 엔진 시계의 오늘부터 10일 전까지, 국면이 정해진 가장 최근 날을 보인다. 그래서 07:30 읽기 전에는 전 거래일의 국면이 온다. `day`로 오늘 것인지 확인한다.
- `decided_at`은 그날 마지막으로 국면을 정한 시각이다. 실패한 출처를 다시 읽으면 늦어진다.
- 엔진은 이 답을 30초 동안 그대로 준다(아침 읽기 때만 바뀌어서다). 그래서 새 읽기는 30초 안에 보인다.
- `readings`는 지표 표의 순서다(`macro.py`의 `INDICATORS`). 보이는 국면을 정한 그 읽기의 값이다. 수집기가 다시 시작해 그날 새로 읽었으면, 그 전 읽기의 값은 섞지 않는다. 그래서 실패하거나 키가 없어 건너뛴 출처의 지표는 빠진다. `as_of`는 출처 기준 값의 날짜, `change_pct`는 KRX 전 거래일 아침 대비 등락률(%)이다. 값을 모르면 `null`이다.
- `failed`는 마지막 읽기에서 실패한 출처와 이유, `skipped`는 키가 없어 건너뛴 출처다.
- 아직 정한 날이 없거나(데이터 디렉터리에 없음) 재생 엔진이면 `day`, `decided_at`, `regime`이 `null`이고 목록은 비어 있다. 데모 엔진은 가상의 국면(`risk_off`)을 보인다.

### `GET /v1/calendar` (#150)

경제 캘린더다. 수집기가 TradingView에서 마지막으로 읽은 것 가운데, 엔진 시계의 오늘 0시(KST)부터의 일정을 시각 순으로 보인다([design.md](design.md#45-매크로-지표)의 "경제 캘린더").

```json
{
  "fetched_at": "2026-10-13T09:15:00+09:00",
  "source": "tradingview",
  "countries": ["US", "KR", "CN", "JP", "EU", "DE", "GB"],
  "events": [
    {"id": "421602", "at": "2026-10-14T21:30:00+09:00", "country": "US", "title": "Inflation Rate YoY", "indicator": "Inflation Rate", "category": "prce", "period": "Sep", "actual": null, "forecast": 3.7, "previous": 3.4, "unit": "%", "scale": null, "currency": "USD", "importance": "high", "source": "Bureau of Labour Statistics", "source_url": "https://www.bls.gov"}
  ]
}
```

- `limit`: 일정 수(기본 100, 1–1000). 범위 밖이면 400이다.
- `fetched_at`은 수집기가 마지막으로 읽은 시각이다. 읽기에 실패하는 동안은 앞의 답이 그대로라서 늦어진다. 한 번도 읽지 않았으면(재생·데모 엔진 포함) `null`이고 목록은 비어 있다.
- 값(`actual`, `forecast`, `previous`)은 숫자이고, 모르면 `null`이다. 값은 `<숫자><scale>`이고 단위는 `unit`이다. `scale`은 `K`(천), `M`(백만), `B`(십억), `T`(조) 또는 `null`이라서, `previous: 23.75, scale: "K"`는 23,750이다. `unit`은 `%`, 통화(`$`, `€`, `£`, `CNY` 등) 또는 `null`이다. 실제 값은 발표 뒤 수집기가 처음 읽을 때(기본 15분 안에) 찬다.
- 엔진은 수집기가 남긴 파일을 그대로 넘기지 않고 한 번 읽어 다시 쓴다. 그래서 파일이 망가지거나 손으로 고쳐져도 답은 이 형식을 지키고, 읽을 수 없는 일정은 빠진다.
- 엔진은 수집기가 쓴 파일을 많아야 30초마다 다시 읽는다.

### `GET /v1/stream` (WebSocket, #19)

엔진이 하는 일을 그때그때 보낸다(`stream.py`). 메시지마다 JSON 텍스트 하나이고, `type`과 `at`(메시지를 만든 시각, 엔진 시계)이 있다. 클라이언트는 아무것도 보내지 않는다.

| `type` | 언제 | 내용 |
|---|---|---|
| `prediction` | 예측이 저장(표시)될 때. 기준 예측 3종은 한 번에, 알고리즘은 각자 끝났을 때 | `bar_close`, `predictions`(항목은 `latest`의 예측 항목에 `symbol`을 더한 것) |
| `consensus` | 합의가 저장될 때 | `kind`(`fast`, `final`), `bar_close`, `predictions`(합의 예측, 종목마다 하나) |
| `outcome` | 예측이 채점될 때(봉 마감 4분 뒤) | `outcomes`(채점된 예측. 항목 형식은 같고 `outcome`이 찬다) |
| `health` | 연결하자마자 한 번, 그리고 KIS 연결이나 피드의 결측 구간이 바뀔 때 | `kis`(`/v1/status`의 `kis`와 같다). 실시간과 데모만. 지연 초(`seconds_since`)가 바뀐 것만으로는 보내지 않는다 |
| `lifecycle` | 알고리즘 상태가 바뀔 때. 일일 점검, 다른 프로세스의 `retire`·`unretire` 명령. 엔진이 시작할 때의 처음 등록은 스트림이 열리기 전이라 오지 않는다 | `algorithm`, `change`(`at`, `from`, `to`, `reason`: `/v1/algorithms`의 상태 이력 항목과 같다) |
| `bar` (#110) | 종목의 지금 만들어지는 1분봉이 바뀌었을 때. 1초마다 살펴 종목마다 많아야 한 번, 그사이 마지막 값으로 보낸다. 바뀌지 않으면 보내지 않는다 | `symbol`, `bar`(`start`, `open`, `high`, `low`, `close`, `volume`, `trades`: `/v1/symbols/{symbol}/bars`의 봉과 같은 형식. 그날 시작한 가장 최근 봉이라, 새 분에 체결이 아직 없으면 끝난 앞 봉이 그대로다) |

```json
{"type": "consensus", "at": "2026-10-12T09:31:00.180000+09:00", "kind": "final", "bar_close": "2026-10-12T09:31:00+09:00", "predictions": [{"symbol": "005930", "algorithm": "consensus-final", "model_version": "condorcet-equal", "p_up": 0.57, "...": "..."}]}
```

- 예측과 채점은 엔진이 저장하는 순간 보낸다. 상태 변경, KIS 상태, 만들어지는 봉은 1초마다 살펴서 보낸다.
- `bar`는 바뀔 때만 오고 연결할 때 지금 값을 따로 보내지 않는다. 화면은 끝난 봉을 `/v1/symbols/{symbol}/bars`로 읽고, 그 뒤 `bar`를 마지막 봉에 합친다. 새 분의 `bar`가 오면 앞 봉은 끝난 것이다.
- 한 봉 마감 안에서는 보통 기준 예측, 알고리즘들(끝난 순서), 빠른 합의, 최종 합의 순서로 온다. 다만 빠른 합의보다 늦게 끝난 알고리즘은 그 뒤에 오고, 정식이 아닌 알고리즘(최종 합의가 기다리지 않는다)은 최종 합의 뒤에도 올 수 있다. VI 중인 종목의 빈 예측(`vi`)은 모든 예측자 것이 봉 마감 처음에 한 번에 온다(`prediction` 다음 `consensus` 둘). 순서에 기대지 말고 `algorithm`과 `bar_close`로 맞춘다.
- 스트림은 연결한 뒤의 일만 보낸다. 연결하거나 다시 연결하면 REST(`/v1/symbols/{symbol}/latest` 등)로 지금 상태를 먼저 읽는다.
- 클라이언트가 1,000개 넘게 밀리면 서버가 그 연결을 닫는다(코드 1013, `too slow`). 엔진이 꺼질 때는 1001로 닫는다. 둘 다 다시 연결하면 된다. 30초마다 ping을 보낸다.
- 재생 엔진과 데모 엔진은 다 돌고 난 뒤에 API를 연다. 그래서 데모 엔진의 스트림에는 연결할 때의 `health` 하나만 오고, 재생 엔진에는 아무것도 오지 않는다. 다만 `demo-engine --pace 초`는 10:00까지만 재생하고 API를 연 뒤, 10:30까지 1분을 그 초마다(10초씩 여섯 번에 나눠) 이어 재생한다. 그동안 `prediction`, `consensus`, `outcome`, `bar`가 실제처럼 온다(#21, #110). `bar`는 1분 안에서도 움직인다. 10:30에 끝난 뒤의 답은 `--pace` 없이 띄운 데모와 같다.

### 텔레그램 신호 알림 (#19)

선택 기능이고 기본은 끈다(`KRX_SIGNAL_ALERT=on`으로 켠다, `signals.py`). 봉 마감마다 최종 합의가 나오면 종목마다 본다.

1. 최종 합의의 상승 확률이 `KRX_SIGNAL_MIN_PROBABILITY`(기본 0.6) 이상이면 상승, 아니면 하락 확률이 그 이상일 때 하락이다. 둘 다 아니면 신호가 없다.
2. 그 합의에 들어간 정식 알고리즘 가운데 `KRX_SIGNAL_MIN_AGREE`(기본 2)개 이상이 같은 방향을 예측해야 한다. 알고리즘의 예측 방향은 세 확률 중 가장 큰 쪽이다(동률이면 보합, 그다음 상승. 통계와 같다).
3. 같은 종목·같은 방향의 신호는 앞 신호의 채점 시각(4분 뒤)까지 다시 보내지 않는다. 매분 같은 신호가 쌓이지 않게 하려는 것이다. 엔진이 다시 시작하면 첫 최종 합의 때 오늘 보낸 신호 기록(`runs`의 `signal_sent`)으로 이 상태를 되살린다.
4. 보내기 직전에, 그때까지 엔진이 안 것으로 막을 이유를 본다. 이유가 있으면 보내지 않는다(막힌 신호). 막힌 신호는 3의 반복 억제를 시작하지 않는다. 다음 분에 이유가 없어지면 그 신호는 나간다.
   - `special`: 그때까지 받은 VI나 서킷브레이커 창이 그 종목의 봉 마감 ~ 목표 시각에 닿는다. 예측의 특수 상황(`special`)보다 좁다. 봉 마감 뒤 최종 합의 전에 받은 VI 상태도 막는다(VI 상태는 5초마다 조회한다). 사이드카는 프로그램매매만 멈추므로 막지 않는다.
   - `no_reference`: 봉 마감 기준가(중간가)가 없다. 호가가 60초 넘게 오지 않았다.
   - `expired`: 지금이 이미 목표 시각이다. 엔진이 밀려 뒤늦게 최종 합의를 낸 경우다.
   - 여러 이유에 걸리면 위 순서의 첫 이유를 남긴다.

막을 이유는 신호와 상관없이 최종 합의 예측마다 정해, 예측과 함께 저장하고 예측 조회와 스트림의 `blocked`로 낸다(`special`, `no_reference`, `expired`, 없으면 `null`. 다른 예측은 늘 `null`, #88). 텔레그램 신호가 꺼져 있어도 같다. 화면의 신호 알림도 이것을 따른다.

  > **바뀜** (2026-10-13, #124): 막을 이유는 텔레그램 신호를 보낼 때만 엔진 안에서 정했다 → 최종 합의 예측마다 정해 저장하고 API와 스트림으로 낸다. 이유: 화면의 데스크톱 알림도 같은 판정을 따르게 하려고. 판정 규칙은 엔진 한 곳에만 둔다(#78, #88).

보낸 신호와 막힌 신호는 `runs` 테이블에 `signal_sent`, `signal_blocked`로 남는다. `detail`은 JSON이다: `symbol`, `direction`(`up`, `down`), `probability`, `agree`(같은 방향인 정식 알고리즘 수), `members`(합의에 들어간 정식 알고리즘 수), `bar_close`, `target_at`, `rule`(`min_probability`, `min_agree`, 그때의 신호 규칙), `blocked`(막힌 이유, 보낸 신호는 `null`). 3에서 반복이라 건너뛴 신호는 남지 않는다. 막힌 신호는 로그에도 `signal blocked (<이유>)`로 남는다.

> **바뀜** (2026-10-12, #116): 최종 합의가 확률·동의 조건만 맞으면 보냈고, 반복 억제 상태는 메모리에만 있었다 → 보내기 직전에 막을 이유(`special`, `no_reference`, `expired`)를 보고, 보낸·막힌 신호를 `runs`에 남기며, 재시작하면 오늘 보낸 신호로 반복 억제를 되살린다. 이유: VI는 봉 마감 시점에만 확인해서 봉 마감 직후에 걸린 VI가 신호를 막지 못했고, 기준가가 없는 종목에도 신호가 나갔고, 엔진이 재시작하면 같은 신호가 목표 시각 전에 다시 나갈 수 있었다(#78, #80).

메시지는 `[신호] 005930 상승 64% · 정식 3개 중 2개 같은 방향 · 09:31 봉 마감, 09:35까지`다. 정식 알고리즘이 없으면 합의가 비어서 신호도 없다. 주문은 하지 않는다(엔진에 주문 코드는 없다).

## 알고리즘

### 규약

알고리즘은 `src/krx_quant/algorithms/<이름>/` 모듈 하나다(`algorithms/contract.py`의 `Algorithm`). 다음을 갖는다.
- `card`: 성격 카드. 과학자, 성격, 핵심 로직, 고유 피처, 학습 방법을 적는다.
- `features`: 선언 피처. 예측과 학습에 이것만 받는다. 다른 피처를 읽으면 `UndeclaredFeature`가 난다.
- `training_days`: 학습에 쓰는 최근 거래일 수
- `default_model()`: 학습 전 기본 모델(`<이름>-default`)
- `fit(samples)`: 학습 샘플로 버전이 붙은 모델을 만든다. 배울 것이 없으면(결과가 있는 표본이 없음, 호가가 없음) `NothingToLearn`을 던진다. 밤 학습은 그 알고리즘을 "학습 안 함"으로 두고, 사전 검증은 그날을 기본 모델로 예측한다. 다른 오류는 실패다(사전 검증은 리포트 없이 멈춘다).
- `predict(features, model)`: 한 종목의 피처로 `{p_up, p_flat, p_down, expected_ticks}`를 낸다. 세 확률의 합은 1이다. 읽는 데이터가 봉 마감에 없으면 `NotPredicted(Abstention.NO_BOOK)`을 던져 그 종목을 예측하지 않는다(#25). 엔진은 이유를 예측의 `status`로 남기고, 밤 학습과 사전 검증은 그 표본을 검증에서 뺀다.

알고리즘은 다른 알고리즘의 출력을 받지 않는다.

학습한 모델의 버전은 `<이름>-<마지막 학습일 YYYYMMDD>-<해시>`다(`Model.fitted`). 해시는 파라미터를 키 순서로 정렬한 JSON, 학습 첫날, 마지막 날, 표본 수를 이은 문자열의 SHA-256 앞 6자리다. 그래서 같은 값이면 늘 같은 버전이다.

> **바뀜** (2026-10-09, #39): 해시에 넣는 파라미터가 Python `dict`의 문자열(넣은 순서대로) → 키 순서로 정렬한 JSON. 이유: 같은 값이면 늘 같은 버전이 나오게 하려고(68d979d). 그래서 같은 데이터로 다시 학습해도 Newton의 해시가 그 전과 다르다. 이미 저장한 모델은 자기 버전을 그대로 쓴다.

### 상태 관리 (#17)

알고리즘마다 상태가 있다(`lifecycle.py`). `/v1/algorithms`의 `status`(지금 상태, 언제부터, 이력)와 순위표 항목의 `status`로 보인다.

| 상태 | 뜻 | 바뀌는 규칙 |
|---|---|---|
| `probation` 수습 | 처음 돌기 시작한 알고리즘. 새 알고리즘은 사전 검증(아래)을 통과한 뒤부터 돈다 | 수습 판정일(`KRX_PROBATION_REVIEW_DAYS`, 기본 10·20·40거래일째)에만, 수습 기간 전체에서 가장 약한 lift의 거래일 단위 신뢰구간(`KRX_REVIEW_CONFIDENCE`, 기본 98.3%) 하한이 0보다 크면 `active`. 목록의 마지막 날(기본 40일)이 지나도 정식이 못 되면 텔레그램으로 은퇴 후보 알림을 한 번 보낸다 |
| `active` 정식 | 합의(#18)에 들어간다 | 최근 20거래일의 가장 약한 lift가 0 이하이면 `bench` |
| `bench` 벤치 | 예측과 채점은 계속한다 | 벤치 판정일(`KRX_BENCH_REVIEW_DAYS`, 기본 20·40·60거래일째)에만, 최근 20거래일의 가장 약한 lift의 거래일 단위 하한(같은 신뢰수준)이 0보다 크면 `active`로 회복. 목록의 마지막 날(기본 60일)이 지나도 회복하지 못하면 텔레그램으로 은퇴 후보 알림을 한 번 보낸다 |
| `retired` 은퇴 | 더 돌리지 않는다. 기록은 남는다 | 명령으로만: `krx-quant retire <이름>`. `krx-quant unretire <이름>`은 `probation`으로 되돌린다 |
| `clone` 복제 | 합의에서 빠진다 | 수습 중 먼저 등록된 알고리즘과 p_up − p_down 상관이 0.9를 넘으면 `clone`. 같은 종목·봉 마감 쌍이 30개 이상일 때만 본다. 상관이 다시 0.9 이하로 내려가면 `probation` |

- 매일 장 마감 10분 뒤(보통 15:40) 점검한다. 그때는 그날 예측이 모두 채점되어 있다. 점검했다는 기록(`runs`의 `review`)을 남긴다. 엔진이 꺼져 있어서 점검을 놓치면 다시 켜질 때 놓친 날 것부터 돌린다.
- 통계는 순위표와 같다. 기준 B로 보고 특수 예측은 뺀다. "가장 약한 lift"는 기준 예측 3종 대비 lift 중 가장 작은 것이다. 하한은 거래일 단위(`by_day`, 위 통계 절)의 것이고, 기준 예측 셋 모두 거래일 단위 값이 있어야 판정한다. 채점된 예측 수와 각 기준 예측과의 짝이 모두 `KRX_MIN_SAMPLE`(기본 200) 이상일 때만 판정한다. 모자라면 상태를 그대로 둔다. 상태 변화 이유에 거래일 단위 하한, 그 신뢰수준과 날 수(채점된 짝이 있는 날)가 적힌다(예: `10 days on probation; weakest lift low 0.0123 by trading day at 98.3% (9 days scored)`).
  - 기준 B로 판정하는 것은 진단 실측을 보고 그대로 두었다(2026-10-14, #157, #90).
    - 기준 B에서는 예측마다 자기 표시 시각의 중간가에서 채점한다. 그래서 lift로 짝지은 알고리즘과 기준 예측이 같은 봉 마감이라도 다른 출발점에서 채점될 수 있다.
    - 2026-10-12·13 실측: 알고리즘마다 예측 2,256건이었다. 표시 지연(봉 마감 → 저장)은 p99 0.12–0.14초, 최대 0.25초였다. 두 기준 모두 채점된 예측에서 A와 B의 클래스가 다른 비율은 0.0–0.1%였다([design.md](design.md) 13장 "진단 실측").
    - 그래서 출발점 차이는 판정에 영향이 없다고 보고 그대로 두었다.
    - 검토한 다른 안: 상태 판정만 기준 A로 보기, 기준 예측도 그 알고리즘의 B 정답으로 채점하기.
    - 무거운 알고리즘이 들어와 표시 지연이 초 단위로 늘면 `krx-quant diagnose`로 다시 본다.

  > **바뀜** (2026-10-13, #123): 수습은 10거래일부터 매일, 벤치 복귀는 매일 95% 하한으로 판정했고 수습에 끝이 없었다 → 수습 10·20·40일째와 벤치 20·40·60일째에만 98.3% 하한으로 판정하고, 수습 40일·벤치 60일이 지나도 정식이 못 되면 은퇴 후보 알림을 한 번 보낸다(설정으로 바꿀 수 있다). 이유: 매일 다시 보면 실력이 없는 알고리즘도 운으로 통과하기 쉬웠다(#78의 합성 실험: lift 0인 알고리즘의 34%가 20일 안에, 47%가 60일 안에 승격). 세 번 보는 판정을 합쳐도 운으로 통과할 확률이 한 번 본 95% 판정(한쪽 2.5%)을 넘지 않게, 한 번마다 98.3%로 본다(본페로니, #87). 숫자는 사용자와 정했다.

  > **바뀜** (2026-10-12, #91): 수습 → 정식과 벤치 → 정식의 하한: 짝 단위 정규근사 하한 → 거래일 단위 t분포 하한. 정식 → 벤치(가장 약한 lift ≤ 0)는 그대로다. 이유: 짝 단위 구간은 겹치는 4분 정답과 종목 공통 움직임을 독립 표본으로 세어, 실제 lift가 0인 알고리즘도 합성 실험에서 13–19% 확률로 하한이 0을 넘었다(#78, #79). 판정을 매일 다시 하는 문제는 #87에서 다룬다.
- 거래일은 엔진이 예측한 날이다. 상태가 시작된 날부터 센다. 그날 점검이 끝난 뒤에 시작된 상태(예: 저녁의 `unretire`)는 다음 날부터 센다.
- 복제 판정은 은퇴하지 않은 먼저 등록된 알고리즘과만 비교한다. 짝이 30개 미만이거나 한쪽 값이 늘 같아 상관을 잴 수 없으면 상태를 그대로 둔다.
- 점검 결과를 쓰기 직전에 상태를 다시 읽는다. 그 사이 은퇴 명령이 들어왔으면 점검의 변경은 버린다.
- 은퇴 후보 알림은 텔레그램이 받았을 때만 보낸 것으로 친다. 보내지 못했거나 텔레그램이 설정되지 않았으면(로그에만 남는다) 다음 점검에서 다시 보낸다.
- 상태 변경은 "읽은 상태 그대로일 때만" 한 SQL 문으로 쓴다. 점검과 은퇴 명령이 동시에 써도 한쪽이 다른 쪽을 덮지 않는다.
- 상태 이력은 `statuses` 테이블에 시각, 이전·이후 상태, 사유로 남는다. 은퇴 후보 알림은 `runs` 테이블에 `retire_candidate`로 남는다. 그래서 알림은 한 번만 간다.
- 은퇴 명령은 DB에 바로 쓴다. 엔진은 봉 마감마다 상태를 읽으므로 다음 봉 마감부터 그 알고리즘을 돌리지 않는다.

### 등록 검사

`algorithms/__init__.py`의 `ALGORITHMS`에 넣으면 등록된다. 등록 순서가 우선순위다. 다음이면 거부한다.
- 피처 조합이 이미 등록된 알고리즘과 같다.
- 고유 피처가 없거나, 고유 피처를 이미 등록된 알고리즘이 쓴다. 나중에 등록하는 알고리즘은 앞선 알고리즘의 고유 피처를 공유 피처로 써도 된다(Turing은 모든 피처를 쓴다). 그래서 검사는 등록 순서대로 한다.
- 고유 피처가 선언 피처에 없거나, 모르는 피처를 선언했거나, 이름이 겹친다.

등록 검사는 엔진이 시작할 때(`ALGORITHMS`를 읽을 때) 한다. 그 뒤 새 알고리즘은 사전 검증을 통과해야 돈다(아래 "사전 검증").

`tests/test_algorithm_contract.py`가 등록된 모든 알고리즘에 다음을 자동으로 확인한다. 성격 카드가 채워졌는지, 선언한 피처만 읽는지, 여러 피처 값(값 없음, 극단값 포함)에서 확률이 분포인지, 학습한 모델이 새 버전으로 저장되고 다시 읽히는지다.

### 사전 검증 (#24)

새 알고리즘은 실시간에 넣기 전에 녹화된 최근 거래일로 재생해 검증한다(`prevalidation.py`).

```bash
docker compose run --rm --no-deps engine prevalidate <이름>          # 최근 20거래일
docker compose run --rm --no-deps engine prevalidate <이름> --days 5  # 빨리 훑어보기. 10일 미만은 통과하지 못한다
```

- **재생할 날**: 녹화된 거래일(모든 종목의 통합 체결이 녹화된 날) 가운데 최근 20일이다. 오늘은 21:00 업로드가 끝난 뒤부터 센다. 녹화가 20일보다 적으면 있는 날만 쓰고, 리포트의 `days`에 남는다. 10일보다 적으면 통과하지 못한다.
- **학습**: 날마다 그 전날까지의 데이터로 다시 학습한다(walk-forward). 학습 구간은 알고리즘의 `training_days`이고, 백필만 있는 날도 쓴다(밤 학습과 같다). 재생하는 날은 학습에 쓰지 않는다. 그 전에 데이터가 없거나 알고리즘이 배울 것이 없다고 하면(`NothingToLearn`) 기본 모델로 예측한다. 학습이 다른 오류로 실패하면 사전 검증도 리포트 없이 실패한다. 날마다 쓴 모델 버전이 리포트의 `models`에 남는다.
- **재생**: 하루씩, 등록된 모든 알고리즘(사전 검증을 기다리는 것 포함)을 실시간과 같은 엔진으로 돌린다. 다른 알고리즘은 서버의 모델 파일(`state/models/`)을 쓴다. 그 모델은 재생하는 날로 학습했을 수 있다. 그래서 다른 알고리즘의 성적은 판정에 쓰지 않고, 상관만 잰다. 결과는 `state/prevalidation-<이름>.sqlite3`에 쓴다. 실시간 DB(`engine.sqlite3`)는 건드리지 않아서 공식 성적에 들어가지 않는다.
- 등록 검사(위)를 통과하지 못하는 `ALGORITHMS`는 엔진이 시작할 때부터 거부되므로, 재생하지 않고 오류로 끝난다.
- **기준**: 다섯을 모두 넘어야 통과한다.

| 검사 | 통과 조건 |
|---|---|
| `days` | 재생한 날이 10거래일 이상이다 |
| `features` | 등록 검사를 통과했다(늘 통과한다). 리포트에는 고유 피처가 나온다 |
| `budget` | 시간 예산(`KRX_ALGORITHM_SECONDS`, 기본 10초)을 넘긴 예측(`timed_out`)이 0번이다 |
| `correlation` | 다른 알고리즘과의 p_up − p_down 상관이 모두 0.9 이하다(복제 규칙과 같다. 짝 30개 이상, 특수 예측 포함). 먼저 등록된 것만이 아니라 다른 모든 알고리즘과 비교한다. 그래서 서로 닮은 두 알고리즘이 함께 기다리면 둘 다 거부된다. 잴 수 없는 상대(짝 부족, 늘 같은 값)는 빠진다 |
| `stats` | 재생 결과의 순위표(기준 B, 특수 예측 제외)에서, 채점된 예측과 각 기준 예측과의 짝이 `KRX_MIN_SAMPLE`(기본 200) 이상이고, 가장 약한 lift의 값이 0보다 크다. 신뢰구간 하한은 보지 않는다. 거래일 단위 하한은 수습 10거래일 뒤 정식 승격의 기준이다 |

> **바뀜** (2026-10-12, #73): `budget` 기준의 시간 예산 기본 30초 → 10초. 그래서 사전 검증도 봉 마감 한 번에 10초를 넘기면 통과하지 못한다. 이유: 실시간의 알고리즘 한도가 10초로 줄었다(#71).

- **리포트**: `state/prevalidations/<이름>.json`. 통과하든 못 하든 마지막 결과로 덮어쓴다.
  - `algorithm`, `code`(재생한 코드의 digest), `prevalidated_at`, `passed`, `days`, `models`(날짜 → 모델 버전), `checks`(`check`, `passed`, `detail`)
  - `stats`: 순위표 항목과 같은 형식(`rank`, `n`, `accuracy`, `precision`, `coverage`, `brier`, `pnl`, `lift`). 재생한 알고리즘들끼리 매긴 순위와 FDR 보정(`q`, `significant`)이다. 기준 A와 종목·시간대별 분할은 없다
  - `correlations`(알고리즘 → r), `timed_out`, `statuses`(예측 상태별 개수), `skipped_for_cpu`(CPU 예산으로 건너뛴 봉 마감 수, 판정에는 쓰지 않는다), `db`
- 명령은 검사별 결과를 출력하고, 통과하면 0, 아니면 1로 끝난다.
- **엔진의 관문**: 실시간 엔진은 봉 마감마다 아직 돌리지 않은 알고리즘의 리포트를 읽는다. `passed`가 `true`이고 `code`가 지금 코드의 digest와 같으면 그 봉 마감부터 수습(`registered`)으로 돌린다. digest는 알고리즘 모듈 파일(패키지면 그 안의 모든 `.py`)의 SHA-256 앞 16자리다. 공용 코드(`features.py` 등)는 넣지 않는다. 그 전에는 예측하지 않고, `/v1/algorithms`와 상태 점검에도 나오지 않는다. 엔진이 시작한 뒤 첫 일일 점검 때 기다리는 알고리즘을 텔레그램으로 한 번 알린다(`[알림] 사전 검증 대기: …`).
- 한 번 돌기 시작한 알고리즘(상태가 있는 알고리즘)은 리포트나 코드가 바뀌어도 계속 돈다. 그 뒤는 상태 관리 규칙이 맡는다.
- 사전 검증이 생기기 전에 등록된 Newton, Gauss, Granger, Markov, Turing은 리포트 없이 돈다(`REGISTERED_BEFORE`). 새 서버의 빈 DB에서도 마찬가지다.
- 기다리는 알고리즘의 모델도 밤 학습이 만든다. 엔진은 등록된 모든 알고리즘의 모델 파일을 보고 `live.json`에도 올린다. 그래서 밤 학습은 서버에 설치된 모델과 비교하고, 알고리즘은 돌기 시작할 때 최신 모델을 쓴다.

### 피처 (Feature Store)

`features.py`에 이름으로 등록한다. 봉 마감마다 종목별로, 알고리즘들이 선언한 피처를 한 번씩만 계산해 모두에게 같은 값을 준다. 입력은 그날 끝난 1분봉, 봉 마감의 기준가, 그날 개장 시각, 그날 매크로 국면(개장 전에 마지막으로 정한 것, #8), 그날 종목의 흐름(프로그램매매, 외국계 회원사, 투자자별 추정), 매분 끝의 microprice, 호가·체결의 주문 흐름(1호가 OFI, 10단계 잔량, 체결 방향, 거래소별 체결량), 매수·매도 체결의 도착(시각, 방향, 크기), 옵션 만기까지 남은 거래일뿐이다. 흐름과 호가·체결은 봉 마감 전에 받은 것만 쓴다. 피처 값은 숫자 하나(모르면 없음)이거나, 숫자의 열이다(`minute_ticks`, `microprice_ticks`, `kospi200f_moves`. 알고리즘은 `FeatureVector.series`로 읽는다). 호가에서 나오는 피처(`microprice_ticks`, `ofi_1`, `ofi_5`, `depth_imbalance`, `spread_ticks`, `top_imbalance`, `top_size_change`, `BOOK_FEATURES`)와 체결 방향·거래소별 체결에서 나오는 피처(`trade_imbalance`, `trade_entropy`, `nxt_share`, `*_excitation_*`, `*_arrivals_1`, `TAPE_FEATURES`)는 녹화된 날에만 값이 있다. 백필에는 호가도 체결 방향도 없다. 1분봉은 통합 체결로 만들어서 NXT 프리마켓(08:00~) 봉도 들어 있다. VWAP 피처는 개장(보통 09:00, 시가 단일가 포함)부터의 봉만 쓴다.

엔진은 흐름 피드도 읽는다(#16): 프로그램매매(`H0UNPGM0`의 `net_value`. 한도로 잘리면 REST 대체 `FHPPG04650101`이 같은 피드 이름으로 들어온다), 회원사(`H0UNMBC0`와 REST 대체 `FHKST01010600`의 `foreign_net_qty`), 외국인·기관 추정 가집계(`HHPTJ04160200`). 프로그램매매와 회원사는 그날 누적값이라, 피처는 봉 마감 전에 받은 마지막 값과 그 5분 전에 받은 값의 차이를 쓴다. 추정 가집계는 시간대별 값이라, 봉 마감 전에 받은 가장 늦은 시간대의 값을 쓴다(외국인·기관 각각 값이 있는 시간대. 시간대 코드가 클수록 늦다고 본다 ⚠ 실측 전). 흐름은 날짜가 바뀌면 처음부터 다시 쌓는다. 백필이 없어 녹화된 날에만 값이 있다.

엔진은 Markov(#53)를 위해 옵션 체결(`H0IOCNT0`, 등가격 ±2 행사가 콜·풋)의 내재변동성(`implied_vol`)과 델타(`delta`)도 읽는다. 시장 전체의 값이라 그날 녹화된 옵션 파티션을 모두 읽는다. 백필에는 옵션이 없어 녹화된 날에만 값이 있다.

엔진은 Shannon(#26)을 위해 통합 체결의 체결 방향(`side`), NXT 전용 체결(`H0NXCNT0`)의 수량, 통합 호가의 10단계 잔량도 읽는다. Poisson(#27)도 통합 체결의 체결 방향과 수량을 쓴다.

엔진은 체결 피드로만 1분봉을 만든다: 종목은 통합 체결(`H0UNCNT0`), ETF는 KRX 전용 체결(`H0STCNT0`), 선행 시리즈는 선물·지수·미국 주간거래 피드다(지수는 REST 대체 `FHPUP02100000`도 읽는다). 선물과 미국 주간거래는 한도로 잘리면 REST 대체가 같은 피드 이름으로 들어온다(#28). 그 시세에는 체결 하나의 수량이 없어서, 그동안 선행 시리즈 1분봉의 거래량은 0이다. 세션 한도로 잘려 종목이나 ETF의 체결이 REST 시세(`FHKST01010100`)로 바뀌면 엔진은 그 시세를 읽지 않는다. 그러면 그 종목의 1분봉과 피처가 비고, ETF 묶음(`lead_etfs_*`)은 값이 없다. Granger는 그만큼 예측 폭을 넓힌다(PR #44 "Known limits"). 3종목 기본 계획(38건)에서는 잘리지 않는다.

| 피처 | 뜻 |
|---|---|
| `velocity` | 마지막 6개 봉 종가에 맞춘 포물선의 마지막 기울기(틱/분). 한 호가단위 구간에서 틱은 가격의 일정 비율이라 수익률 기울기와 같은 뜻이다. |
| `acceleration` | 그 포물선의 곡률(틱/분²) |
| `relative_volume` | 최근 5개 봉의 봉당 거래량 ÷ 최근 60개 봉의 봉당 거래량 |
| `volatility` | 최근 20개 1분 종가 변화의 표준편차(틱) |
| `flat_ticks` | 보합 범위 k |
| `vwap_gap` | 기준가가 당일 VWAP보다 몇 틱 위에 있는지(아래면 음수). VWAP는 개장부터의 봉으로, 봉마다 대표가 (고가 + 저가 + 종가) / 3을 거래량으로 가중한다. 개장 뒤 봉이 5개 미만이면 값이 없다. |

### 학습

학습 샘플은 하루 단위로 만든다(`training.py`). 예측 구간의 봉 마감마다 종목별로 하나다. 실시간과 같은 피처 코드를 쓰고, 보합 범위도 채점과 같다. 날마다 둘 중 하나로 만든다.

- **녹화된 날**: 예측 종목 모두의 통합 체결(`H0UNCNT0`)이 녹화된 날이다. 그날 이벤트를 엔진과 같은 Market View(`market_view.py`)에 받은 순서대로 넣는다. 그래서 1분봉, 선행 묶음, 기준가가 엔진이 그 봉 마감에 본 것과 같다. 기준가는 통합 중간가이고, 정답은 4분 뒤 중간가와 비교한 클래스다(채점 기준 A). 지수와 미국 주간거래 묶음도 학습된다. 녹화가 끊긴 시간대는 중간가를 몰라 정답이 없다.
- **백필만 있는 날**: 백필에는 호가가 없다. 그래서 기준가를 직전 종가로 보고, 정답을 4분 뒤 종가와 비교한 클래스로 정한다. 종가는 매수호가와 매도호가 사이를 오간다(bid-ask bounce). 중간가로 채점하는 실전에는 이 튐이 없다. 선행 묶음은 백필된 다른 종목, 선물 연속 1분봉, ETF다. 지수와 미국 주간거래는 백필이 없어 값이 없다.
- 녹화된 날은 백필이 있어도 녹화로 학습한다.
- 날마다 그날 `macro` 계층에서 개장 전에 마지막으로 정한 국면을 읽어 피처 `macro_regime`에 넣는다(#14). 엔진과 같은 국면이다. 국면이 없는 날은 값이 없다. 밤 학습은 그날 국면도 S3에서 캐시로 받는다.
- 백필로 학습하려면 예측 종목 모두의 백필이 있어야 한다. 녹화도 백필도 모든 종목을 갖추지 못한 날(한 종목은 백필만, 다른 종목은 녹화만 있는 날)은 학습하지 않는다. 일부 종목만으로 학습하지 않기 위해서다.
- 밤 학습의 검증은 이 표본으로 한다. 리포트에는 검증일별·기준가(`mid`·`close`)별 손실과 짝지은 손실 차이의 평균과 날 단위로 묶은 표준오차가 남는다(#89, [operations.md](operations.md) Object Store 표의 `reports/`). 녹화 중간가로 만든 날과 백필 종가로 만든 날의 검증 손실을 나눠 볼 수 있다.
- 녹화된 날에는 실전에서 예측하지 않거나 통계에서 빼는 봉 마감도 표본에서 뺀다. VI 중인 종목의 봉 마감(엔진이 예측하지 않는다)과, 4분 구간에 VI·서킷브레이커·사이드카가 닿는 봉 마감(특수 예측)이다. 특수 여부는 엔진처럼 정한다. 그 봉 마감에 알던 구간과 그 뒤에 알게 된 구간이 닿으면 특수다. 백필만 있는 날은 VI 정보가 없어서 빼지 않는다.

> **바뀜** (2026-10-10, #48): 이전에는 모든 날을 백필 1분봉과 종가 기준으로 학습했다 → 지금은 녹화된 날을 녹화 이벤트와 중간가로 학습한다. 이유: 종가의 bid-ask bounce 때문에 되돌림을 실제보다 크게 배울 수 있었다(2026-10-08 첫 학습의 Granger `return_1 = −0.335`). 또 지수·미국 주간거래 묶음은 백필이 없어 계수가 늘 0이었다.

```bash

uv run krx-quant fit gauss
uv run krx-quant fit granger
uv run krx-quant fit markov
uv run krx-quant fit turing            # 60일
uv run krx-quant fit newton --days 60
```

- 최근 `--days`개(기본 `training_days`)의 데이터 있는 날로 학습한다. 오늘은 녹화가 S3에 올라간 21:00 뒤에만 센다. 그 전에는 아직 녹화 중이다.
- 출력에 녹화(중간가)로 학습한 날짜가 나온다. 예: `recorded days, on mid-points: 2026-10-08; the others on backfilled closes`.
- 모델은 `state/models/<이름>.json`에 저장한다. 학습에 쓴 마지막 날(`trained_until`)도 적는다.
- 엔진은 시작할 때 이 파일을 읽고, 없으면 기본 모델을 쓴다. 실행 중에 파일이 바뀌면(학습, 08:00 교체, `rollback`) 1분 안에 새 모델로 바꾼다.
- 매일 밤 자동 학습(walk-forward, champion/challenger)과 08:00 교체, 롤백은 [operations.md](operations.md#밤-학습과-모델-교체-22)에 있다(#22).

### Newton

추세 추종이다.
- 속도 v와 가속도 a에 상대 거래량 m(최대 3)을 곱해 운동량과 힘으로 본다.
- 감쇠 γ를 넣은 dv/dt = F − γv로 4분 뒤 변위를 외삽한다.
- 변위가 θ·k보다 작으면 0으로 본다.
- 변위를 중심으로, 최근 변동성 × √4(최소 0.5틱) 폭의 정규분포에서 상승·보합·하락 확률을 낸다.
- 학습은 γ ∈ {0, 0.1, 0.25, 0.5, 1, 2, 4}, θ ∈ {0, 0.5, 1, 1.5, 2, 3}에서 log loss가 가장 작은 쌍을 고른다. 기본값은 γ = 0.5, θ = 1이다.
- 모델 버전은 `newton-<마지막 학습일>-<해시>`다.

### Gauss

역추세다. 가격이 당일 VWAP에 용수철처럼 끌려 돌아온다고 본다.
- VWAP 대비 괴리 X(틱)가 Ornstein–Uhlenbeck 과정 dX = −κX dt + σ dW를 따른다고 본다. 4분 뒤 괴리의 기대값은 X·e^(−4κ)이므로, 기대 움직임은 −X·(1 − e^(−4κ))틱이다.
- κ는 당일 추정치(`reversion_speed`)와 학습한 κ를 가중치 w로 섞는다(당일 추정치가 없으면 학습한 κ).
- |z|(`vwap_z`)가 θ보다 작으면 잡음으로 보고 움직임을 0으로 둔다.
- 움직임을 중심으로 정규분포에서 상승·보합·하락 확률을 낸다. 폭은 OU 과정이 4분 동안 퍼지는 만큼이다. 1분 변동성 × √((1 − φ⁸)/(1 − φ²)), φ = e^(−κ)(κ = 0이면 √4). 최소 0.5틱이다.
- 학습은 θ ∈ {0, 0.5, 1, 1.5, 2, 2.5}마다 θ 밖 괴리의 4분 움직임에 −X·(1 − e^(−4κ))를 최소제곱으로 맞춰 κ를 구한다. 그다음 w ∈ {0, 0.25, 0.5, 0.75, 1}과 함께 log loss가 가장 작은 조합을 고른다. 괴리가 오히려 커졌으면 κ = 0이다. 기본값은 κ = 0.05, w = 0.5, θ = 1이다.
- 모델 버전은 `gauss-<마지막 학습일>-<해시>`다.
- 학습 샘플의 기준가는 직전 종가다(위 "학습"). 종가는 매수·매도 호가를 오가며 튀고(bid-ask bounce), 이 튐은 다음 움직임에서 되돌아온다. 그래서 학습한 κ는 실시간(중간가 기준)보다 조금 클 수 있다.
- 2026-09-03..2026-10-02부터 2026-09-08..2026-10-08까지의 학습 창(모델 네 개)은 이 튐이 있는데도 κ = 0, w = 0을 골랐다(#162). 4분 움직임과 VWAP 괴리 사이에 되돌림이 보이지 않았다. 그래서 지금 Gauss의 `expected_ticks`는 언제나 0이고, 상승·하락 확률이 같다. 이때 `threshold`는 의미가 없다. 예측이 어느 θ에서나 같아서 격자의 첫 값 0이 남는다. 조사 내용은 [design.md](design.md#71-명단-v1)의 "Gauss의 학습 결과"에 있다.

### Granger

이웃 관찰이다. 다른 시리즈가 먼저 움직인 것을 반영한다.
- 4분 뒤 움직임(종목 자신의 1분 변동성 단위)을 자기 시차 수익률(`return_*`)과 남긴 선행 묶음의 시차 수익률(`lead_*`)로 선형 회귀한다. 절편은 없다.
- 기대 움직임 = 변동성 × Σ 계수 × 값(틱)이다. 그 주변 정규분포에서 상승·보합·하락 확률을 낸다. 폭은 변동성 × 회귀 잔차 표준편차다.
- 남긴 묶음의 값이 없으면(피드가 비었을 때, 예: 미국 서머타임이 아닐 때 10:00 전 주간거래) 움직임 0으로 보고, 폭은 √(잔차² + Σ 계수²)로 넓힌다.
- 학습(Granger 인과 검정):
  1. 자기 시차 수(0–3)를 BIC로 고른다.
  2. 묶음마다 시차 수(1–3)를 BIC로 고른다. 자기 시차만 쓴 회귀보다 BIC가 낮을 때만 그 묶음을 남긴다(같은 봉 마감들에서 비교). 값이 있는 봉 마감이 100개 미만이거나, 자기 시차를 아는 봉 마감의 절반 미만인 묶음은 시험하지 않는다. 3단계는 남긴 묶음을 모두 아는 봉 마감만 쓰므로, 녹화된 며칠에만 있는 묶음(지수, 미국 주간거래)을 남기면 나머지 날이 빠지기 때문이다.
  3. 남긴 것 전부로 최소제곱을 다시 맞춘다.
  - 이웃한 봉 마감의 4분 움직임은 서로 겹친다. 그래서 BIC는 봉 마감 수의 4분의 1만큼을 독립된 표본으로 센다.
- 모델 파라미터는 모든 계수(남기지 않은 것은 0)와 잔차 표준편차(`residual`)다. 기본 모델은 계수가 모두 0, 잔차 2(4분 랜덤워크)다.
- 모델 버전은 `granger-<마지막 학습일>-<해시>`다.
- 백필만 있는 날은 정답도 종가로 정한다. 종가는 호가 사이를 튀고(bid-ask bounce) 다음 분에 되돌아온다. 그래서 그런 날로 학습한 자기 시차 계수는 실시간(중간가 기준)보다 음수 쪽으로 치우칠 수 있다. 녹화된 날은 정답이 중간가라 이 치우침이 없다.
- 지수와 미국 주간거래 묶음은 녹화된 날에만 값이 있다. 학습 구간의 절반 넘게 녹화가 쌓이면 시험한다.

> **바뀜** (2026-10-10, #48): 이전에는 "지수와 미국 주간거래는 학습 데이터가 없어 계수가 늘 0"이었다 → 지금은 녹화된 날로 학습한다. 이유: 녹화 이벤트로 엔진과 같은 1분봉을 만들 수 있다.

### Markov

국면 탐정이다(#14, `algorithms/markov/`). 1분 움직임을 조용함·상승추세·하락추세·급변동 4국면의 은닉 마르코프 모델로 본다.
- 국면마다 1분 종가 변화(틱)가 정규분포를 따른다고 본다(평균, 표준편차).
- 최근 1시간의 움직임(`minute_ticks`)을 전이행렬의 장기 분포에서 시작해 앞으로 걸러(forward filter), 지금 각 국면에 있을 확률을 낸다.
- 그 확률에서 전이행렬로 4분 뒤까지 국면을 옮겨 가며 4분 움직임 합의 평균과 분산을 정확히 계산한다(분마다의 분산, 국면이 이어지며 생기는 공분산 포함). 그 정규분포로 상승·보합·하락 확률을 낸다.
- **IV 국면(#53).** 봉 마감의 옵션 등가격 내재변동성(`atm_iv`)이 모델의 두 경계(`iv_cut.0`, `iv_cut.1`)보다 낮으면 낮음, 위 경계 이상이면 높음, 그 사이는 보통이다. 그 국면의 배율(`iv_scale.0`–`iv_scale.2`, 보통은 늘 1)을 4국면의 평균과 표준편차에 곱해, 최근 1시간을 거르고 4분 뒤를 계산한다(IV 국면은 천천히 바뀌므로 지금 국면을 그 1시간 전체에 쓴다). 표준편차의 0.5틱 하한은 곱한 뒤에 적용한다. IV를 모르거나 모델에 경계가 없으면 배율은 1이다.
- 전이행렬은 그날 매크로 국면(`macro_regime`)의 것을 쓴다. 국면이 없거나 엔진이 모르는 이름(새 버전 수집기의 국면 등)인 날은 기본 전이행렬을 쓰고, 엔진이 `runs`에 `no_regime`(`no macro regime for <날짜>`, 모르는 이름이면 뒤에 `(unknown: <이름>)`)을 하루 한 번 남기고 로그에 경고한다.
- 학습은 Baum–Welch 재추정이다. 종목·날짜마다 그날의 1분 움직임을 한 줄로 이어(첫 표본의 1시간, 그 뒤 표본마다 새 분) 최대 30번 반복한다.
  - 국면별 분포(평균, 표준편차)는 모든 날로 배운다.
  - 매크로 국면의 전이행렬은 그 국면의 날로 배운다. 기본 행렬 20개분을 더해서, 날이 적은 국면은 기본 행렬 쪽으로 당겨진다. 그 국면의 날이 없으면 기본 행렬과 같다.
  - 기본 전이행렬은 모든 날로 배운다.
  - **IV 국면의 경계**는 반복 전에 정한다. 학습 표본 가운데 `atm_iv`가 있는 봉 마감의 값을 셋으로 똑같이 나누는 두 값(3분위)이다. 그런 날이 5거래일보다 적으면 경계를 두지 않는다(파라미터에 `iv_cut.*`이 없다). 그러면 IV 국면도 배율도 배우지 않는다.
  - 각 분은 함께 온 표본의 IV 국면을 가진다(첫 표본의 1시간은 첫 표본의 국면). 국면별 분포는 그 분의 움직임을 국면 배율로 나눈 값으로 배운다.
  - 낮음·높음 국면의 배율은 그 국면에 속한 분들의 움직임 제곱 평균이 4국면 분포가 기대하는 값(평균² + 표준편차²의 가중 평균. 표준편차는 예측처럼 0.5틱 하한을 적용한다)과 같아지게 정하고, 60분어치의 1을 더해 1 쪽으로 당긴다. 그래서 몇 분 안 되는 국면의 배율은 1에 가깝다.
  - 보통 국면의 배율은 1로 고정한다. 배율과 4국면의 표준편차는 서로 크기를 주고받을 수 있어서(둘을 곱한 값만 정해진다), 하나를 1로 두어야 IV를 모르는 분(배율 1)과 보통 국면이 같은 뜻이 된다.
  - 학습한 뒤 국면 번호를 정렬한다. 표준편차가 가장 큰 것이 급변동, 나머지 중 가장 작은 것이 조용함, 남은 둘 중 평균이 큰 쪽이 상승추세다.
- 기본값(학습 전): 평균 0, +1, −1, 0틱, 표준편차 0.5, 1, 1, 2.5틱, 모든 국면이 한 분에 0.9의 확률로 머문다.
- 국면의 표준편차는 0.5틱 아래로 내려가지 않는다. 움직임이 정수 틱이라, 더 좁으면 조용함 국면이 정확히 0만 설명하게 되어 1틱 움직임 하나에 바로 추세로 넘어간다.
- 기본 전이행렬은 데이터에 학습 전 행렬 1개분을 더해 배운다. 그래서 데이터가 거의 없는 국면의 행은 학습 전 값(머물 확률 0.9)에 가깝게 남는다.
- 반복은 로그우도가 거의 변하지 않으면 멈춘다. 국면별 행렬을 기본 행렬 쪽으로 당기므로 엄밀한 EM은 아니어서, 로그우도가 조금 오르내릴 수 있다.
- 파라미터 이름은 `mean.<국면>`, `sd.<국면>`, `<전이행렬>.<from>.<to>`, `iv_cut.0`·`iv_cut.1`(IV 경계, %, 없을 수 있다), `iv_scale.<IV 국면>`(0 낮음, 1 보통, 2 높음)이다(국면 0–3은 조용함, 상승, 하락, 급변동, 전이행렬은 `shock`, `risk_off`, `risk_on`, `neutral`, `default`). 학습 전 기본값에는 경계가 없고 배율은 모두 1이다. #53 전에 학습한 모델에는 경계도 배율도 없어서 IV를 읽지 않는다.
- 모델 버전은 `markov-<마지막 학습일>-<해시>`다.
- 백필만 있는 날은 종가로 움직임을 재서, 호가 사이를 튀는 만큼(bid-ask bounce) 급변동 국면이 실시간보다 조금 넓게 배워질 수 있다.
- 학습하는 날의 국면은 그날 개장 전에 마지막으로 정한 국면이다(엔진과 같다). #8 전의 날(지금 학습 데이터 대부분)은 국면이 없어 기본 전이행렬만 배운다. 국면별 행렬은 07:30 수집이 쌓이면서 배워진다.

> **바뀜** (2026-10-11, #54): 설계(design.md 7.1)는 "옵션 IV 국면, 변동성, 스프레드, 시간대"도 피처로 들었다 → 지금은 매크로 국면과 1분 움직임만 쓴다. 이유: 엔진이 옵션 피드를 읽지 않고 백필에 옵션이 없다(#53으로 미룸). 변동성은 국면의 표준편차가 대신하고, 스프레드와 시간대는 이슈의 요구사항에 없었다.

> **바뀜** (2026-10-11, #66): 옵션 IV 국면을 #54에서 미뤘다 → 더했다(`atm_iv`, IV 국면별 움직임 배율). 이유: 엔진이 옵션 체결(`H0IOCNT0`)을 읽게 되었다(#53). 경계를 고정값 대신 학습하고, 전이행렬이 아니라 움직임의 크기에 쓰는 것은 사용자와 정했다. 녹화된 날이 적어도 국면마다 배울 것이 배율 하나뿐이라 안정적이다.

### Kalman

잡음 제거·선물 추종이다(#25, `algorithms/kalman/`). 호가창의 microprice를 숨은 적정가에 잡음이 낀 관측으로 보는 상태공간 모델이다. 시간 간격은 1분이고 단위는 틱이다.
- 상태: 적정가 L과 추세 v. 매분 L ← L + v + b·(1분 전 KOSPI200 선물 움직임, bp) + 잡음(분산 `q_level`), v ← φ·v + 잡음(분산 `q_trend`). 관측: microprice = L + 잡음(분산 `r`).
- 예측: `microprice_ticks`의 열(최근 1시간, 호가가 빈 뒤부터)을 칼만 필터로 걸러 봉 마감의 L과 v를 얻는다. 처음 L은 첫 microprice 주변에서 아무것도 모르는 상태(분산 100틱²), v는 정상분포에서 시작한다. 그 상태를 4분 뒤로 옮긴다. 첫 분은 봉 마감까지 1분의 선물 움직임을 넣고, 그 뒤 분의 선물 움직임은 모르므로 b² × (최근 선물 움직임 제곱 평균)만큼 분산을 더한다. 4분 뒤 L의 평균이 기대수익(봉 마감 기준가 대비 틱)이고, 분산에 r을 더한 정규분포로 상승·보합·하락 확률을 낸다.
- 봉 마감에 호가가 비어 있으면 예측하지 않는다(`no_book`).
- 학습: 최근 20거래일의 녹화된 날로 EM을 한다. 종목·날짜마다 서로 겹치지 않는 1시간 구간을 장 마감 쪽부터 고르고(그날의 마지막 표본의 열, 그 열이 시작하기 전에 끝나는 표본의 열, …), 구간마다 칼만 스무더(RTS)로 상태의 평균·분산·이웃 분 공분산을 구한다. 그것으로 `q_level`, `q_trend`, `r`, `φ`, `b`를 닫힌 해로 다시 추정하고, 로그우도가 거의 변하지 않을 때까지(최대 50번) 반복한다. 백필만 있는 날은 호가가 없어 학습에 쓰지 않는다. 학습 구간에 녹화된 날이 없으면 학습하지 않는다(밤 학습 리포트 `not trained: no training samples with the book`).
- 범위: 분산은 0.0001 이상, φ는 0–0.99다.
- 기본값(학습 전): `q_level` 0.5, `q_trend` 0.02, `r` 0.25, `φ` 0.8, `b` 0(선물을 따르지 않는다).
- 파라미터 이름은 `q_level`, `q_trend`, `r`, `phi`, `b`다. 모델 버전은 `kalman-<마지막 학습일>-<해시>`다.
- 사전 검증(#24) 뒤에 등록된 첫 알고리즘이다. 배포되면 사전 검증을 통과할 때까지 돌지 않는다. 녹화가 10거래일 쌓여야 통과할 수 있다.
- 설계(design.md 7.1)의 "KOSPI200 선물을 외부 입력으로"는 1분 전 선물 움직임의 계수 b로 넣었다. 같은 분의 선물 움직임은 예측할 때 모르므로 쓰지 않는다.

### Shannon

호가창 해독이다(#26, `algorithms/shannon/`). 다음 4분의 상승·보합·하락을 다항 로지스틱 회귀(소프트맥스)로 낸다.
- 입력: `ofi_1`, `ofi_5`, `depth_imbalance`, `trade_imbalance`, `trade_entropy`, `nxt_share`, `program_net`, `member_foreign_net`. 고유 피처는 `ofi_1`, `ofi_5`, `trade_entropy`다.
- 입력마다 학습 표본의 평균과 표준편차로 표준화한다. 값이 없는 입력은 평균(표준화하면 0)으로 본다.
- 기대수익은 학습에서 클래스별 평균 움직임(틱, `move.up`, `move.flat`, `move.down`)을 확률로 가중한 값이다.
- 봉 마감에 호가가 비어 있으면(`depth_imbalance`가 없음) 예측하지 않는다(`no_book`).
- 학습: 최근 20거래일의 녹화된 날로, 가중치에 L1을 건 평균 교차엔트로피를 가속 근접 경사법(FISTA, 백트래킹)으로 최소화한다(최대 1000번). 절편에는 L1을 걸지 않는다.
  - L1 강도는 0.1, 0.03, 0.01, 0.003, 0.001 중에서 고른다. 가장 최근 거래일들을 통째로 검증에 두고, 그 전 날들로 학습해 검증일의 로그손실이 가장 작은 강도다(같으면 강한 쪽). 검증일 수는 검증 표본이 전체의 20%에 가장 가까워지는 수다(같으면 적은 쪽). 학습할 날이 적어도 하루 남는다. 날을 쪼개지 않으므로 4분 정답이 학습과 검증에 걸치지 않는다. 표본이 100개 미만이거나 날이 하루뿐이면 0.01이다. 고른 강도로 전체를 다시 학습한다.
  - 모델에 고른 강도(`penalty`)와 검증일(`validation_from`, `validation_to`: YYYYMMDD, `validation_days`: 날 수. 검증하지 않았으면 0)이 남는다.

    > **바뀜** (2026-10-13, #122): 표본을 시간순 앞 80%·뒤 20%로 나눴다 → 거래일 경계로 나눈다. 검증일을 모델에 남긴다. 이유: 같은 날 안에서 나누면 경계 직전 봉 마감의 4분 정답이 검증 구간에 걸쳐 검증이 낙관적이었다(#78, #86).
  - 호가가 있는 표본이 없으면 학습하지 않는다(`not trained: no training samples with the book`).
- 기본값(학습 전): 가중치와 절편 0. 세 확률이 같고 기대수익 0이다.
- 파라미터 이름은 `penalty`, `validation_from`, `validation_to`, `validation_days`, `mean.<입력>`, `sd.<입력>`, `w.<클래스>.<입력>`, `bias.<클래스>`, `move.<클래스>`다(클래스: `up`, `flat`, `down`). 모델 버전은 `shannon-<마지막 학습일>-<해시>`다.
- 사전 검증(#24)을 통과해야 돈다. 녹화가 10거래일 쌓여야 통과할 수 있다.

### Poisson

쏠림 감지다(#27, `algorithms/poisson/`). 매수·매도 시장가 체결의 도착을 이산화한 Hawkes 과정(자기흥분 점과정)으로 본다.
- 체결마다 크기(그날 평균 대비)만큼 자기 쪽과 반대쪽을 흥분시키고, 흥분은 감쇠 시간 10초·60초의 지수로 줄어든다. 피처는 봉 마감에서의 흥분 4개와 최근 1분의 도착 2개다(`*_excitation_*`, `*_arrivals_1`, 모두 고유 피처).
- 강도: 매수·매도 쪽마다 다음 4분의 도착 기댓값 = 기준 강도(`base.<쪽>`) + 흥분 4개 × 계수(`excite.<쪽>.<흥분>`). 계수는 0 이상이다(자기·교차 흥분).
- 예측: 봉 마감의 흥분으로 4분 동안의 매수·매도 도착 기댓값을 내고, 쏠림 = (매수 − 매도) ÷ (매수 + 매도)를 순서형 로지스틱으로 바꾼다: P(상승) = σ(k·쏠림 − c), P(하락) = σ(−k·쏠림 − c), 나머지가 보합. 기대수익은 클래스별 평균 움직임(`move.*`)을 확률로 가중한 값이다.
- 그날 방향이 있는 체결을 아직 받지 못했으면(흥분을 모름) 세 확률이 같다.
- 학습: 최근 20거래일의 녹화된 날로 한다.
  - 표본마다 다음 4분의 도착(1·2·3·4분 뒤 표본의 `*_arrivals_1` 합)을 선형 강도의 Poisson 과정의 도착으로 보고, 우도를 최대로 하는 기준 강도와 흥분 계수를 EM으로 구한다(쪽마다 따로, 최대 1000번). 도착은 정수 건수가 아니라 크기 가중이라 엄밀히는 준-Poisson 우도다. 4분이 다 있는 표본만 쓴다.
  - 그다음 기울기 k(0.5–16)와 문턱 c(0–3)를 격자에서 로그손실이 가장 작은 것으로 고른다(같으면 완만한 쪽, 낮은 문턱).
  - 방향이 있는 체결이 없으면 학습하지 않는다(`NothingToLearn`).
- 기본값(학습 전): 기준 강도 4(1분에 하나), 흥분 계수 0, k 1, c 1.
- 파라미터 이름은 `base.<쪽>`, `excite.<쪽>.<흥분 피처>`, `slope`, `cut`, `move.<클래스>`다(쪽: `buy`, `sell`). 모델 버전은 `poisson-<마지막 학습일>-<해시>`다.
- 시간 예산: 예측은 숫자 몇 개의 계산이다. 재생 테스트에서 봉 마감당 0.1초 안이다(엔진이 잰 시간). 흥분과 도착은 Market View가 그날 방향이 있는 체결을 압축 배열(체결당 17바이트)로 들고 봉 마감마다 계산하고, 피처 저장소가 그날 평균 크기로 나눈다. 이 시간은 알고리즘의 예산에 들지 않는다.
- 사전 검증(#24)을 통과해야 돈다.
- 설계(design.md 7.1)의 "Hawkes 과정"은 감쇠 시간을 고정한 이산화로 했다. 체결 하나하나를 피처로 넘기면 밤 학습의 표본 메모리가 2GB 서버를 넘기 때문이다(사용자와 정함).

### Turing

만능 학습이다(#16, `algorithms/turing/`. 호가·체결·옵션 피처는 #55). LightGBM 그래디언트 부스팅 트리로 4분 뒤 상승·보합·하락을 분류한다.
- 피처: 피처 저장소의 숫자 피처(다른 알고리즘의 피처 포함)와 고유 피처 7개다. 호가·체결 피처(`BOOK_FEATURES`, `TAPE_FEATURES`: Shannon과 Poisson의 피처)와 Markov의 옵션 등가격 내재변동성(`atm_iv`)도 읽는다. 예측은 모델의 트리가 학습한 피처 이름 순서대로 값을 넣는다. 그래서 나중에 피처가 더해져도 예전 모델은 자기 피처로 계속 예측한다. 고유 피처는 `minutes_since_open`, `days_to_expiry`, `investor_foreign`, `investor_institution`과 최우선 호가의 `spread_ticks`, `top_imbalance`, `top_size_change`(#55)다. 열 피처(`minute_ticks`, `microprice_ticks`, `kospi200f_moves`)는 쓰지 않는다. 모든 피처를 읽으므로 등록 순서의 맨 끝에 둔다(나중 알고리즘의 고유 피처를 먼저 쓰면 등록이 거부된다).

  > **바뀜** (2026-10-13, #131): 호가·체결 피처와 `atm_iv`는 읽지 않았고 고유 피처는 4개였다 → 모두 읽고, 최우선 호가 피처 3개를 고유 피처로 더했다. 이유: 녹화가 10거래일 쌓이면 더하기로 했다(#16, #55). 60거래일 학습 구간 중 녹화 전의 날에는 이 피처들이 비어 있고, 트리가 비어 있는 값의 방향을 배운다.

  > **바뀜** (2026-10-11, #59): 고유 피처 6개 → 4개. `program_net`, `member_foreign_net`은 고유에서 빠지고 공유 피처로 계속 읽는다. 이유: 스펙대로 Shannon(#26)이 프로그램매매·회원사 흐름을 쓰는데, Shannon이 먼저 등록되므로 Turing의 고유 피처로 두면 등록이 거부된다(사용자와 정함).

- 모르는 피처(백필만 있는 날의 흐름과 호가·체결, 미국 주간거래 등)는 비워 두고, 트리가 학습하면서 비어 있는 값의 방향을 정한다.
- 예측: 트리가 낸 세 확률이 그대로 예측이다. 기대수익은 학습에서 클래스별 평균 움직임(틱, `move.up`, `move.flat`, `move.down`)을 확률로 가중한 값이다.
- 학습: 최근 60거래일로 200번 부스팅한다. 학습률 0.05, 잎 15개, 잎당 최소 표본 50, 피처 80%·표본 80% 무작위 사용, L2 1. 한 스레드와 고정 시드로 돌아서, 같은 표본이면 같은 트리가 나온다.
- 학습 전(기본 모델)에는 트리가 없어서 세 확률이 같다(1/3).
- 모델은 숫자 파라미터 말고도 트리 전체를 텍스트로 가진다(`blob`). `state/models/turing.json`, 모델 이력, S3의 모델 파일에는 들어가고, 엔진 API(`/v1/algorithms`)에는 나오지 않는다. 버전 해시에 트리도 들어간다.
- 모델 버전은 `turing-<마지막 학습일>-<해시>`다.
- 호가·체결 피처는 녹화가 10거래일 쌓인 뒤 더했다(#55). 사전 검증을 거치지 않는 Turing이 검증 전의 피처를 먼저 실시간에 쓰지 않게 하려는 것이다. 이전 버전 모델(1분봉 버전)은 다음 밤 학습에서 새 모델이 이길 때까지 자기 피처로 계속 예측한다.
- 등록 순서의 맨 끝이라 CPU 예산이 모자라면 가장 먼저 건너뛴다.
- 모델 파일이 크다(트리 텍스트, 학습 표본 3,000개에 약 1MB).
- 실행 환경: LightGBM은 OpenMP가 필요하다. 서버 이미지에는 `libgomp1`을 넣었다. 맥에서 테스트하려면 `brew install libomp`가 필요하다.

## 재생

`krx-quant replay <날짜>`는 녹화된 하루를 실시간과 같은 엔진으로 다시 돌린다. 결과는 별도 DB(기본 `state/replay-<날짜>.sqlite3`, 있으면 새로 만든다)에 쓴다. KIS 키는 필요 없다. 거래 일정은 `state/market_calendar.json` 캐시를 쓰고, 없으면 평일을 거래일로 본다.

```bash
uv run krx-quant replay 2026-10-12
```

- 실시간 엔진의 DB(`state/engine.sqlite3`)와 그 옆의 `-wal`, `-shm` 파일은 `--db`로 지정해도 거부한다. 그날 녹화가 없으면 아무것도 지우지 않고 끝난다.
- 녹화 파일은 파티션마다 파일 순서대로 조금씩(4,096행씩) 읽어 받은 시각순으로 합친다. 그래서 하루가 길어도 메모리를 적게 쓴다. 서버 시계가 뒤로 물러나 앞 행보다 이른 시각이 찍힌 행은 앞 행과 같은 시각에 받은 것으로 친다.
- 출력은 기준 예측과 알고리즘별 예측 수, 건너뛴 수, 봉 마감 기준(A)의 채점·채점 불가·대기 수, 그리고 클래스 분포다.
- 알고리즘은 `state/models/`의 모델을 쓴다. 다만 재생하는 날이나 그 뒤의 데이터로 학습한 모델은 쓰지 않는다. 배운 날로 채점하게 되기 때문이다. 그런 모델은 기본 모델로 바꾸고 그 사실을 출력한다.
- 시간 예산과 CPU 예산은 실제 시간으로 잰다. 재생 시계는 알고리즘이 도는 동안 멈춰 있다. 그래서 예산에 걸리지 않는 한 재생 결과는 늘 같다. 예산에 걸리는 경우(`timed_out`, `cpu_budget`)는 기계의 속도에 따라 달라질 수 있다.
- 재생은 계산 시간을 0으로 친다. 그래서 표시 시각이 봉 마감과 같고, 표시 기준(B)이 봉 마감 기준(A)과 같다. 실시간에서는 둘 사이가 계산 시간(수 ms)만큼 벌어진다.

같은 입력을 두 번 재생하면 결과가 같다. 녹화 데이터를 손으로 만든 이벤트로 바꾼 것이 자동 테스트의 주 seam이다(`tests/test_replay.py`).
